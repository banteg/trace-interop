# trace_filter decisions H04, H23, H30, H32: should the draft change?

Read-only review, 2026-09-26. Evidence: current matrix `evidence/2026-09-26/anvil` (reports.lock.json), corpora `a`, `initial`, `h30`, `mined-probes`, `probes-forks`. Draft: banteg/execution-apis `feat/trace` at the locked `e437815d` (trace-profile.md, methods.yaml; the local checkout at e38fc96c is 11 commits behind, so the locked files were read through the GitHub API). Client source: Erigon `e26d9bd4` (main, 2026-09-24) and `bdc78cc4` (3.7.0); Nethermind `641592d2`; Reth `58a51b3e` (pinned) and `074bf32e` (#27411); Alloy `alloy-rpc-types-trace` 2.5.0; Besu `f9572aa8`; Parity `55c90d40`; geth `572bd369`.

Build labels in the matrix: Besu 26.9.0 `ee9c64c8` and 26.9-develop `accdae00`; Erigon 3.7.0 `bdc78cc4` and 3.8.0-dev `7853b922`; Nethermind 2.0.0 `bec830cd` and 2.1.0-preview `fca93966`; Reth release 2.6.0 `73a3a008` and development 2.5.2 nightly `df7b7fdf`; Anvil 1.8.3 and nightly; Geth draft fork `c8449896`.

## Bottom line

The brief starts from two premises that the evidence does not support:

1. **"Only Erigon's dev build treats an empty list as unrestricted" is false.** On `initial/filter-empty`, `a/filter-from-empty-to-set` and `a/filter-to-empty-from-set`, Besu, both Erigon builds, both Reth builds, Anvil and the Geth draft all treat `[]` as no restriction. Only Nethermind treats `[]` as "match nothing". Besu is marked ⚠️ under H04 only because the H04-tagged case `filter-from-empty-to-set` expects a SELFDESTRUCT-beneficiary record. Besu never matches that record under any filter, so the failure belongs to H23 (`rules.py:337` assigns the topic from the case name). Reth is ⚠️ under H04 only because it rejects `null` (the H14 overlap; Alloy #4257 fixes it).
2. **"H30 latest/latest breaks Erigon and Nethermind, which search history" is half false.** Nethermind defaults both bounds to latest in both builds (`h30/filter-no-bounds` returns block 48; source `TraceRpcModule.cs:294-295 ?? BlockParameter.Latest`). Only its error code for the reversed range differs (-32000). Besu does the same, and so does Reth's development build, through a Reth-maintainer-merged change (#27411). Erigon (both builds), Reth 2.6.0 and Anvil search from genesis.

With those corrected, the draft already follows the majority, or the majority plus Parity heritage, on almost every atomic rule. **Verdicts: H04 keep. H23 keep; its failed-CREATE sub-rule is kept but must be justified and tied to H09. H30 keep. H32: keep the filter-bound rules. Two simulation and single-block `pending` sub-rules and one untested hash-bound sub-rule need maintainer input.** No normative spec change is required. Several ledger and report claims are stale or misattributed (listed under "Ledger corrections").

### Findings

- Evidence: [initial/filter-empty](../../../reports/cases/initial/filter-empty.md), [a/filter-from-empty-to-set](../../../reports/cases/a/filter-from-empty-to-set.md), [a/filter-to-empty-from-set](../../../reports/cases/a/filter-to-empty-from-set.md), [a/filter-both-null](../../../reports/cases/a/filter-both-null.md), [a/filter-from-null](../../../reports/cases/a/filter-from-null.md), [a/filter-to-null](../../../reports/cases/a/filter-to-null.md) (paths relative to the trace-interop root).
- Besu treats `[]` as unrestricted deliberately: `fromAddress.isEmpty() || …` and `toAddress.isEmpty() || …` ([TraceFlatTransactionStep.java:66-80 @f9572aa8](https://github.com/besu-eth/besu/blob/f9572aa82a2dadb3dd1b218d3ca97101540faf97/ethereum/api/src/main/java/org/hyperledger/besu/ethereum/api/jsonrpc/internal/methods/TraceFlatTransactionStep.java#L66-L80)), and null → `emptyList()` ([FilterParameter.java:68-69](https://github.com/besu-eth/besu/blob/f9572aa82a2dadb3dd1b218d3ca97101540faf97/ethereum/api/src/main/java/org/hyperledger/besu/ethereum/api/jsonrpc/internal/parameters/FilterParameter.java#L68-L69)). Its miss on `filter-from-empty-to-set` is the SUICIDE record `[6,0]` with refundAddress `0x9dcd…d0`, the same record it misses on `a/filter-suicide-beneficiary` (H23).
- Reth and Anvil (Alloy) treat `[]` as unrestricted deliberately. The Alloy docs say "empty address set means match all addresses" ([filter.rs:122-136, alloy-rpc-types-trace 2.5.0](https://github.com/alloy-rs/alloy/blob/v2.5.0/crates/rpc-types-trace/src/filter.rs#L122-L136)). They reject `null` only because the field is `Vec<Address>` with `#[serde(default)]` (filter.rs:21-26).
- Erigon: a special case when both lists are empty (`trace_filtering.go:298-303`, `includeAll` at :469). Erigon #24255 (merged by Erigon maintainers, in 3.8.0-dev) documents in Erigon's ChangeLog and docs that "an omitted, `null` or empty list imposes no restriction". That is a maintainer-merged statement of H04. fixes.json records the PR only under H03.
- Nethermind's behavior is incidental. `_fromAddresses?.Contains(x) != false` treats null as unrestricted and an empty array as "no match" ([TxTraceFilter.cs:56-57 @641592d2](https://github.com/NethermindEth/nethermind/blob/641592d2/src/Nethermind/Nethermind.JsonRpc/Modules/Trace/TxTraceFilter.cs#L56-L57)). Nethermind's own eth_getLogs treats an empty set as any address (`AddressFilter.AnyAddress = new([])`, `Accepts => Addresses.Count == 0 || …`, [Facade/Filters/AddressFilter.cs:12,23](https://github.com/NethermindEth/nethermind/blob/641592d2/src/Nethermind/Nethermind.Facade/Filters/AddressFilter.cs#L12-L23)).
- Parity: `from_address: self.from_address.map_or_else(Vec::new, …)` ([trace_filter.rs:61-62](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/types/trace_filter.rs#L61-L62)); `matches_all() = list.is_empty()` ([filter.rs:39-46](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/trace/src/types/filter.rs#L39-L46)); the bloom path uses an unrestricted bloom for an empty list.

### Verdict

- R1 **keep**. Four natives (Besu, Erigon, Reth, plus Anvil), Parity and every eth_getLogs implementation agree. Nethermind is the lone outlier, and incidentally so, since it contradicts its own eth_getLogs.
- R2 **keep**. Besu, Erigon, Nethermind and Parity agree; Reth and Anvil are fixed upstream by Alloy #4257.
- R3 and R4 **keep** (uncontroversial; R4 is untested but follows from byte parsing).

### Spec delta

None.

### Consequences

- Agreement once these land: Besu (already agrees; only the harness attribution is wrong), Erigon (already), Reth and Anvil (with Alloy #4257 uptake).
- Remaining work:
  - Nethermind: normalize an empty array to "unrestricted" before matching.
  - Harness: attribute `filter-from-empty-to-set` to H23 when the expected set includes a SELFDESTRUCT beneficiary, or narrow the case to a block without one.
- Fix PRs:
  - **Nethermind #13857** (open, ours, H03) keeps `[]` restrictive. Its test comment reads "An empty list matches no address, so under union it adds no matches", and `TraceFilterMode` documents only "omitted or null list never restricts". Under union the expected outcomes happen to match H04. Under the default intersection, `{fromAddress: [], toAddress: [X]}` still returns nothing. The PR is not wrong for H03, but it encodes the non-draft semantics. Amend it, cheaply since it is open, or follow up with the H04 fix. It must not be cited as H04 progress.
  - **Erigon #24255**: consistent with H04 (and implements it under intersection). Add H04 to its decisions.
  - **Alloy #4216**: consistent (empty lists still `matches_all` under intersection).
  - **Alloy #4257**: implements R2 for Reth. Add H04, not only H14.

### Findings

- S2–S7 and S9: every native client except Besu agrees with the draft and Parity, in the live matrix, not only in source. Besu's failures share one root cause: generic `getFrom()`/`getTo()` matching ([TraceFlatTransactionStep.java:66-80](https://github.com/besu-eth/besu/blob/f9572aa82a2dadb3dd1b218d3ca97101540faf97/ethereum/api/src/main/java/org/hyperledger/besu/ethereum/api/jsonrpc/internal/methods/TraceFlatTransactionStep.java#L66-L80)). CREATE and SUICIDE actions have no `to`, SUICIDE has no `from`, and a reward has only `author`. Parity's per-action mapping is explicit ([filter.rs:96-121](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/trace/src/types/filter.rs#L96-L121)).
- Reth's and Anvil's SELFDESTRUCT-to-self misses are a revm inspector bug (revm #3834, fix #3833), not a policy choice.
- S8 is the only rule where three natives share an alternative: Erigon, Nethermind and Reth (with Anvil) all return the reverted CREATE for `toAddress: [would-be address]`. In each client that is incidental:
  - Alloy intends Parity semantics: `_ => self.to_addresses.is_empty()` when the result is not a create output ([filter.rs:176-184](https://github.com/alloy-rs/alloy/blob/v2.5.0/crates/rpc-types-trace/src/filter.rs#L176-L184)). The failed-CREATE record reaches the matcher with `result: {address, code: <revert data>, gasUsed}`, the H09 shape difference, so the create-output branch fires.
  - Erigon matches `result.Address` when a result exists (`trace_filtering.go:679-685`), and its failed CREATE also carries that result (H09).
  - Nethermind's generic `ReportAction` sets `action.To = to` for every action type ([ParityLikeTxTracer.cs:419-430](https://github.com/NethermindEth/nethermind/blob/641592d2/src/Nethermind/Nethermind.Blockchain/Tracing/ParityStyle/ParityLikeTxTracer.cs#L419-L430)), and the matcher reads it. The emitted record has `result: null` and no address anywhere.
  - Under the draft's H09 ("reject failed creation addresses"), a failed CREATE record shows no address. Matching it on the would-be address would therefore match on data the caller cannot see.
- The counter-argument deserves recording. A reverted CALL matches its `to` in every client ("membership describes actions, not committed transfers"). By symmetry a reverted CREATE could match its target, and a CREATE2 retry investigation ("every attempt to deploy at X") needs exactly that. The rule is structurally consistent only while failed-CREATE records omit the address (H09).
- Stale claims:
  - `docs/source-review/filter-selection.md §5` says Alloy/Reth and Erigon "implement" no-match for a failed CREATE. The matrix shows they match (via H09's `result.address`).
  - The H23 page says of Nethermind 2.1.0-preview: "From source: rewards never match toAddress". `rewards-to` shows the preview returning all 8 rewards (#13800 is in `fca93966`).
  - The H23 background says "no fixture covers" rewards and failed CREATE; `probes-forks` and `mined-probes` now do.
- An untested Erigon edge case remains. Erigon emits a reward whenever the coinbase is in `toAddresses`, ignoring `fromAddress` and `mode` (`trace_filtering.go:597,608`). The intersection cases pass only because the from/to txNum bitmaps did not intersect in those blocks. A block in which a sender listed in `fromAddress` also sends a transaction to the coinbase would leak the reward under intersection.

### Verdict

- S1–S7 and S9 **keep**. Erigon, Nethermind (dev) and Reth already agree, together with Parity. Only Besu differs, and Nethermind's S7 gap is an H03 issue.
- S8 **keep, but couple it explicitly to H09 and state the justification**. The shared alternative is incidental in all three clients: Alloy's code states the draft's intent, and Nethermind's record does not even show the matched address. Keeping costs little, because Erigon and Reth drop the match automatically when they adopt H09 (no `result.address` on failed CREATE), and Nethermind needs a one-line matcher guard. **Needs maintainer input only if H09's removal of the failed-CREATE address is contested.** In that case, change S8 to "a failed CREATE matches toAddress by the address its record reports", so that matching always tracks the visible record.

### Proposed recommendation text (clarification, not a behavior change)

> Define from/to equivalents per action: creator and created address for CREATE; the executing (self-destructing) account and beneficiary for SELFDESTRUCT, which after EIP-6780 usually survives; recipient only (author) for rewards. A record matches only on addresses it reports: a failed CREATE reports no created address (H09), so it can match its creator but never a populated recipient list, even though a client may know the would-be address. A reward has no from side: in intersection mode it is excluded whenever fromAddress is populated, even if other records in the same block match fromAddress, while in union mode a toAddress match suffices. Apply H03 composition. Matching a reverted action does not imply a committed transfer.

Spec delta: in trace-profile.md "Filter membership…", add "A record matches only on addresses it reports; a failed CREATE reports no created address (H09)". Add "even when other records of that block match fromAddress" to the reward sentence. methods.yaml needs no schema change.

### Consequences

- Agreement once the fixes land:
  - Erigon: matches except S8, which H09 adoption resolves, and the reward edge case.
  - Nethermind: matches except S8 and S7 (#13857).
  - Reth: matches except S8 (H09 plus Alloy) and SELFDESTRUCT to self (revm #3833).
  - Besu: needs per-action matching for CREATE, SELFDESTRUCT and rewards.
- Work: add a reward-leak case for Erigon (sender in `fromAddress` also calls the coinbase in the same block).
- Fix PRs:
  - **Nethermind #13800** (rewards by author, marked partial) is correct and remains partial for S8.
  - **revm #3833** is unaffected.
  - None becomes wrong.

## H30: omitted range bounds

### Atomic rules and behavior

| Rule | Besu | Erigon | Nethermind | Reth | Anvil | Parity | eth_getLogs analogue | Draft |
|---|---|---|---|---|---|---|---|---|
| T1 omitted fromBlock = latest (`h30/filter-no-bounds`) | ✅ block 48 | ❌ genesis (records from block 1), both builds | ✅ block 48, both builds | 2.6.0 ❌ genesis; dev `df7b7fdf` ✅ 48 (#27411) | ❌ genesis | ✅ `map_or(BlockId::Latest)` | latest in geth, Reth, Besu, Nethermind, **and Erigon's own eth_getLogs** (`begin = latest`) | latest |

### Findings

- The live matrix contradicts the brief's premise for Nethermind: it already defaults to latest ([TraceRpcModule.cs:294-295](https://github.com/NethermindEth/nethermind/blob/641592d2/src/Nethermind/Nethermind.JsonRpc/Modules/Trace/TraceRpcModule.cs#L294-L295)), faithful to Parity ([trace_filter.rs:57-58](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/types/trace_filter.rs#L57-L58)).
- Besu does the same, deliberately: it shares `FilterParameter` with eth_getLogs, defaulting to `BlockParameter.LATEST` ([FilterParameter.java:66-67](https://github.com/besu-eth/besu/blob/f9572aa82a2dadb3dd1b218d3ca97101540faf97/ethereum/api/src/main/java/org/hyperledger/besu/ethereum/api/jsonrpc/internal/parameters/FilterParameter.java#L66-L67)).
- Reth main switched to latest in [#27411 (074bf32e, 2026-09-24, Matthias Seitz)](https://github.com/paradigmxyz/reth/commit/074bf32ef193987b41ee79a93f07e2251ff6fe81), with the test `trace_filter_defaults_to_latest`, which asserts -32602 for `{toBlock: 0x1}`. The README's definition makes this a maintainer-merged position, but fixes.json and the positions column do not record it.
- Erigon's genesis default is an unexamined legacy:
  - `if req.FromBlock == nil { fromBlock = 0 }` dates from 2020 (turbo-geth, `2aa6fb50`) ([trace_filtering.go:335-336 @e26d9bd4](https://github.com/erigontech/erigon/blob/e26d9bd4056586e004488c31b561fb2663d46019/rpc/jsonrpc/trace_filtering.go#L335-L336)).
  - It contradicts Erigon's own eth_getLogs, which starts at latest ([eth_receipts.go:171,188](https://github.com/erigontech/erigon/blob/e26d9bd4056586e004488c31b561fb2663d46019/rpc/jsonrpc/eth_receipts.go#L171-L188)).
  - Since #18798 (2026-01), `trace_filter` enforces `--rpc.blockrange.limit` with a **default of 1000** ([flags.go:476-480](https://github.com/erigontech/erigon/blob/e26d9bd4056586e004488c31b561fb2663d46019/cmd/utils/flags.go#L476-L480), also in 3.7.0; check at [trace_filtering.go:393-395](https://github.com/erigontech/erigon/blob/e26d9bd4056586e004488c31b561fb2663d46019/rpc/jsonrpc/trace_filtering.go#L393-L395)).
  - So on any chain above block 1000, a default-configured Erigon already rejects an omitted fromBlock with "exceed block range", with or without address lists. The historical-search default works only on short chains or where operators set the limit to 0.
- Reth 2.6.0's genesis default fails the same way on real chains, through the 100-block cap or 4444 when pruned ([trace.rs:377, 407-413 @58a51b3e](https://github.com/paradigmxyz/reth/blob/58a51b3ee3f6714ded9207b244a273c8afb592fd/crates/rpc/rpc/src/trace.rs#L377-L413)).
- Real breaking cost falls only on Erigon archive operators with `--rpc.blockrange.limit=0` whose callers send `{toAddress:[X]}` with no bounds. Those queries are cheap in Erigon because they are index-backed (`TracesFromIdx`/`TracesToIdx`). After the change they silently return head-block matches only, not an error. The migration is one field (`fromBlock: "earliest"`, which the draft accepts) and is explicit about intent. Caller surprise is otherwise lowest with latest: it is the eth_getLogs rule every caller already knows.
- Reversed-range code: -32602 matches upstream eth_getLogs (#875, geth `errInvalidBlockRange = invalidParamsErr`, [api.go:39-42](https://github.com/ethereum/go-ethereum/blob/572bd3696587d4f9599d577c3211c23985f7e4d1/eth/filters/api.go#L39-L42)). Besu and Reth dev return it already; Nethermind's -32000 is a code-only fix.

### Verdict

- T1 and T2 **keep**. Besu, Nethermind and Reth dev agree (three natives, one maintainer-merged), as do Parity and every client's eth_getLogs, including Erigon's.
- T3 **keep** (-32602). Besu and Reth dev agree; Nethermind rejects with a different code; the rule follows eth_getLogs #875.
- The explicit-history rules (4444, no silent narrowing) **keep** (H06 scope).
- Breaking-change weighting: the change is breaking only for Erigon and only where the range cap is disabled. The breakage is silent (fewer results), so it needs a ChangeLog "Breaking" entry in Erigon, as #24255 had, and ideally an Erigon position before the spec freezes. That is maintainer input on rollout, not on the rule.

### Spec delta

None. Background and ledger updates:
- Nethermind already agrees on the default.
- Record Reth #27411 as a maintainer-merged H30 fix and position.
- Record Erigon's default 1000-block cap as evidence that its genesis default is not a usable historical-search contract on real chains.
- The H30 page's Reth row mislabels the dev build ("2.5.2 · 4630cc58" versus the matrix build `df7b7fdf`).

### Consequences

- Agreement: Besu (default and code), Nethermind (default), Reth dev, Geth draft.
- Work remaining:
  - Erigon: change fromBlock nil → latest and document it as breaking.
  - Nethermind: -32000 → -32602 for a reversed range.
  - Reth: ship #27411 in a release.
  - Anvil: follows Reth/Alloy defaults only if Foundry adopts them.
- Fix PRs:
  - **Erigon #24255** is unaffected (H03 only).
  - **Alloy #4216 and #4257** are unaffected.
  - **Nethermind #13857 and #13800** are unaffected.

### Findings

- P1 and P2 follow the upstream eth_getLogs type ([execution-apis block.yaml:133-148, filter.yaml:21-24 @5bcdc34a](https://github.com/ethereum/execution-apis/blob/5bcdc34a477b10af278c079525374e6a4046f291/src/schemas/block.yaml#L133-L148)).
  - Erigon and Nethermind implement them.
  - Besu's -32603 comes from an incomplete resolver ([TraceFilter.java:275-282](https://github.com/besu-eth/besu/blob/f9572aa82a2dadb3dd1b218d3ca97101540faf97/ethereum/api/src/main/java/org/hyperledger/besu/ethereum/api/jsonrpc/internal/methods/TraceFilter.java#L275-L282)), not a policy.
  - Reth's rejections come from Alloy's `TraceFilter` typing bounds as `u64` quantities ([filter.rs:16-19](https://github.com/alloy-rs/alloy/blob/v2.5.0/crates/rpc-types-trace/src/filter.rs#L16-L19)), which also rejects `"latest"`. No Reth case covers that yet. That matters because Parity callers do send `"latest"` explicitly.
- P3: three natives reject `pending` (Besu with the wrong code, Erigon deliberately, Reth by typing). Erigon's rejection is a documented maintainer decision: "prevents committed tracing from silently substituting the latest executed block for pending" ([tracing.go:44-53](https://github.com/erigontech/erigon/blob/e26d9bd4056586e004488c31b561fb2663d46019/rpc/jsonrpc/tracing.go#L44-L53)), and Erigon's docs say "the 'pending' tag is not supported for either block bound". Only Nethermind keeps Parity's silent latest fallback ([Parity trace_filter.rs:51-55](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/types/trace_filter.rs#L51-L55)), and that fallback printed "might be removed in future versions".
- Stale background: the H32 page says "Erigon development rejects pending with -32000 while its release resolves it to mined block 48". In the current matrix both Erigon builds reject.
- P5: no case captured. Reth and Nethermind both trace a real pending block, via generic block-id resolution rather than a trace-specific design. Parity returned `null` for `trace_block` ([traces.rs:72-75](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/impls/traces.rs#L72-L75)) and invalid params for replay ([traces.rs:137,160,184](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/impls/traces.rs#L137)). No three-client cluster exists for any alternative, and the draft's reject preserves Parity's "not supported" intent with a clearer signal. However, Reth's pending-block tracing may have users (searchers previewing the pending block).
- P7: Besu and Nethermind accept `pending` for `trace_call`/`trace_callMany` but run with NUMBER = head (0x30), indistinguishable from latest. That is the silent substitution the H32 rationale says a caller must be able to detect. Reth and Anvil provide a real pending environment (0x31). Erigon, the Geth draft and Parity reject. The draft's "must reject if not implemented" does not say whether "pending = latest" counts as implemented.
- P8: Parity ([block_number.rs](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/types/block_number.rs#L115-L156)), Erigon (`TraceFilterRequest.FromBlock *rpc.BlockNumberOrHash`, trace_filtering.go:1086-1087) and Nethermind (`BlockParameter` with a BlockHash kind) accept hash bounds. That is two natives plus Parity heritage, but only because each uses a generic block-selector type. The draft rejects them without saying so, and no case covers it.

### Verdict

- P1 and P2 **keep**. Erigon and Nethermind agree, plus the eth_getLogs type; the dissenters (Besu's internal error, Reth's missing tag support) are incidental defects.
- P3 **keep** (-32602). Erigon (deliberate), Besu and Reth reject, as eth_getLogs does. The only change is the code: Erigon -32000, Besu -32603. Nethermind's Parity fallback loses: rejection is the explicit direction of three natives, and the fallback cannot be distinguished from `latest`.
- P4 **keep** (shared tag definition). Add the pruned-node case that the ledger already plans.
- P5 **keep as an explicit deferral, needs maintainer input from Reth and Nethermind**. Both currently serve a pending-block trace; the draft asks them to reject until a pending contract (localization with a non-canonical hash) exists. Add the `trace_block("pending")` and `trace_replayBlockTransactions("pending")` cases before claiming verdicts.
- P6 **keep**.
- P7 **needs maintainer input (Besu, Nethermind)**. Proposed clarification, to make the existing rule testable:

  > For trace_call and trace_callMany, a client that accepts `pending` must evaluate it in a pending-block environment (block number head+1 and that block's header fields). A client without one must reject `pending` with -32602 rather than evaluate it as `latest`.

  This keeps Reth, Anvil and the rejecters as they are, and asks Besu and Nethermind to either implement a pending environment or reject.
- P8 **needs maintainer input (low priority), default keep (reject)**. It follows eth_getLogs, where a single block is selected by the `blockHash` member, not by range bounds. Record it as a deliberate departure from Parity, Erigon and Nethermind, and add a case (`{fromBlock: {blockHash: …}}`) so the rejection is observable. Consider -32602 for it.

### Spec delta

- trace-profile.md (simulation paragraph or "Open details"): replace "`pending` for simulations and its localization … need further agreement" with the P7 sentence above, if maintainers agree.
- Add under explicit choices: "Filter bounds do not accept block hashes or EIP-1898 objects (Parity, Erigon and Nethermind did); select a single block by number."
- The methods.yaml filter bound schema already uses the ForRange tag set; no change.

### Consequences

- Agreement once fixed:
  - Erigon: P1–P3, needing only the P3 code change to -32602.
  - Nethermind: P1 and P2; needs a P3 rejection, and P5/P7 are subject to input.
  - Besu: needs a safe/finalized resolver and the -32602 code.
  - Reth: needs tag support in Alloy's `TraceFilter`, a larger Alloy change that should cover `latest`, `earliest`, `safe` and `finalized` together, and P5 subject to input.
- Fix PRs: none in fixes.json targets H32 directly. **Alloy #4257** (null members) does not add tag support; a separate Alloy change is required, so do not mark Reth H32 as 🛠️ on the strength of #4257.
