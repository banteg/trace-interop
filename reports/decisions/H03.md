## Recommendation

Use OR within each address list and AND between `fromAddress` and `toAddress` by default. An omitted, null, or empty side imposes no restriction. Accept optional `mode: "intersection"` (the default) and `mode: "union"` (match either populated side); treat a null mode as the default, and reject unknown mode values (`-32602` recommended).

Adding a second filter should narrow a search. This matches `eth_getLogs`, where each topic position accepts a list of alternatives (OR) and all positions must match (AND); a null position is a wildcard, just as an omitted or empty address list is here. Explicit union is still useful when callers need one globally paginated result across both address sets.

## Background

Parity's [original matcher](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/trace/src/types/filter.rs#L42-L111) treats each address list as alternatives, combines sender and recipient with `&&`, and builds the Cartesian product of address blooms for indexed search. An empty list matches all addresses. The [RPC filter type](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/types/trace_filter.rs#L28-L68) had no `mode` field and rejected unknown fields. Thus intersection follows the Parity implementation, while explicit union is a later Erigon compatibility extension, not an original namespace option.

In [Erigon #2119](https://github.com/erigontech/erigon/issues/2119), banteg asked in June 2021 for an intersection option to narrow calls from a sender set to a recipient set. Erigon merged the [mode implementation in #3167](https://github.com/erigontech/erigon/pull/3167) in January 2022, corrected the list-level boolean composition in [#3304](https://github.com/erigontech/erigon/pull/3304), and [backported it to stable in #3305](https://github.com/erigontech/erigon/pull/3305). This is established client precedent for retaining an explicit mode.

[Alloy #4216](https://github.com/alloy-rs/alloy/pull/4216), merged on 2026-09-22, cites H03 and changes the default from union to intersection while retaining explicit union. Its tests cover OR within each list, AND between lists, empty lists, and both recognized modes. Reth uses [Alloy's matcher](https://github.com/paradigmxyz/reth/blob/03cb186c1d36eebbacc7bda08f36e25711d0804e/crates/rpc/rpc/src/trace.rs#L354-L371), but the tested Reth builds and [main@47c2166bc4](https://github.com/paradigmxyz/reth/blob/47c2166bc48bba25b95787c1f0640ec42bb9dee0/Cargo.lock) (checked 2026-09-23) still lock Alloy 2.4.2, which predates the PR. Reth needs dependency uptake and a retest before its observed result changes.

The pinned draft accepts recognized modes. The mode cases were recaptured on 2026-09-23 against every tested build, including one-sided `union` queries. The Geth draft fork adopted recognized modes and nullable address lists at [40eecf3647](https://github.com/banteg/go-ethereum/commit/40eecf3647f26546df9dbf72ce48f372df469ef2). Reth's null-list rejections are tracked under [H04](H04.md).

Nethermind master has no `mode` property at all ([TraceFilterForRpc.cs](https://github.com/NethermindEth/nethermind/blob/ac02224f25fd4901116ebf2643d522ec4a0e60a1/src/Nethermind/Nethermind.JsonRpc/Modules/Trace/TraceFilterForRpc.cs#L10-L24)), and its matcher is intersection-only. That explains both observations: union behaves as intersection, and an unrecognized value is accepted because nothing reads it. The Nethermind change is therefore to add a validated field, not to reimplement matching.
