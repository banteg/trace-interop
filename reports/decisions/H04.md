# Empty address lists

H04 · Spec decision · [All decisions](../README.md#decisions-to-review)

**Status: ⚪ Under review** · [Status definitions](../../decisions/README.md#status-key)

No policy conclusion has been recorded. Implementation observations below do not establish client-team agreement.

## Recommendation

Treat an omitted, null or empty address list as no restriction. A nonempty list restricts that side. Compare address bytes independently of hex letter case.

Programmatically adding an empty optional filter should not erase all results.

## Background

Parity's [RPC filter type](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/types/trace_filter.rs#L28-L67) made both address arrays optional and converted an omitted or JSON-null field to an empty vector. Its [address matcher](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/trace/src/types/filter.rs#L28-L63) explicitly treats that vector as matching all addresses; the bloom path gives it an unrestricted bloom rather than a zero-match search. This is an inherited API convention, not merely an intuition about empty filters.

The modern clients differ at both input decoding and matching. The pinned [Nethermind matcher](https://github.com/NethermindEth/nethermind/blob/a404c4f06a67aee52cc448216b8d37a77062f106/src/Nethermind/Nethermind.JsonRpc/Modules/Trace/TxTraceFilter.cs#L56) and [Erigon filter](https://github.com/erigontech/erigon/blob/c25b8e47dc1a77ecdbd15d38ba3beae1d29530ec/rpc/jsonrpc/trace_filtering.go#L311) must be read together with the linked empty/null cases: accepting a JSON field does not prove it is treated as unrestricted. H03 determines how nonempty sides compose; this decision only establishes when a side has no constraint.
