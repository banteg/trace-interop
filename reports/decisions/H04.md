# Empty address lists

**Question:** Does an empty address list in trace_filter match every record or none?

H04 · Spec decision · [All decisions](../../decisions/README.md)

**Status: 🤝 Converged** · [Status definitions](../../decisions/README.md#status-key)

Every development build treats an omitted, null or empty address list as no restriction: Besu and the Geth draft already did, and Erigon (#24255) and Nethermind (#13857) merged the change. Reth takes it through Alloy #4257, merged but not yet in an Alloy release that Reth ships. This records direction from implementations, not unanimous formal approval.

## Recommendation

Treat an omitted, null or empty address list as no restriction. A nonempty list restricts that side. Compare address bytes independently of hex letter case.

Programmatically adding an empty optional filter should not erase all results.

## Background

Parity's [RPC filter type](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/types/trace_filter.rs#L28-L67) made both address arrays optional and converted an omitted or JSON-null field to an empty vector. Its [address matcher](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/trace/src/types/filter.rs#L28-L63) explicitly treats that vector as matching all addresses; the bloom path gives it an unrestricted bloom rather than a zero-match search. This is an inherited API convention, not merely an intuition about empty filters.

The modern clients differ at both input decoding and matching. The pinned [Nethermind matcher](https://github.com/NethermindEth/nethermind/blob/a404c4f06a67aee52cc448216b8d37a77062f106/src/Nethermind/Nethermind.JsonRpc/Modules/Trace/TxTraceFilter.cs#L56) and [Erigon filter](https://github.com/erigontech/erigon/blob/c25b8e47dc1a77ecdbd15d38ba3beae1d29530ec/rpc/jsonrpc/trace_filtering.go#L311) must be read together with the linked empty/null cases: accepting a JSON field does not prove it is treated as unrestricted. H03 determines how nonempty sides compose; this decision only establishes when a side has no constraint.

### Divergent-decisions review (2026-09-26)

The [review](../../docs/reviews/2026-09-26-divergent-decisions/H04-H23-H30-H32.md) kept the rule. Every native client except Nethermind treats `[]` as unrestricted (Besu, both Erigon builds, both Reth builds), as do Anvil, Parity (`matches_all() = list.is_empty()`) and every eth_getLogs implementation, Nethermind’s own included (`AddressFilter.AnyAddress = new([])`). Nethermind is the lone outlier, incidentally: `_fromAddresses?.Contains(x) != false` treats null as unrestricted and an empty array as no match. Besu’s H04 difference is misattributed: its only failure, on `a/filter-from-empty-to-set`, is the SELFDESTRUCT-beneficiary miss tracked under H23. Reth only rejects null, because Alloy’s `TraceFilter` defaults the lists only when absent; Alloy #4257 fixes it. Erigon #24255 documents in Erigon’s ChangeLog that an omitted, null or empty list imposes no restriction. Nethermind #13857 keeps the restrictive reading in its tests and docs, so it does not count toward this decision.

## Decision needed

Review the compatibility choice to accept null alongside omitted and empty lists; retain separate checks for special-action membership. `a/filter-from-empty-to-set` also expects a SELFDESTRUCT-beneficiary record, so Besu’s miss there belongs to H23, not to empty-list handling.
