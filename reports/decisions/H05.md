# Post-merge reward records

H05 · Spec decision · [All decisions](../../decisions/README.md)

**Status: ⚪ Under review** · [Status definitions](../../decisions/README.md#status-key)

No policy conclusion has been recorded. Implementation observations below do not establish client-team agreement.

## Recommendation

Do not emit a synthetic PoW reward on a PoS block. Historical PoW rewards follow all transaction records of their block: the block reward, then uncle rewards in ommer order, each with null transaction localization. The genesis block has no transaction or reward records, so trace_block(0) and trace_replayBlockTransactions(0) return [] and filters over genesis contribute nothing. System operations (EIP-4788 and EIP-2935 pre-block calls, EIP-7002 and EIP-7251 post-block calls) and withdrawals are applied to replay state in protocol order, but they are not trace records and belong to no transaction’s stateDiff; replay arrays hold exactly one envelope per transaction. Keep transaction tips in transaction accounting.

A reward trace should correspond to a real protocol operation, not a zero-value placeholder that changes pagination. A fixed position for rewards and an explicit list of operations that are never records keep pagination offsets and replay arrays identical across clients.

## Background

Parity [added reward traces in 2017](https://github.com/openethereum/parity-ethereum/commit/06862c7dee400e3b9f37c6cfdae52c081ee9d7f1) for consensus payouts and then [made transaction IDs optional](https://github.com/openethereum/parity-ethereum/commit/1f3f91136ca9438336e5eb824ce31555ac116fae) because a reward is not a transaction. Its [serializer test](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/types/trace.rs#L814-L831) expects a `reward` action with null transaction localization. This explains why the trace model has non-transaction records at all.

[EIP-3675](https://eips.ethereum.org/EIPS/eip-3675#block-and-ommer-rewards) removed the PoW block and ommer balance increases at the Merge while leaving transaction fees in place. [EIP-4895](https://eips.ethereum.org/EIPS/eip-4895) later introduced withdrawals as block-level balance changes, but neither Parity's reward encoding nor that EIP defines a `trace_*` withdrawal action. The observed Besu and Nethermind zero-value reward placeholders therefore should not be treated as actual post-Merge rewards; whether to include withdrawals or other system changes needs an explicit separate trace contract.

Erigon already ships an opt-in representation ([PR #21592](https://github.com/erigontech/erigon/pull/21592), 2026-06-28). With the extra `traceConfig.includeWithdrawals` argument, `trace_block` appends `reward` records with `rewardType: "withdrawal"` and the value in wei ([trace_filtering.go](https://github.com/erigontech/erigon/blob/3b4861d10387ca3e19f7b16d1b8c0ec1fcd616cd/rpc/jsonrpc/trace_filtering.go#L252-L256)), and `trace_replayBlockTransactions` appends an extra envelope without a transaction hash that carries the withdrawal stateDiff ([trace_adhoc.go](https://github.com/erigontech/erigon/blob/3b4861d10387ca3e19f7b16d1b8c0ec1fcd616cd/rpc/jsonrpc/trace_adhoc.go#L1015-L1062)). It is off by default and absent from `trace_filter`. The extension lies outside the baseline: the draft’s `rewardType` enum is `block`/`uncle`, and a baseline replay array holds exactly one envelope per transaction.

No client emits records for EIP-4788, EIP-2935, EIP-7002 or EIP-7251 operations. Reth runs `apply_pre_execution_changes` untraced, Nethermind uses `NullTxTracer` for system calls, Erigon runs `InitializeBlockExecution` untraced and skips `txIndex == -1` in filters ([trace_filtering.go](https://github.com/erigontech/erigon/blob/3b4861d10387ca3e19f7b16d1b8c0ec1fcd616cd/rpc/jsonrpc/trace_filtering.go#L746-L752)), and the Geth draft replays transactions only. The draft previously stated the exclusion only for withdrawals; stating it for system operations keeps anyone from later adding them as call frames with null localization, which would shift pagination.

Reward order is already uniform: the block reward first, then uncle rewards in ommer order, after the block’s transaction records. Parity appended rewards as a trailing pseudo-transaction ([db.rs](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/trace/src/db.rs#L189-L193)), Besu inserts the block reward at index 0 of its reward list ([RewardTraceGenerator.java](https://github.com/besu-eth/besu/blob/07f0a4b2f832257842db71eacf4bca584f87fafe/ethereum/api/src/main/java/org/hyperledger/besu/ethereum/api/jsonrpc/internal/results/tracing/flat/RewardTraceGenerator.java#L95-L102)), and Erigon, Reth and the Geth draft follow the same order. The PoW block-47 evidence agrees on all nine builds.

Genesis handling differs. Reth’s `trace_block` appends a reward whenever `calculate_base_block_reward` returns one, and that function has no genesis guard ([trace.rs](https://github.com/paradigmxyz/reth/blob/861a56167cd4eee8ed66e2bfb5d54a6b0620b40d/crates/rpc/rpc/src/trace.rs#L307-L318)); on a PoW-genesis chain such as the `forks` fixture it reports a 5-ETH genesis reward that never happened, and `trace_filter` from block 0 includes it. Nethermind’s `trace_block(0)` fails because the genesis parent lookup fails ([TraceRpcModule.cs](https://github.com/NethermindEth/nethermind/blob/ac02224f25fd4901116ebf2643d522ec4a0e60a1/src/Nethermind/Nethermind.JsonRpc/Modules/Trace/TraceRpcModule.cs#L367-L371)); this is still true on current master, and a fix is being prepared. Erigon, Besu and the Geth draft return `[]`. Erigon’s filter path has no block-0 guard for the reward branch, so an address-less filter from block 0 on a PoW genesis may still emit a genesis reward (medium confidence, source only). No captured case covers genesis yet.

### Revised recommendation (2026-09-24 source review)

The previous recommendation left the placement of rewards and the status of system operations to a later decision ("specify which protocol operations belong in this namespace") and said nothing about genesis. The revision fixes all three: rewards follow a block’s transaction records in ommer order, genesis has no records, and system operations and withdrawals are applied to state but never emitted. Reward ordering and the system-operation exclusion match every tested client, so they move no client. The genesis rule moves Reth (a fabricated genesis reward on PoW-genesis chains) and Nethermind (`trace_block(0)` fails). Erigon’s opt-in withdrawal records remain a non-baseline extension. See [filter-selection §4, §8 and §9](../../docs/source-review/filter-selection.md).
