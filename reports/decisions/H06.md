# Missing transactions and paths

**Question:** When a transaction, block or trace path does not exist, does a method return null, [] or an error?

H06 · Spec decision / client exception · [All decisions](../../decisions/README.md)

**Status: 🤝 Converged** · [Status definitions](../../decisions/README.md#status-key)

Converged on null for a missing transaction or trace path: Reth and Erigon support it, Nethermind merged its alignment (#13937), matching Parity, eth_getTransactionByHash in every client, and the current behavior of Erigon, Reth and Besu (Besu for trace_get). Errors stay for what cannot be answered: pruned history returns an error, never a fake absence, and a bad range is an error (-32602 recommended). An unknown selected block errors (-32001 recommended); Erigon’s question whether it should also be null was answered on #890, and trace_replayBlockTransactions follows trace_block. This records direction from implementations and client teams, not unanimous formal approval.

Policy evidence: [Nethermind review of #13937](https://github.com/NethermindEth/nethermind/pull/13937#issuecomment-5853618602) · [Open question on execution-apis#890](https://github.com/ethereum/execution-apis/issues/890#issuecomment-5854429094) · [Reth on execution-apis#890](https://github.com/ethereum/execution-apis/issues/890#issuecomment-5854639007) · [Erigon on execution-apis#890](https://github.com/ethereum/execution-apis/issues/890#issuecomment-5856824874) · [Unknown-block answer on execution-apis#890](https://github.com/ethereum/execution-apis/issues/890#issuecomment-5857021080).

## Recommendation

Return null for a well-formed lookup of a transaction that is not in a canonical block, or of a missing trace path, consistently across these methods. Reserve [] for a successfully evaluated collection with no elements. Preserve -32601 for unsupported methods and return errors for unavailable/pruned state instead of pretending data is absent. For an unknown selected block, trace_block and trace_replayBlockTransactions accept null or an error (-32001, Resource not found, recommended); neither may return a successful collection. An unknown trace_call/trace_callMany block returns an error (-32001 recommended). Where clients already agree, the draft keeps their answer: null for a missing transaction or path. For block lookup, retain both the errors Erigon, Nethermind and Reth return and the null Besu and Parity return; the original null was coherent, so grandfathering does not require a harmonization change. trace_filter bounds follow eth_getLogs: if either bound resolves beyond the current head, or fromBlock resolves above toBlock, return an error, with -32602 (Invalid params) recommended; never clamp the range or return a partial result. earliest means the lowest available block; an explicit number below retained history returns an error (4444 recommended). If pruned indexing prevents establishing whether a hash is absent, return an error (4444 recommended) rather than a definitive not-found result. Error codes are recommended throughout; the error response itself is required (H14).

Not found, empty, unsupported and unavailable are different states that callers need to distinguish.

## Background

Parity's [trace lookup methods](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/src/client/client.rs#L2052-L2110) returned `Option`: absent transaction, missing trace data and disabled tracing could all become JSON `null`; [mocked RPC tests](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/tests/mocked/traces.rs#L83-L166) confirm null for missing trace storage. By contrast, its [ad hoc call path](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/impls/traces.rs#L108-L127) raises an explicit state-pruned error when required state is absent. Separating absence from unavailability improves on a real historical ambiguity.

[EIP-1474](https://eips.ethereum.org/EIPS/eip-1474#error-codes) names `-32001` Resource not found and `-32002` Resource unavailable. [execution-apis #636](https://github.com/ethereum/execution-apis/pull/636), merged on 2025-10-14, defines `4444` (Pruned history unavailable) for several eth/debug methods, including `eth_getLogs`. Extending that code to trace methods and pruned execution state is the proposal here, not an already adopted trace policy. A requested range must not silently become a partial search at the retention boundary. [Reth #27367](https://github.com/paradigmxyz/reth/pull/27367) and the linked pruning cases show why unavailable state must not serialize as an apparent empty result.

[EIP-4444's JSON-RPC discussion](https://eips.ethereum.org/EIPS/eip-4444#json-rpc-changes) notes that pruned indexing may prevent distinguishing an unknown hash from an old one. When this prevents establishing absence, return unavailable history rather than claiming `null` proves the transaction never existed. An absent path in a successfully obtained tree still returns `null`. Harmonizing missing individual replay to `null` is also deliberate: Parity's replay path used a transaction-not-found error, unlike its indexed lookups.

Nethermind master at ac02224f broke out of the `trace_filter` block loop and returned the records gathered so far when a block or its parent lacked state (`TryResolveParentForTracing`, [TraceRpcModule.cs](https://github.com/NethermindEth/nethermind/blob/ac02224f25fd4901116ebf2643d522ec4a0e60a1/src/Nethermind/Nethermind.JsonRpc/Modules/Trace/TraceRpcModule.cs#L299-L346)); genesis has no parent, so every range starting at block 0 returned `[]`. That is the silent narrowing this decision forbids. [Nethermind #13677](https://github.com/NethermindEth/nethermind/pull/13677) (2a3b2531, merged 2026-09-24) rejects missing state or parent up front and skips genesis in `trace_filter`. The development build in the current matrix, 2.2.0-preview · 287f54f0, contains it and returns the records for ranges from genesis; release 2.0.0 · bec830cd predates it and returns `[]`.

Reth main (861a5616) returns null for a missing individual replay ([#27364](https://github.com/paradigmxyz/reth/pull/27364)); released 2.6.0 still errored, and 2.7.0 returns null.

### Revised recommendation (2026-09-24 source review)

The previous recommendation also used -32001 for unknown range endpoints. [execution-apis #875](https://github.com/ethereum/execution-apis/pull/875) (0a4179bc, 2026-09-07) since requires `eth_getLogs` to return -32602 when a bound resolves beyond the head or the bounds are reversed, and forbids clamping ([filter.yaml](https://github.com/ethereum/execution-apis/blob/465d1b98d43e94ff3d57e904fd7d4bea7f6b804c/src/eth/filter.yaml#L153-L160)); Geth implements it as invalid-params errors ([eth/filters/api.go](https://github.com/banteg/go-ethereum/blob/fa8ecb9242dda61858c44cf43c70d00548fbd7cd/eth/filters/api.go#L39-L42)). The trace draft already mirrors getLogs for filter composition and defaults, so it now follows this contract too. On `a/missing-block-filter` (toBlock 0xffff at head 0x30) the change flips Besu, whose `FilterParameter.validateBlockRange` is shared with eth_getLogs and already returns -32602 ([FilterParameter.java](https://github.com/besu-eth/besu/blob/07f0a4b2f832257842db71eacf4bca584f87fafe/ethereum/api/src/main/java/org/hyperledger/besu/ethereum/api/jsonrpc/internal/parameters/FilterParameter.java#L193-L209)), from differing to agreeing, and flips Reth and the Geth draft, which return -32001, from agreeing to differing. Erigon (`[]`) and Nethermind (-32000) differ under either rule. Reth main still returns `HeaderNotFound` for such bounds ([trace.rs](https://github.com/paradigmxyz/reth/blob/861a56167cd4eee8ed66e2bfb5d54a6b0620b40d/crates/rpc/rpc/src/trace.rs#L381-L388)). Single-block selectors return -32001. Only Reth does so today. Erigon, Nethermind, Besu (for the trace_call block) and Parity (for trace_call and replayBlockTransactions, under a misleading state-pruning message) return -32000, and upstream `debug_traceBlockByHash`/`debug_traceTransaction` fixtures also use -32000. `eth_getBlockAccessList` returns null for an unknown block; only `debug_getRawBlockAccessList` specifies -32001. The dedicated code is kept because in trace_call and trace_callMany every native client also uses -32000 for transaction-validation failures, so a caller cannot tell "unknown block" from "invalid call" without parsing the message. See [filter-selection §1, §3 and §10](../../docs/source-review/filter-selection.md).

### Divergent-decisions review (2026-09-26)

The [review](../../docs/reviews/2026-09-26-divergent-decisions/H06-H09.md) kept every rule and corrected the rationale for -32001. Null for a missing transaction or path has a real cluster (Erigon, Reth and Parity’s indexed lookups); the dissent is incidental, a module-wide receipt helper in Nethermind and an `orElse(empty)` fallback in Besu and Anvil. An unknown single block errors in most native clients, but the code does not converge on the draft: Erigon, Nethermind, Besu and Parity return -32000 and only Reth -32001. The earlier claim that -32001 matches the eth/debug getters was half wrong and is replaced above; -32001 is kept because -32000 already means an invalid call in every native trace_call. Anvil’s agreement on `a/missing-block-filter` is false: it trips its 300-block range cap, not the bound check. Pruned state has no convergence: Nethermind deliberately uses -32002, and Reth #27367, #27378 and alloy-evm #411 assume 4444, so they would change only if that code is replaced.

### Null versus a not-found error (2026-09-27)

Nethermind's reviewer objected to [#13937](https://github.com/NethermindEth/nethermind/pull/13937), which aligned its missing-transaction lookups with the draft's null: he prefers meaningful errors over nulls, and would argue for other clients to move to errors. The draft's null follows Parity and the other native trace clients (Erigon and Reth for both methods, Besu for trace_get) and eth_getTransactionByHash, so it was not introduced by the spec. The case for an error is that null is ambiguous where history is pruned: a caller cannot tell a transaction that never existed from one that is no longer indexed. The draft answers part of that with 4444 when pruned indexing prevents establishing absence, but not the general case. Nethermind's current not-found code is the generic -32000, so an error contract would also need a dedicated code. From the caller's side the two answers lead to different actions. A null reads as a definitive "nothing here", and the caller gives up; an error such as "history unavailable, lookup inconclusive" tells the caller to retry against an archive node. So null is only safe when the node can prove absence (a complete transaction index), and any node that cannot must return an error. The open question is narrower than null against errors: whether a proven absence should also be an error, as Nethermind prefers, and how a client signals that it cannot prove absence in general, beyond the pruned-index case. The missing-transaction rule is therefore diverging until client teams settle it.

### eth_getTransactionByHash precedent (2026-09-27)

A static check of eth_getTransactionByHash for an unknown hash: the execution-apis schema returns `notFound` (null), and every client returns null. [Geth](https://github.com/ethereum/go-ethereum/blob/920c07774c65ebb3023536f85df642c44478b540/internal/ethapi/api.go) returns null only once its transaction index is complete, and -32000 "transaction indexing is in progress" (code marked "to be decided") while it is not. [Erigon](https://github.com/erigontech/erigon/blob/5f59ece1667/rpc/jsonrpc/eth_txs.go) returns null for an unknown hash but a pruned-history error when the lookup finds the transaction in a pruned block. [Nethermind](https://github.com/NethermindEth/nethermind/blob/971d87d767/src/Nethermind/Nethermind.JsonRpc/Modules/Eth/EthRpcModule.cs), [Reth](https://github.com/paradigmxyz/reth/blob/863f7055d8/crates/rpc/rpc-eth-api/src/helpers/transaction.rs) and Besu return null for every miss. No client errors on a provable miss, and Geth's indexing error is shipped precedent for null when absence is provable and an error when the lookup is inconclusive, the first option raised on execution-apis#890. An error for every miss would also make Nethermind's trace_transaction disagree with its own eth_getTransactionByHash. Reth [supports keeping null](https://github.com/ethereum/execution-apis/issues/890#issuecomment-5854639007) for hash-based lookups as the least bad option, since most clients already return it and applications would not need to handle new behavior.

### Erigon supports null; unknown blocks reopened (2026-09-27)

[Erigon](https://github.com/ethereum/execution-apis/issues/890#issuecomment-5856824874) wants the trace methods to answer as its eth_* methods do, one rule per state: null for a missing entity, [] for a query that ran and matched nothing, -32602 for a bad range (eth_getLogs after execution-apis#875), and an error for pruned history, never a fake absence. Erigon already refuses pruned trace requests (checkPruneHistory and checkBlockHistoryAvailable guard six trace_adhoc.go call sites and trace_filter), but `state.PrunedError` carries no RPC code, so they surface as -32000. With Reth also supporting null, the missing-transaction rule converges; Nethermind's preference for errors is recorded, and merging its alignment PR would settle it. Erigon also points out an inconsistency: the draft justifies null for a missing transaction by eth_getTransactionByHash, yet gives an unknown selected block -32001 where eth_getBlockByNumber returns null. One consistent criterion would be that lookups of a missing entity return null (trace_transaction, trace_get, and arguably trace_block and trace_replayBlockTransactions, as eth_getBlockByNumber), while methods that must execute at the selected block (trace_call, trace_callMany) return an error, as eth_call does.

### Unknown-block agreement corrected (2026-09-27)

The draft said an unknown block errors "as every client already does for `trace_block`". The 2026-09-27 eval shows Besu returns null from both trace_block and trace_replayBlockTransactions, as Parity's trace_block did (its replay errored), and Anvil returns `[]`; Reth errors from trace_block but returns null from replay. Error remains the cheaper rule (Besu, Reth's replay and Anvil change, against five methods under null), and the schema's non-nullable results require it, but it is a harmonization choice. The draft now names the clients that already error.

### Grandfathered unknown-block lookup (2026-09-30)

The decision review found no strong reason to reject Parity’s coherent null for an unknown trace_block. Accept null or an error for unknown block lookups, with trace_replayBlockTransactions following trace_block. Preserve mandatory errors for unavailable/pruned state, uncertain absence, simulation blocks and invalid filter ranges. The updated pinned draft and quoted decision table now permit both conventions. Null result schemas are restricted to the block lookup methods; simulation and pruned-state errors remain required.

## Decision needed

Extend the retention fixture to Erigon, Nethermind and Besu; the current pruning result is Reth-only, and Reth answers its pruned trace methods with an internal error (-32603), a server failure rather than the required error. `probes-forks/range-reversed` checks an explicit reversed range (fromBlock 3, toBlock 2); Erigon development returns -32602 for it since #24341, Nethermind development since #13935, and Nethermind 2.0.0’s -32000 now agrees too. `a/missing-block-replay` replays an unknown block: Erigon, Nethermind and the Geth draft error, Besu and Reth return null (Reth locks that in an integration test) and Anvil returns `[]`. `a/missing-block-filter-next` ends one block past the head: Besu and the Geth draft return -32602, Erigon `[]`, Nethermind -32000, Reth -32001 and Anvil the head’s records; with codes recommended since 2026-09-29, only Erigon and Anvil differ there, in behavior. Which code to recommend for unavailable state stays open: Nethermind deliberately returns -32002 (Resource unavailable) for missing state, and only Reth has a pruned case, so settle 4444 against -32002 after a Nethermind or Erigon pruned case; either way an error is required. Nethermind, which preferred errors, merged [#13937](https://github.com/NethermindEth/nethermind/pull/13937), recording null for a missing transaction as agreed: its development build returns null from trace_transaction and trace_get, while trace_replayTransaction still returns -32000. Erigon's question on unknown blocks is [answered](https://github.com/ethereum/execution-apis/issues/890#issuecomment-5857021080): the September 29 draft requested errors, but the accepted September 30 compatibility relaxation permits null or an error for both block lookup methods. The existing Besu #11381 and Reth #27478 proposals remain valid choices, but are no longer required for conformance.
