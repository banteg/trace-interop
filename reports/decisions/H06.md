# Missing transactions and paths

H06 · Spec decision / client exception · [All decisions](../../decisions/README.md)

**Status: ⚪ Under review** · [Status definitions](../../decisions/README.md#status-key)

No policy conclusion has been recorded. Implementation observations below do not establish client-team agreement.

## Recommendation

Return null for a well-formed lookup of a transaction that is not in a canonical block, or of a missing trace path, consistently across these methods. Reserve [] for a successfully evaluated collection with no elements. Preserve -32601 for unsupported methods and use errors for unavailable/pruned state instead of pretending data is absent. An unknown single selected block (trace_block, trace_replayBlockTransactions, the trace_call/trace_callMany block) returns -32001 (Resource not found). trace_filter bounds follow eth_getLogs: if either bound resolves beyond the current head, or fromBlock resolves above toBlock, return -32602 (Invalid params); never clamp the range or return a partial result. earliest means the lowest available block; an explicit number below retained history returns 4444. If pruned indexing prevents establishing whether a hash is absent, return 4444 rather than a definitive not-found result.

Not found, empty, unsupported and unavailable are different states that callers need to distinguish.

## Background

Parity's [trace lookup methods](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/src/client/client.rs#L2052-L2110) returned `Option`: absent transaction, missing trace data and disabled tracing could all become JSON `null`; [mocked RPC tests](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/tests/mocked/traces.rs#L83-L166) confirm null for missing trace storage. By contrast, its [ad hoc call path](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/impls/traces.rs#L108-L127) raises an explicit state-pruned error when required state is absent. Separating absence from unavailability improves on a real historical ambiguity.

[EIP-1474](https://eips.ethereum.org/EIPS/eip-1474#error-codes) names `-32001` Resource not found and `-32002` Resource unavailable. [execution-apis #636](https://github.com/ethereum/execution-apis/pull/636), merged on 2025-10-14, defines `4444` (Pruned history unavailable) for several eth/debug methods, including `eth_getLogs`. Extending that code to trace methods and pruned execution state is the proposal here, not an already adopted trace policy. A requested range must not silently become a partial search at the retention boundary. [Reth #27367](https://github.com/paradigmxyz/reth/pull/27367) and the linked pruning cases show why unavailable state must not serialize as an apparent empty result.

[EIP-4444's JSON-RPC discussion](https://eips.ethereum.org/EIPS/eip-4444#json-rpc-changes) notes that pruned indexing may prevent distinguishing an unknown hash from an old one. When this prevents establishing absence, return unavailable history rather than claiming `null` proves the transaction never existed. An absent path in a successfully obtained tree still returns `null`. Harmonizing missing individual replay to `null` is also deliberate: Parity's replay path used a transaction-not-found error, unlike its indexed lookups.

Nethermind master at ac02224f broke out of the `trace_filter` block loop and returned the records gathered so far when a block or its parent lacked state (`TryResolveParentForTracing`, [TraceRpcModule.cs](https://github.com/NethermindEth/nethermind/blob/ac02224f25fd4901116ebf2643d522ec4a0e60a1/src/Nethermind/Nethermind.JsonRpc/Modules/Trace/TraceRpcModule.cs#L299-L346)); genesis has no parent, so every range starting at block 0 returned `[]`. That is the silent narrowing this decision forbids. [Nethermind #13677](https://github.com/NethermindEth/nethermind/pull/13677) (2a3b2531, merged 2026-09-24) rejects missing state or parent up front and skips genesis in `trace_filter`. The captured development build 641592d2 contains it and returns the records for ranges from genesis; release 2.0.0 · bec830cd predates it and returns `[]`.

Reth main (861a5616) returns null for a missing individual replay ([#27364](https://github.com/paradigmxyz/reth/pull/27364)); released 2.6.0 still errors.

### Revised recommendation (2026-09-24 source review)

The previous recommendation also used -32001 for unknown range endpoints. [execution-apis #875](https://github.com/ethereum/execution-apis/pull/875) (0a4179bc, 2026-09-07) since requires `eth_getLogs` to return -32602 when a bound resolves beyond the head or the bounds are reversed, and forbids clamping ([filter.yaml](https://github.com/ethereum/execution-apis/blob/465d1b98d43e94ff3d57e904fd7d4bea7f6b804c/src/eth/filter.yaml#L153-L160)); Geth implements it as invalid-params errors ([eth/filters/api.go](https://github.com/banteg/go-ethereum/blob/fa8ecb9242dda61858c44cf43c70d00548fbd7cd/eth/filters/api.go#L39-L42)). The trace draft already mirrors getLogs for filter composition and defaults, so it now follows this contract too. On `a/missing-block-filter` (toBlock 0xffff at head 0x30) the change flips Besu, whose `FilterParameter.validateBlockRange` is shared with eth_getLogs and already returns -32602 ([FilterParameter.java](https://github.com/besu-eth/besu/blob/07f0a4b2f832257842db71eacf4bca584f87fafe/ethereum/api/src/main/java/org/hyperledger/besu/ethereum/api/jsonrpc/internal/parameters/FilterParameter.java#L193-L209)), from differing to agreeing, and flips Reth and the Geth draft, which return -32001, from agreeing to differing. Erigon (`[]`) and Nethermind (-32000) differ under either rule. Reth main still returns `HeaderNotFound` for such bounds ([trace.rs](https://github.com/paradigmxyz/reth/blob/861a56167cd4eee8ed66e2bfb5d54a6b0620b40d/crates/rpc/rpc/src/trace.rs#L381-L388)). Single-block selectors keep -32001, matching the eth/debug getters. See [filter-selection §1, §3 and §10](../../docs/source-review/filter-selection.md).
