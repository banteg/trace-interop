# Creation result field names

**Question:** Which fields and values describe a creation result and a call action?

H10 · Spec decision / likely schema fix · [All decisions](../../decisions/README.md)

**Status: ⚪ Under review** · [Status definitions](../../decisions/README.md#status-key)

No policy conclusion has been recorded. Implementation observations below do not establish client-team agreement.

[Client positions](../../decisions/README.md#client-positions): none recorded.

## Recommendation

Use result.address, result.code and result.gasUsed for successful creation. result.code is deployed runtime bytecode, including "0x" for an empty deployment. Use result.output for CALL results; vmTrace.code for executing initcode. Every create action carries creationMethod, "create" or "create2", from the opcode that created that frame. CALL and STATICCALL report the caller as from and the target as to; DELEGATECALL and CALLCODE report the executing address as from and the code address as to. DELEGATECALL value is the inherited value and STATICCALL value is 0.

Creation has two different bytecodes—initcode and deployed code—and their field meanings should remain distinct.

## Background

Parity's [CreateResult type](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/types/trace.rs#L432-L450) has `gasUsed`, `code` and `address`; its [serializer test](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/types/trace.rs#L748-L769) expects those exact keys. The [executive tracer](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/trace/src/executive_tracer.rs#L112-L125) fills `code` from the completed creation's deployed bytes; the action's `init` records constructor input. The [VM trace type](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/types/trace.rs#L109-L124) separately describes executing code.

Parity later [distinguished CREATE from CREATE2](https://github.com/openethereum/parity-ethereum/commit/87e108058125098ec404951393a054f08aebef7a) and [restored backward-compatible encoding](https://github.com/openethereum/parity-ethereum/commit/dcc6307f8a5f6037db6c99989d684985be9b8826). That history concerns creation-method metadata, not a change from `code` to `output`. The pinned [Besu flat-trace generator](https://github.com/besu-eth/besu/blob/d997aad7b3be6333464c0687d3761c568ee63524/ethereum/api/src/main/java/org/hyperledger/besu/ethereum/api/jsonrpc/internal/results/tracing/flat/FlatTraceGenerator.java#L330-L365) handles call output and creation code in adjacent branches, making the linked mixed-creation case important for checking where the published result gets its field name.

The zero-fee [constructor](../cases/initial/call-constructor.md) and [environment](../cases/coverage/model-environment-free.md) requests are H15 fee-validation probes. A fee-cap rejection has no creation result to assess, so H10 requires their priced counterparts instead. If a zero-fee request executes, the general creation-result assertion still checks its fields.

Parity emitted `creationMethod` ([trace.rs](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/types/trace.rs#L217-L229)). Erigon, Nethermind, Reth and the Geth draft emit it on every create frame in the evidence, and Alloy defaults it when absent. Besu emits it on 116 of 586 create frames and computes it per transaction: every create frame is labelled `create2` if any frame in the transaction executed CREATE2 ([FlatTraceGenerator.java](https://github.com/besu-eth/besu/blob/07f0a4b2f832257842db71eacf4bca584f87fafe/ethereum/api/src/main/java/org/hyperledger/besu/ethereum/api/jsonrpc/internal/results/tracing/flat/FlatTraceGenerator.java#L651-L666)). The `from`/`to`/`value` rules per call type are Parity’s ([trace.rs](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/trace/src/types/trace.rs#L225-L245)); all five implementations agree on them in the matrix.

### Revised recommendation (2026-09-24 source review)

The previous next step left creationMethod undecided and the action fields per call type unwritten. creationMethod is now required with the values `create` and `create2`, because CREATE2 changes address derivation and nothing else distinguishes the two. Only Besu moves. The call-type rules describe what every client already reports. See [call-trace A1 and A5](../../docs/source-review/call-trace.md).

Supporting controls (not standalone assertions): [repeat/debug-mixed-create](../cases/repeat/debug-mixed-create.md).
