## Recommendation

Accept an empty selection, execute the call and return its output with empty/unrequested components. Never leak a collection-reduction exception.

An empty list of auxiliary views is a useful request for execution output alone. Its validity should not depend on whether detail tracers are enabled; fee-validation differences in the captured calls do not establish identical cross-client behavior.

## Background

The [OpenEthereum trace guide](https://openethereum.github.io/JSONRPC-trace-module#trace_call) describes the requested trace types as an array containing one or more of `vmTrace`, `trace` and `stateDiff`. The [Parity RPC trait](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/traits/traces.rs#L44-L58), however, used a plain vector; its [option mapping and call execution](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/impls/traces.rs#L36-L42) have no nonempty guard. With an empty vector all detail tracers are off, while the call still executes and yields its output. This is observed source behavior, not a documented promise.

The linked Nethermind case reaches an internal collection-reduction exception for an empty selection. That is independently a reporting bug. The proposed contract chooses to accept [] because output-only execution is useful and follows the same envelope rules as other selections; it intentionally clarifies the guide’s narrower “one or more” wording. A deliberate -32602 would be well formed but would still differ from this proposed selection policy.
