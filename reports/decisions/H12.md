# Raw-transaction block argument

**Question:** Does trace_rawTransaction take a block argument, and which state does it run against?

H12 · Spec / extension decision · [All decisions](../../decisions/README.md)

**Status: 🤝 Converged** · [Status definitions](../../decisions/README.md#status-key)

Every build runs two-argument trace_rawTransaction against latest state in the head block environment, so the baseline is settled. The optional third block selector is an extension: Reth and Anvil honor it (the selected block’s post-state and header; pending uses the next-block environment over latest), and Erigon, Nethermind, Besu and the Geth draft reject it with -32602. No client ignores it. This records direction from implementations, not unanimous formal approval.

Policy evidence: [H12 raw-selector capture (2026-09-29)](https://github.com/banteg/trace-interop/blob/main/evidence/2026-09-29/raw-selector/README.md).

[Client positions](../../decisions/README.md#client-positions): none recorded.

[Rule in the pinned draft](https://github.com/banteg/execution-apis/blob/7281ad53dea560ed99859319ebe60a8240fedabc/docs-api/docs/trace-profile.md#explicit-choices-in-this-draft)

## Recommendation

Standardize the two-argument baseline with latest state. Observe an explicitly supplied third block selector as an extension, without marking its acceptance or rejection as baseline conformance. An accepted request alone does not prove that the selected state was used. Agree extension semantics and unsupported-argument errors separately.

The baseline should be usable on all four today without silently changing which state is traced.

## Background

The [OpenEthereum guide](https://openethereum.github.io/JSONRPC-trace-module#trace_rawtransaction) documents only raw bytes and trace types. Parity's [RPC trait](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/traits/traces.rs#L55-L61) and [implementation](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/impls/traces.rs#L148-L169), however, accepted an optional third `BlockNumber`, defaulted omission to latest, and used the selected state and header. Explicit pending was rejected. The original published examples and source therefore disagree about whether the third argument was part of the public contract.

The pinned [Reth implementation](https://github.com/paradigmxyz/reth/blob/03cb186c1d36eebbacc7bda08f36e25711d0804e/crates/rpc/rpc/src/trace.rs#L120-L141) likewise takes an optional block ID and selects its EVM environment; [Erigon](https://github.com/erigontech/erigon/blob/c25b8e47dc1a77ecdbd15d38ba3beae1d29530ec/rpc/jsonrpc/trace_adhoc.go#L1656), [Nethermind](https://github.com/NethermindEth/nethermind/blob/a404c4f06a67aee52cc448216b8d37a77062f106/src/Nethermind/Nethermind.JsonRpc/Modules/Trace/TraceRpcModule.cs#L141) and the Geth draft fork expose two parameters in the pinned source. Accepted third-argument syntax still requires an observable state-selection test, as the existing decision says.

The third selector is an inherited optional capability omitted from the old guide, not a newly invented Reth feature. The portable two-argument baseline reflects current client coverage while leaving that capability available. Adoption of a shared selector contract requires state-sensitive probes, not just accepted syntax. A historical selector means that block’s post-state; it is not necessarily the selected transaction’s pre-state, so it does not by itself make an already-mined signed transaction valid under H13.

### State-sensitive probes (2026-09-29)

The `raw-selector` corpus signs one creation from a hivechain account that never transacts on chain a, so it is valid at every block. It returns NUMBER, BASEFEE and the balance of an account whose one-wei receipts make block 0x19’s post-state, block 0x18’s post-state and latest distinguishable. On all eleven builds of the 2026-09-29 refresh, two arguments ran against the latest post-state in the head environment (NUMBER 0x30 and the head’s BASEFEE), as `trace_call` does at latest; `initial/raw-valid-current-nonce` agrees through the sender nonce its stateDiff starts from. No build ignored an explicit selector. Reth and Anvil honor it: block 0x19 by number, hash and EIP-1898 object ran on that block’s post-state in its own header environment, `latest` matched the two-argument request, and `pending` ran on the latest state in a next-block environment (NUMBER 0x31 with the EIP-1559 successor base fee); on `initial/raw-valid` both start from sender nonce 0 at block 0. Besu, Erigon, Nethermind and the Geth draft reject every third argument, `latest` included, with -32602.

Source at the current default branches agrees. [Reth](https://github.com/paradigmxyz/reth/blob/4f34cad8f2e9c4df1613be1fb37313138bda8e39/crates/rpc/rpc/src/trace.rs#L120-L146) resolves `block_id.unwrap_or_default()` (latest) through `evm_env_at` and `spawn_with_state_at_block`: a named block uses its own header, and `pending` without a consensus-layer pending block uses a [synthetic next-block environment](https://github.com/paradigmxyz/reth/blob/4f34cad8f2e9c4df1613be1fb37313138bda8e39/crates/rpc/rpc-eth-api/src/helpers/pending_block.rs#L71-L107). [Anvil](https://github.com/foundry-rs/foundry/blob/965a885f74b3ed03832bc29301c446f528073b8b/crates/anvil/src/eth/api.rs#L1674-L1689) builds `pending` from its pool’s ready transactions and [selects the stored state and header](https://github.com/foundry-rs/foundry/blob/965a885f74b3ed03832bc29301c446f528073b8b/crates/anvil/src/eth/backend/mem/mod.rs#L6859-L6931) for other blocks. [Nethermind](https://github.com/NethermindEth/nethermind/blob/de17a1a837375b742b91c65527aa517a99ee87bc/src/Nethermind/Nethermind.JsonRpc/Modules/Trace/TraceRpcModule.cs#L206-L222), [Erigon](https://github.com/erigontech/erigon/blob/79432aecaea707ef63c03d65bc2238fa4124bd61/rpc/jsonrpc/trace_adhoc.go#L1820-L1968), [Besu](https://github.com/besu-eth/besu/blob/c197ac57d1c4c132f68a9e3c3e056f360b417a93/ethereum/api/src/main/java/org/hyperledger/besu/ethereum/api/jsonrpc/internal/methods/TraceRawTransaction.java#L70-L73) and the [Geth draft](https://github.com/banteg/go-ethereum/blob/e26833e3322f918c365f74be6971061c41736fc5/eth/tracers/trace_namespace.go#L102-L129) hard-code latest, and their dispatchers reject extra parameters as invalid params. No implementation executes on the selected block’s pre-state. Validity at the selected state (H13) differs separately: Besu, Erigon, Reth, Anvil and the Geth draft check nonce and balance against it, while Nethermind [replaces the signed nonce with the state nonce](https://github.com/NethermindEth/nethermind/blob/de17a1a837375b742b91c65527aa517a99ee87bc/src/Nethermind/Nethermind.Consensus/Processing/TransactionProcessorAdapterExtensions.cs#L20-L23) and Parity [skipped the nonce check and topped up the balance](https://github.com/openethereum/openethereum/blob/6c2d392d867b058ff867c4373e40850ca3f96969/crates/ethcore/src/client/client.rs#L1614-L1648). Parity’s [selector](https://github.com/openethereum/openethereum/blob/6c2d392d867b058ff867c4373e40850ca3f96969/crates/rpc/src/v1/impls/traces.rs#L192-L235) also took the selected block’s post-state and header, accepting numbers, `latest`, `earliest` and block-hash objects.

## Decision needed

Decide the extension contract with client teams. The implementations that accept a selector already agree on its semantics: the selected block’s post-state in its own header environment, and for `pending` the next-block environment over latest (Reth, Anvil, and Parity except `pending`); every other build rejects it with -32602 and none ignores it. A contract stating exactly that, with -32602 from a server without the extension, would change no tested build. Keep extension requests outside baseline assessment: `raw-selector` classifies them as extension observations, while its two-argument case and `initial/raw-valid-current-nonce` assess the latest baseline.
