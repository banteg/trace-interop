# Signed transaction execution validity

**Question:** Which validity checks does trace_rawTransaction apply to a signed transaction before tracing it?

H13 · Compatibility change / validation policy proposal · [All decisions](../../decisions/README.md)

**Status: 🤝 Converged** · [Status definitions](../../decisions/README.md#status-key)

Converged on strict execution validation, including nonce, balance and sender-code checks. Error codes are recommended, not required (2026-09-29): the eth_sendRawTransaction groups with the -32003 fallback, so a rejection agrees when it names its own violation. Erigon’s development build and Reth agree; Besu differs in behavior, and compatibility migration remains open. Nethermind explicitly supports block-inclusion validation for trace_rawTransaction and permissive eth_call-like trace_call (2026-09-30), and its development build implements it (#14091, captured 2026-10-01).

## Recommendation

Validate trace_rawTransaction for execution against the selected state and fork: signature, chain identity, nonce equality (both low and high), balance for value and upfront gas, intrinsic gas, fees and sender-code restrictions with the EIP-7702 delegation exception. Do not change signed fields, override the sender nonce or supplement its balance. This is not pool admission: exclude local replacement, already-known and minimum-tip policies. Reject a decodable transaction that fails validation for the rule it violates, and report that violation: a transaction signed for another chain fails chain identity, not the funds of the sender its signature recovers. The eth_sendRawTransaction error groups are recommended: 1 nonce too low, 2 nonce too high, 800 intrinsic gas, 804 priority fee above fee cap, 806 fee cap below base fee and 809 insufficient funds, with -32003 (Transaction rejected) as the generic fallback; a signed gas limit above the server’s execution cap is rejected (-38026 recommended) rather than reduced; malformed encoding or parameters are rejected (-32602 recommended). Valid execution that REVERTs or halts still returns a trace.

A signed trace should describe those bytes executing against the selected state. Skipping nonce validation can change CREATE addresses and nonce-dependent behavior; overriding nonce or balance instead invents a different pre-state. Strict validation intentionally tightens historical permissive simulation and can reject queued or already-mined transactions at latest state. Client acceptance alone does not establish a deliberate nonce policy, and malformed error JSON does not prove validation was skipped.

## Background

[Erigon supports strict execution validation](https://github.com/ethereum/execution-apis/issues/890#issuecomment-5784143408), including balance and EIP-3607 sender-code checks. Error-code mapping and compatibility migration require client agreement.

Erigon reports that OpenEthereum skipped nonce checks and could supplement sender balance. Strict validation therefore changes legacy diagnostic behavior. A transaction pool can retain a future-nonce transaction that cannot execute next against the selected state. Block selectors conventionally refer to post-state; use transaction replay to obtain a mined transaction’s actual pre-transaction state.

The raw-validation corpus uses independently verified Prague state, funded controls and observable storage/output markers. It covers both nonce directions, chain identity, value and upfront-gas affordability, intrinsic gas, base fee and sender code, with valid EIP-7702 delegation and execution-OOG controls.

Erigon and Nethermind execute low- and high-nonce CREATE probes at the address derived from the state nonce. Constructor ADDRESS bytes, the returned address and created code in stateDiff agree. This establishes execution semantics; for Nethermind the source also shows the mechanism, a nonce replaced in memory before execution (below). The wire evidence does not identify Erigon’s. Besu’s empty success-shaped results and Nethermind’s malformed responses are distinct from demonstrated execution. See the [H13 validation study](../../docs/h13-validation.md) for results and reproduction.

Parity's [raw RPC path](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/impls/traces.rs#L148-L170) used the same `client.call` as unsigned simulation. Its [virtual-call helper](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/src/client/client.rs#L1206-L1233) explicitly disables nonce checking, while [`transact_virtual`](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/machine/src/executive.rs#L819-L833) supplies missing sender balance. The source comment identifies extra-block executions for consensus contracts and RPCs as the purpose of that virtual path. Thus permissiveness was a deliberate shared simulation mechanism in Parity; it is not evidence that modern clients silently rewrote signed bytes.

**Recommendation risk:** strict selected-state rejection gives a truthful execution-validity result but removes Parity's historical hypothetical-inspection behavior for future-nonce or underfunded signed transactions. The [Erigon review comment](https://github.com/ethereum/execution-apis/issues/890#issuecomment-5784143408) supports strict execution; it does not by itself settle migration for callers relying on virtual simulation. Keep that compatibility question visible even though the validation direction is converged.

### Revised recommendation (2026-09-24 source review)

The previous recommendation proposed a single -32003 for every validation failure. `trace_rawTransaction` takes the same bytes as `eth_sendRawTransaction`, which already references the [#650](https://github.com/ethereum/execution-apis/pull/650) error-group catalog ([submit.yaml](https://github.com/ethereum/execution-apis/blob/465d1b98d43e94ff3d57e904fd7d4bea7f6b804c/src/eth/submit.yaml#L54-L59)). The revision reuses that catalog’s codes for nonce, gas, fee and funding rejections, so callers can tell them apart without matching text, and keeps -32003 as its generic fallback for failures without a group code, such as chain identity or sender code. Pool-only groups (already known, minimum price) do not apply. None of the tested builds emits the group codes on this method: Reth returns -32000 or -32003, Erigon -32000, and Besu and Nethermind return success-shaped or malformed responses, so all four need code changes. See [simulation §3](../../docs/source-review/simulation.md).

### Nethermind raw-transaction validation (2026-09-29)

Nethermind decodes the bytes and runs them through trace_call’s own `TraceTx` ([TraceRpcModule.cs](https://github.com/NethermindEth/nethermind/blob/de17a1a837375b742b91c65527aa517a99ee87bc/src/Nethermind/Nethermind.JsonRpc/Modules/Trace/TraceRpcModule.cs#L209-L216)), so trace_rawTransaction gets trace_call’s relaxed options: `LoadNonceFromState | NoValidation` ([TraceProcessingOptions.cs](https://github.com/NethermindEth/nethermind/blob/de17a1a837375b742b91c65527aa517a99ee87bc/src/Nethermind/Nethermind.Consensus/Tracing/TraceProcessingOptions.cs#L11-L12)) with transactions executed under `SkipValidationAndCommit`. A transaction with the wrong nonce executes with the sender’s state nonce, since `currentTx.Nonce = stateProvider.GetNonce(sender)` replaces the decoded nonce in memory before execution ([TransactionProcessorAdapterExtensions.cs](https://github.com/NethermindEth/nethermind/blob/de17a1a837375b742b91c65527aa517a99ee87bc/src/Nethermind/Nethermind.Consensus/Processing/TransactionProcessorAdapterExtensions.cs#L20-L23)), and the EIP-3607 sender-code check is skipped. That is Parity-faithful: it answers “what would these bytes do”, as Parity’s virtual-call path did. Erigon ([#24329](https://github.com/erigontech/erigon/pull/24329)), Reth and the Geth draft reject such transactions, so for Nethermind this is the open design question, not an incidental bug. Chain identity is different: on master a typed transaction signed for another chain executed, and a legacy one failed only incidentally, for the funds of the sender its signature recovers; [NethermindEth/nethermind#14048](https://github.com/NethermindEth/nethermind/pull/14048) rejects both before tracing. Besu validates but ignores the result and returns an empty success-shaped trace (output `0x`, zero gas used, no VM operations).

### Strict validation retained (2026-09-30)

After reviewing permissive diagnostic use cases, retain strict selected-state signed validation as the intended client contract. This is a deliberate departure from legacy diagnostic simulation. Preserve signed gas, nonce, signature and transaction type; grandfathering does not excuse replacing the signed transaction during execution.

### Nethermind position (2026-09-30)

[Nethermind explicitly supports](https://github.com/ethereum/execution-apis/issues/890#issuecomment-5906720536) strict trace_rawTransaction validation with the same checks as block inclusion, while trace_call stays permissive like eth_call. H13 was already converged; this adds an explicit client position rather than a new policy conclusion or measured implementation uptake. Permissive unsigned-call validation does not settle H15’s fee and funding defaults.

## Decision needed

Agree the execution-validity requirements and a migration path for permissive diagnostic workflows. The raw-validation checks require each invalid transaction to be rejected for its own violation, named in the error; since 2026-09-29 the code is recommended and only noted (H14), so Erigon’s development build and Reth, which reject every probe for the right violation with -32000 or -32003, agree. Nethermind’s development build validates as block inclusion does since #14091 ([2026-10-01 eval](../../evidence/2026-10-01/eval/README.md)): it rejects every invalid probe for its own violation except an EIP-3607 sender, which it rejects with -32000 “sender has deployed code”, a message the checks do not yet recognize as a validation failure; decide whether that message names the violation. Besu validates but ignores the result, returning an empty success-shaped trace for every invalid probe. Keep H12 block-selection semantics separate. Erigon [asks](https://github.com/ethereum/execution-apis/issues/890#issuecomment-5857403064) that, if trace_rawTransaction adopts the eth_sendRawTransaction groups, the mapping be one table a client implements once for both methods, so one daemon does not report the same rejection with two codes; as a recommendation it no longer decides conformance.
