# Signed transaction execution validity

H13 · Compatibility change / validation policy proposal · [All decisions](../../decisions/README.md)

**Status: 🤝 Converged** · [Status definitions](../../decisions/README.md#status-key)

Converged on strict execution validation, including nonce, balance and sender-code checks. Error-code mapping and compatibility migration remain open; client implementations are not harmonized.

Policy evidence: [Erigon’s trace API review](https://github.com/ethereum/execution-apis/issues/890#issuecomment-5784143408).

[Rule in the pinned draft](https://github.com/banteg/execution-apis/blob/f5b9d877ffd62fb88530da83b5a115de6df49c11/docs-api/docs/trace-profile.md#open-details-requiring-focused-review)

## Recommendation

Validate trace_rawTransaction for execution against the selected state and fork: signature, chain identity, nonce equality (both low and high), balance for value and upfront gas, intrinsic gas, fees and sender-code restrictions with the EIP-7702 delegation exception. Do not change signed fields, override the sender nonce or supplement its balance. This is not pool admission: exclude local replacement, already-known and minimum-tip policies. Report a decodable transaction that fails validation with the eth_sendRawTransaction error groups: 1 nonce too low, 2 nonce too high, 800 intrinsic gas, 804 priority fee above fee cap, 806 fee cap below base fee and 809 insufficient funds, with -32003 (Transaction rejected) as the generic fallback; malformed encoding or parameters use -32602. Valid execution that REVERTs or halts still returns a trace.

A signed trace should describe those bytes executing against the selected state. Skipping nonce validation can change CREATE addresses and nonce-dependent behavior; overriding nonce or balance instead invents a different pre-state. Strict validation intentionally tightens historical permissive simulation and can reject queued or already-mined transactions at latest state. Client acceptance alone does not establish a deliberate nonce policy, and malformed error JSON does not prove validation was skipped.

## Background

[Erigon supports strict execution validation](https://github.com/ethereum/execution-apis/issues/890#issuecomment-5784143408), including balance and EIP-3607 sender-code checks. Error-code mapping and compatibility migration require client agreement.

Erigon reports that OpenEthereum skipped nonce checks and could supplement sender balance. Strict validation therefore changes legacy diagnostic behavior. A transaction pool can retain a future-nonce transaction that cannot execute next against the selected state. Block selectors conventionally refer to post-state; use transaction replay to obtain a mined transaction’s actual pre-transaction state.

The raw-validation corpus uses independently verified Prague state, funded controls and observable storage/output markers. It covers both nonce directions, chain identity, value and upfront-gas affordability, intrinsic gas, base fee and sender code, with valid EIP-7702 delegation and execution-OOG controls.

Erigon and Nethermind execute low- and high-nonce CREATE probes at the address derived from the state nonce. Constructor ADDRESS bytes, the returned address and created code in stateDiff agree. This establishes execution semantics without implying mutation of the signed bytes. Besu’s empty success-shaped results and Nethermind’s malformed responses are distinct from demonstrated execution. See the [H13 validation study](../../docs/h13-validation.md) for results and reproduction.

Parity's [raw RPC path](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/impls/traces.rs#L148-L170) used the same `client.call` as unsigned simulation. Its [virtual-call helper](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/src/client/client.rs#L1206-L1233) explicitly disables nonce checking, while [`transact_virtual`](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/machine/src/executive.rs#L819-L833) supplies missing sender balance. The source comment identifies extra-block executions for consensus contracts and RPCs as the purpose of that virtual path. Thus permissiveness was a deliberate shared simulation mechanism in Parity; it is not evidence that modern clients silently rewrote signed bytes.

**Recommendation risk:** strict selected-state rejection gives a truthful execution-validity result but removes Parity's historical hypothetical-inspection behavior for future-nonce or underfunded signed transactions. The [Erigon review comment](https://github.com/ethereum/execution-apis/issues/890#issuecomment-5784143408) supports strict execution; it does not by itself settle migration for callers relying on virtual simulation. Keep that compatibility question visible even though the validation direction is converged.

### Revised recommendation (2026-09-24 source review)

The previous recommendation proposed a single -32003 for every validation failure. `trace_rawTransaction` takes the same bytes as `eth_sendRawTransaction`, which already references the [#650](https://github.com/ethereum/execution-apis/pull/650) error-group catalog ([submit.yaml](https://github.com/ethereum/execution-apis/blob/465d1b98d43e94ff3d57e904fd7d4bea7f6b804c/src/eth/submit.yaml#L54-L59)). The revision reuses that catalog’s codes for nonce, gas, fee and funding rejections, so callers can tell them apart without matching text, and keeps -32003 as its generic fallback for failures without a group code, such as chain identity or sender code. Pool-only groups (already known, minimum price) do not apply. None of the tested builds emits the group codes on this method: Reth returns -32000 or -32003, Erigon -32000, and Besu and Nethermind return success-shaped or malformed responses, so all four need code changes. See [simulation §3](../../docs/source-review/simulation.md).

## Decision needed

Agree the execution-validity requirements, the error-group mapping and a migration path for permissive diagnostic workflows. The raw-validation checks require each rejection to use its error-group code or the -32003 fallback and to name its violation. Keep H12 block-selection semantics separate.
