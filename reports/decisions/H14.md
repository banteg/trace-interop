# Invalid parameters and rejected calls

**Question:** How do malformed parameters and rejected unsigned calls fail, and which error codes are recommended?

H14 · Spec decision · [All decisions](../../decisions/README.md)

**Status: 🤝 Converged** · [Status definitions](../../decisions/README.md#status-key)

Converged on the core parameter and rejection direction: malformed input and conflicting data/input are rejected, equal calldata values are accepted, and validation errors name the actual violation. ## Recommendation

An explicit null for an optional parameter or an optional member of a parameter object is the same as omitting it: the default applies, and null keeps its own meaning only where the schema gives it one (a null to creates a contract). Error codes are recommended; conformance requires the error response itself: never a result, null, [], a clamped or partial result or a malformed response where the draft requires an error, and a rejection for the request’s own violation. The JSON-RPC base protocol keeps its codes: -32700 for a parse error, -32601 for an unserved method (H01), and an internal error (-32603) is a server failure, not the required error. Reject malformed encodings, wrong types, unsupported argument shapes, disagreeing data and input, a priority fee above the fee cap and a non-null override parameter a client does not implement, with -32602 recommended. Unsigned-call validation rejections report their violation, with the eth_simulateV1 codes recommended: -38012 base fee too low, -38013 intrinsic gas, -38014 insufficient funds, -38025 init-code size and -38026 client limit. A call object that is invalid regardless of state (a priority fee above the fee cap, a transaction type or field combination no transaction can carry, an empty authorization list) takes precedence when a request violates several rules, and its rejection reports that defect (-32602 recommended). A legacy gasPrice with an authorizationList is not such a combination: the call is accepted, gasPrice serves as both maxFeePerGas and maxPriorityFeePerGas, and the authorizations apply. Any other rejection of a well-formed call at the selected block, such as a blob fee cap below the blob base fee or a type not active at that fork, recommends -32003 (Transaction rejected), the same fallback trace_rawTransaction recommends (H13). Signed-transaction rejections recommend the eth_sendRawTransaction error groups (H13). List each method’s codes in its errors. Every call-object field the schema defines must take effect or cause a rejection; only fields outside the schema are ignored, and filters reject unknown fields. Keep message wording implementation-specific but name the violation; omit internal stack traces.

Callers should distinguish a malformed request from a valid request that cannot execute, without text matching.

## Background

Parity's [RPC error helpers](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/helpers/errors.rs#L145-L178) distinguished invalid parameters from execution errors. The [raw trace handler](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/impls/traces.rs#L148-L170) mapped invalid RLP through InvalidParams, while its [transaction-error helper](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/helpers/errors.rs#L466-L481) used a separate server code for transaction errors. [EIP-1474's error table](https://eips.ethereum.org/EIPS/eip-1474#error-codes) later named `-32602` Invalid params and `-32003` Transaction rejected; aligning categories is better grounded than matching historical message text or Parity's private numeric transaction code.

Parity's [trace filter](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/types/trace_filter.rs#L27-L46) and [call request](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/types/call_request.rs#L20-L42) rejected unknown fields. The draft deliberately accepts extra call-object fields for interoperability with shared transaction objects, while keeping filters closed. Fields the schema defines must take effect or be rejected, and conflicting fee fields are rejected. Ignoring extras cannot establish extension support and can hide typos; clients must declare supported extensions and callers must not infer support from success. H02 separately retains integer output paths and hex request indices.

### Revised recommendation (2026-09-24 source review)

The previous recommendation named no code for unsigned fee, funding or intrinsic-gas rejections, and the draft said unknown call-object fields MUST be ignored while treating standard fields as supported "when supported by the selected fork". Together these let a client that lacks a defined field run a different transaction and return a success-shaped trace. Erigon’s `TraceCallParam` declares only `data` among the calldata fields ([trace_adhoc.go](https://github.com/erigontech/erigon/blob/3b4861d10387ca3e19f7b16d1b8c0ec1fcd616cd/rpc/jsonrpc/trace_adhoc.go#L66-L79)), so Go’s decoder drops `input`, `nonce`, `chainId`, `type`, `blobVersionedHashes` and `authorizationList`: a request using the canonical `input` field executes with empty calldata. Nethermind maps `data` into `input` so the last one wins, while Besu and Reth reject a mismatch; requiring agreement is stricter than Geth’s eth_call, which silently prefers `input`, and is a deliberate choice. The eth_simulateV1 codes are already emitted by Geth ([errors.go](https://github.com/banteg/go-ethereum/blob/fa8ecb9242dda61858c44cf43c70d00548fbd7cd/internal/ethapi/errors.go#L103-L160)), Erigon, Nethermind and Reth from their eth_simulateV1 paths; Besu’s eth_simulateV1 maps -38010…-38015, -38020, -38021, -38023 and -38026, but not -38025. Geth maps tip above cap to -32602 there, which the revision adopts. No corpus request sends `input` or any post-Berlin call field yet, so the Erigon defect is not captured. See [simulation §3, §12 and §13](../../docs/source-review/simulation.md).

### Settled details (2026-09-24, Geth implementation)

Implementing the codes in the Geth draft showed that three listed `eth_simulateV1` codes cannot occur for unsigned calls: a supplied nonce is neither validated nor used (H15), so -38010 and -38011 do not apply; a single call has no block of transactions to exceed (-38015); and unsigned calls skip the EIP-3607 sender-code check exactly as `eth_call` and `eth_simulateV1` do in Geth, so -38024 does not apply. Failures without a specific code, such as a blob fee cap below the blob base fee, a transaction type not active at the fork or an empty authorization list, use -32602 rather than an internal error. The [pinned draft](https://github.com/banteg/execution-apis/commit/53ffb857) states these codes.

### Explicit null is omission (2026-09-26)

A Nethermind review of the `trace_filter` mode field asked whether `"mode": null` should be rejected, since null usually means the default for an optional field. Two throwaway captures on all nine builds answered it. Across the `eth_*` methods, every client, including Geth's own code, treats an explicit null as omitted: null `value`, `data`, `gas`, `gasPrice` and `nonce` in `eth_call`, null `value` in `eth_estimateGas`, null `fromBlock` and `address` in `eth_getLogs`, and null `blockOverrides`, `stateOverrides` and call `value` in `eth_simulateV1` all succeed, although the execution-apis schemas allow none of them. The exceptions are type quirks: Nethermind and Reth reject null for `eth_simulateV1`'s three boolean options, where Besu, Erigon and Geth accept it. In `trace_filter`, null `count` and `toBlock` were accepted by every client build, `after` by Besu, Erigon and Reth, and the address lists by all but Reth; `mode` null was rejected by the three clients that implement the field, each because it decodes an enum, and `fromBlock` split. The draft had followed the schemas' strictness, so the Geth draft alone rejected `trace_call` with a null `value`. The draft now adopts the convention the clients share: an explicit null for an optional member is omitted, and the `trace_*` schemas mark those members nullable. `probes-prague` (`field-null-members`, `field-null-block`, `callmany-null-block`) and `probes-forks` (`filter-null-members`, and null bounds compared with their omitted twins) test it.

### Divergent-decisions review (2026-09-26)

The [review](../../docs/reviews/2026-09-26-divergent-decisions/H14-H15-H16.md) kept -32602 for malformed input, which every client’s JSON decoder already emits and Parity reported as InvalidParams, and kept the eth_simulateV1 codes: all five codebases, Besu included, already map -38012, -38013 and -38014 in their eth_simulateV1 paths, and only their trace paths bypass that mapping. The fallback it replaced, -32602 for any validation failure without a listed code, matched no client: each client’s eth_simulateV1 falls back to -32603 (Reth to its generic codes) for unmapped validation errors, and reporting a state-dependent rejection such as a blob fee cap below the blob base fee as invalid params contradicted this decision’s own rationale. -32602 now covers only call objects that are invalid regardless of state, and every other rejection is -32003 (Transaction rejected), the fallback H13 already uses and the code Reth and Anvil already emit for unsigned rejections. State-independent checks take precedence, as in Geth’s preCheck order: a positive tip with an omitted fee cap exceeds its zero cap and falls below the base fee, and is -32602, where Geth, Erigon and Anvil already report the tip and Besu and Nethermind the base fee. Only the Geth draft, go-ethereum #35791 and execution-apis #895 move, from -32602 to -32003 for those fallbacks.

### Error codes recommended (2026-09-29)

Chase, for execution-apis, warned against bikeshedding error codes, and the draft had already relaxed one: an unknown selected block returns an error with -32001 recommended (H06, 2026-09-27). The draft ([feat/trace afcbc676](https://github.com/banteg/execution-apis/tree/afcbc676aa2d11cc5a3afcc73555b99a8f69ac33)) now applies that rule everywhere: error codes named in the profile are recommended, and conformance requires the error response itself, never a result, null, [], a clamped or partial result or a malformed response. Behavior stays required: execute or reject, null versus error versus [], which requests are rejected at all, and a rejection for the request’s own violation, including the precedence of a defect invalid regardless of state. A transaction signed for another chain must still be rejected for chain identity, not for the funds of the sender its signature recovers. The JSON-RPC base protocol keeps its distinctions: -32700 for a parse error, -32601 for an unserved method (H01), and an internal error (-32603), which reports a server failure rather than a rejection. -32602 for malformed parameters is standard JSON-RPC, but it is recommended too: clients reach some malformed-input rejections through their own validation paths and codes, and the behavior that matters to callers is the rejection. The harness keeps each observed code in the check detail (`Code -32000 (-32602 recommended).`) and no longer fails on it; the eth_sendRawTransaction error-group check (H13) is removed, and the duplicate -32602 chain-id probe merges into the rejection probe. On the 2026-09-29 matrix 1,166 code-only checks turn from differing to agreeing (Nethermind 408, Reth 228, Erigon 226, Anvil 304), mostly H15 fee and funding rejections that named the right violation with -32000 or -32003. Decision verdicts move less, because most remaining differences are behavior: H13 now agrees on Erigon’s development build and both Reth builds, and H30 on Nethermind 2.0.0, while H14 and H15 still differ on every client. Across the Besu, Erigon, Nethermind and Reth development builds, agreement rises from 77 to 79 of 128 decisions.

### data and input disagreement (2026-09-29)

Erigon ([#24336](https://github.com/erigontech/erigon/pull/24336)), Reth (alloy-evm’s `try_into_unique_input`), Besu (a check in `CallParameter`) and the Geth draft all reject a call object whose `data` and `input` disagree as invalid params. Nethermind alone lets the last member win: `Data` is a setter alias for `Input` in [LegacyTransactionForRpc](https://github.com/NethermindEth/nethermind/blob/de17a1a837375b742b91c65527aa517a99ee87bc/src/Nethermind/Nethermind.Facade/Eth/RpcTransaction/LegacyTransactionForRpc.cs#L43-L51). This is a plain Nethermind change, not a design question, but it touches the call-object class that eth_call shares. Explicit nulls follow the same pattern: the four other clients treat a null `blobVersionedHashes` or `authorizationList` as omitted, while Nethermind selects that member’s transaction type and rejects the call; [NethermindEth/nethermind#14049](https://github.com/NethermindEth/nethermind/pull/14049) fixes it in the shared call object. trace_filter strictness (rejecting unknown members and a negative `after` or `count`) is in flight for Nethermind as [#14050](https://github.com/NethermindEth/nethermind/pull/14050).

### Client positions and core convergence (2026-09-30)

[Nethermind supports](https://github.com/ethereum/execution-apis/issues/890#issuecomment-5906720536) rejecting conflicting data/input across methods with -32602 while accepting equal values, and prefers one shared error map for the same failure across methods. Together with Erigon’s recorded agreement and the majority behavior documented above, this supports marking the core parameter and rejection direction converged. Nethermind’s position is scoped to those statements: it does not endorse every null, field, precedence or numeric-code rule. The draft’s codes remain recommended. Implementation changes and a complete shared-map review remain; convergence is direction aligned, not unanimous formal approval or harmonized captures.

### Legacy gasPrice with an authorization list (2026-10-03)

No signed transaction carries both a legacy `gasPrice` and an `authorizationList`, so the rule against field combinations no transaction can carry could be read to reject such a call. Unsigned simulations price a call rather than sign it, though, and most clients already accept it: Nethermind, Reth and Erigon’s development build run `probes-prague/field-authorization` with the authorization applied, as Anvil does, while Erigon 3.7.1 ignores the authorization, Besu fails with -32603 and the Geth draft rejects it with -32602. The profile accepts the call: `gasPrice` serves as both fee caps and the authorizations apply, consistent with H15’s eth_call pricing. The probe, observed until now as an open input policy, is required.

## Decision needed

`probes-prague` covers input only, equal and disagreeing data/input, access list (warm-SLOAD gas), authorization list (delegated code, with EIP-1559 fees and with a legacy gasPrice), omitted from (CALLER), omitted and null gas (eth_call GAS), and a chainId mismatch.
