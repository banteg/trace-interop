# Unsigned simulation fees and block environment

**Question:** Which fee defaults and block environment do unsigned trace_call and trace_callMany use?

H15 · Spec decision / call-method consistency · [All decisions](../../decisions/README.md)

**Status: 🤝 Converged** · [Status definitions](../../decisions/README.md#status-key)

Converged: ordinary execution fees follow eth_call (omitted fees are 0; a zero effective price runs with GASPRICE and BASEFEE 0 and no fee effects; priced calls are validated and charged), blob calls without a positive maxFeePerBlobGas run with BLOBBASEFEE 0 (Erigon’s rule), and an explicit gas of 0 is a zero limit. Erigon agreed on execution-apis#890 and shipped it; Nethermind merged its alignment (#14045, #14046, #14092), which counts as agreement. Besu merged #11404 (2026-10-02), which runs unsigned trace calls like eth_call. This records direction from implementations and client teams, not unanimous formal approval.

## Recommendation

Align ordinary execution fees of unsigned trace simulations with eth_call. Omitted execution-fee fields default to 0. The zero-fee rule applies to the effective gas price after defaulting (gasPrice, or min(maxPriorityFeePerGas + base fee, maxFeePerGas)): a zero price runs with GASPRICE = 0, opcode-visible BASEFEE = 0 and no gas-fee balance effects. The blob fee is decided independently of the execution fee. A blob call, one carrying blobVersionedHashes or maxFeePerBlobGas, whose maxFeePerBlobGas is omitted, null or 0 runs with opcode-visible BLOBBASEFEE = 0 and pays no blob fee; an explicit zero cap is therefore accepted, not rejected, matching Geth’s eth_call CallDefaults and the eth_simulateV1 schema default of 0. A positive maxFeePerBlobGas is validated against the selected block’s blob base fee and charged. Non-blob calls keep the selected block’s BLOBBASEFEE. Defined blob fields must take effect or cause rejection, never be ignored. Preserve the selected block’s other fields. Skip execution-fee validation only when both execution fee caps are 0. Otherwise require the price to cover the base fee and the priority-fee cap not to exceed the total cap, and enforce funding, rejecting a violation for itself (-38012, -32602 and -38014 recommended), and simulate upfront gas payment, refunds, base-fee burn and beneficiary tips so execution and later calls observe them. A supplied nonce is accepted but neither validated nor used; CREATE addresses derive from the state nonce. gas is a uint64. Omitted gas follows the client’s eth_call defaulting at the selected state, bounded by the server’s execution cap; a sender allowance or block limit may lower that default but must never raise the cap. Only omitted or null gas takes that default: an explicit gas of 0 is a supplied limit of 0, which fails the intrinsic-gas check, so the call is rejected (-38013 recommended) with no trace, and in trace_callMany the whole request errors as for any invalid item. Supplied gas above the cap is reduced to the cap. Consumers needing a portable gas budget should supply gas explicitly. Preferred positional StateOverrides and BlockOverrides are optional extensions at trace_call parameters 4 and 5 and trace_callMany parameters 3 and 4, using the eth_simulateV1 fields with storage optional for balance/code/nonce-only overrides and state/stateDiff mutually exclusive. Existing recognized configuration wrappers remain optional extensions where their contents take effect. The baseline call arity does not require either form. Reject an unsupported non-null override shape (-32602 recommended), never silently treat a state map as an empty configuration. Accepted overrides apply before execution, once before the first batch item; with a block override the zero-fee rule uses the overridden base fee. Trace selections must not change execution. Apply the same rules independently to each trace_callMany item while carrying prior simulated state forward. Keep strict signed validation separate.

Requesting a trace should not change the execution or fee semantics of an equivalent call. The zero-fee BASEFEE convention and zero defaults preserve established eth_call compatibility; they do not exempt positive prices from validation or payment. Enforcing funding removes Parity’s virtual balance top-up.

## Background

Parity's [call-request adapter](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/helpers/fake_sign.rs#L24-L37) defaulted an unsigned call's `gasPrice` to zero and fake-signed it for the same [virtual execution path](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/src/client/client.rs#L1206-L1233) used by `trace_call` and `trace_callMany`. That path disabled nonce checks and used the requested block's header; it treated simulations as extra-block execution rather than pool admission. This explains the zero-fee precedent, but Parity predates `BASEFEE`. That is not precedent for preserving every environmental field: Parity's [call executors](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/src/client/client.rs#L1490-L1538) also replaced the gas limit with U256::max_value(). The BASEFEE convention and preservation of the other selected block fields are explicit modern contract choices.

### Revised recommendation: zero-fee eth_call compatibility

The earlier H15 proposal preserved BASEFEE even for a zero-fee unsigned call. Reth’s compatibility objection changes this recommendation: adding tracing should not change the execution of the same call. Current upstream Geth `920c0777` explicitly zeroes BASEFEE in both [eth_call preparation](https://github.com/ethereum/go-ethereum/blob/920c07774c65ebb3023536f85df642c44478b540/internal/ethapi/api.go#L794-L806) and [debug_traceCall preparation](https://github.com/ethereum/go-ethereum/blob/920c07774c65ebb3023536f85df642c44478b540/eth/tracers/api.go#L948-L963) when the effective gas price is zero. This is an observable compatibility convention, not a claim that an unsigned simulator cannot technically preserve the header fee. Changing it should be coordinated across call methods. Reth’s zero-fee override is therefore no longer classified as an H15 environment defect; its positive-price validation and accounting are separate questions. Our Geth draft fork implemented the earlier proposal at the time and is not an independent upstream vote; since c8449896 it returns BASEFEE 0 for a zero-fee trace_call.

This is a revision to the proposed policy, not a statement of client-team agreement. The re-pinned draft at execution-apis e0e588fc states this rule, including the zero defaults below; its schema validates response structure, while the H15 semantic oracle checks behavior. The experimental Geth implementation then still followed the earlier proposal (historical; see the 2026-09-26 review below). Neither is evidence of upstream consensus.

Reth's [unsigned-call environment](https://github.com/paradigmxyz/reth/blob/58a51b3ee3f6714ded9207b244a273c8afb592fd/crates/rpc/rpc-eth-api/src/helpers/call.rs#L882-L912) disables base-fee validation and fee charging, then sets the EVM block base fee to zero when the call's gas price is zero. Both [trace_call](https://github.com/paradigmxyz/reth/blob/58a51b3ee3f6714ded9207b244a273c8afb592fd/crates/rpc/rpc/src/trace.rs#L98-L109) and [trace_callMany](https://github.com/paradigmxyz/reth/blob/58a51b3ee3f6714ded9207b244a273c8afb592fd/crates/rpc/rpc/src/trace.rs#L149-L169) use this call setup. In the pinned [zero-fee](../cases/coverage/model-environment-free.md) probe, the tested release and development builds return GASPRICE 0 and BASEFEE 0 although the selected block's base fee is 765625000 wei. In the [priced](../cases/coverage/model-environment.md) probe, they return the supplied GASPRICE of 2 gwei and the original BASEFEE, but stateDiff shows no gas-fee debit. These are implementation observations, not client-team agreement; the dedicated fee-policy corpus also reads BASEFEE independently in single-call and mixed-fee callMany executions. Under the revised policy, the zero-fee BASEFEE result is expected. The disabled fee charging on valid priced requests remains a difference.

Reth’s legacy/EIP-1559 distinction originates in its locked [alloy-evm 0.39.0 dependency](https://github.com/paradigmxyz/reth/blob/58a51b3ee3f6714ded9207b244a273c8afb592fd/Cargo.lock#L310-L313). The [fee normalizer](https://github.com/alloy-rs/alloy-evm/blob/ba6f83b80aba8cf005175f4d776d8b90796c72d9/crates/evm/src/rpc/fees.rs#L53-L109) accepts legacy gasPrice directly, but rejects a supplied nonzero EIP-1559 fee cap below the block base fee. Reth disables the later EVM base-fee check and gas-fee charging for unsigned calls.

Erigon instead [validates the fee cap](https://github.com/erigontech/erigon/blob/e26d9bd4056586e004488c31b561fb2663d46019/execution/protocol/txn_executor.go#L323-L329), while gasBailout [skips the sender debit](https://github.com/erigontech/erigon/blob/e26d9bd4056586e004488c31b561fb2663d46019/execution/protocol/txn_executor.go#L233-L247) without disabling the [beneficiary tip](https://github.com/erigontech/erigon/blob/e26d9bd4056586e004488c31b561fb2663d46019/execution/protocol/txn_executor.go#L750-L765). Fee validation and simulated payment therefore need separate assertions.

Omission and explicit zero are not interchangeable across clients. With all execution-fee fields omitted, [Nethermind](https://github.com/NethermindEth/nethermind/blob/2a3b2531b4dcfaa58b21e4197c27cbab959a7f3e/src/Nethermind/Nethermind.Facade/Eth/RpcTransaction/LegacyTransactionForRpc.cs#L110-L114), [Reth](https://github.com/alloy-rs/alloy-evm/blob/ba6f83b80aba8cf005175f4d776d8b90796c72d9/crates/evm/src/rpc/fees.rs#L92-L101) and the [Geth draft fork](https://github.com/banteg/go-ethereum/blob/fa8ecb9242dda61858c44cf43c70d00548fbd7cd/internal/ethapi/transaction_args.go#L441-L455) default to zero; [Besu](https://github.com/besu-eth/besu/blob/f9572aa82a2dadb3dd1b218d3ca97101540faf97/ethereum/core/src/main/java/org/hyperledger/besu/ethereum/transaction/TransactionSimulator.java#L608-L617) and [Erigon](https://github.com/erigontech/erigon/blob/e26d9bd4056586e004488c31b561fb2663d46019/rpc/jsonrpc/trace_adhoc.go#L188-L211) default to the block base fee. An explicit maxFeePerGas 0 / maxPriorityFeePerGas 0 pair is accepted as zero-price execution by Nethermind, Reth and the Geth fork; Reth still changes BASEFEE to zero. Besu rejects the pair. Erigon replaces the pair with the block base fee and executes with GASPRICE = B. A zero priority fee alone is not a zero total fee.

The NoBaseFee name does not mean all fees are disabled. Upstream Geth skips fee validation only when [both execution-fee caps are zero](https://github.com/ethereum/go-ethereum/blob/920c07774c65ebb3023536f85df642c44478b540/core/state_transition.go#L573-L589). Priced calls still enter [buyGas](https://github.com/ethereum/go-ethereum/blob/920c07774c65ebb3023536f85df642c44478b540/core/state_transition.go#L435-L489), check cap-based funding, and debit the effective-price gas payment before EVM execution. [Settlement](https://github.com/ethereum/go-ethereum/blob/920c07774c65ebb3023536f85df642c44478b540/core/state_transition.go#L761-L784) skips beneficiary payment for the all-zero exception and pays tips otherwise. Consequently, positive under-base-fee prices should still fail; a valid nonzero price requests ordinary simulated accounting. The zero-fee exception does not exempt value transfers from funding or disable gas metering.

For trace_callMany, start every item from the selected block environment and apply the zero-fee adjustment only to that item. A free → priced → free sequence sees BASEFEE 0 → B → 0, while balances and other simulated state carry forward. The existing fee-policy corpus checks this independently with both fee styles, mixed trace selections, upfront sender balance, prior beneficiary settlement, refunds, REVERT and out-of-gas. It must never carry a preceding call’s zeroed fee environment into a later priced call.

### Paired checks and independent policy checks

The fee-compat corpus sends byte-for-byte identical call objects and block selectors through eth_call and every trace_call selection, including no trace components. Returned bytecode exposes seven words: GASPRICE, BASEFEE, NUMBER, TIMESTAMP, GASLIMIT, CALLER BALANCE after upfront payment/value, and COINBASE BALANCE before the tip. Each trace is assessed against an independently calculated policy output and separately compared with its own client’s eth_call result. Two identically wrong outputs therefore do not earn a policy pass. Rejections are compared by identifiable fee/funding reason, not error-message wording. Missing, malformed or generic/internal errors block the compatibility check. Omitted/incomplete fee defaults were observations under the previous recommendation; the revision below decides them.

Nethermind's malformed responses come from deferred trace execution: the writer starts a successful JSON-RPC envelope before fee/funding validation throws, so the request ID and closing brace are never written. The development capture has 232 such responses and 232 logged validation exceptions (128 base-fee, 104 funding). The [streaming investigation](../../docs/nethermind-streamed-errors.md) links the exact tested source, explains the release/development count difference, and identifies [PR #13666](https://github.com/NethermindEth/nethermind/pull/13666). Internal rejection is established by logs. #13666 is merged, and the development build in the [2026-09-27 eval](../../evidence/2026-09-27/eval/README.md), 2.1.0-preview · 5ece5fba, returns no malformed response: each rejection is one complete error, mostly -32000; 2.0.0 still truncates them.

### Revised recommendation (2026-09-24 source review)

The previous recommendation applied the zero-fee rule to explicit zero fees and left omitted and incomplete fee defaults, blob fees and overrides open. All nine tested eth_call builds agree that an omitted fee runs free (GASPRICE 0, BASEFEE 0, no debit), and eth_simulateV1’s `GenericCallTransaction` documents every fee default as 0 ([execute.yaml](https://github.com/ethereum/execution-apis/blob/465d1b98d43e94ff3d57e904fd7d4bea7f6b804c/src/schemas/execute.yaml#L240-L315)), so the principle H15 already applies decides them. The zero-fee condition moves from "explicit zero" to the effective price after defaulting, which is Geth’s rule ([transaction_args.go](https://github.com/banteg/go-ethereum/blob/fa8ecb9242dda61858c44cf43c70d00548fbd7cd/internal/ethapi/transaction_args.go#L401-L495), [api.go](https://github.com/banteg/go-ethereum/blob/fa8ecb9242dda61858c44cf43c70d00548fbd7cd/internal/ethapi/api.go#L798-L806)). The fee-validation skip stays a separate predicate (both caps zero); the two differ only for a zero cap with a positive tip, which is rejected anyway. The BLOBBASEFEE half of Geth’s rule is now explicit.

Compatibility cost: Besu and Erigon trace_call price an omitted fee at the base fee (Besu also charges it) while their eth_call runs free; Nethermind and the Geth draft keep BASEFEE at B for an omitted fee; Reth prices a tip-only request at B in both methods. Besu’s trace paths validate a supplied nonce ([AbstractTraceByBlock.java](https://github.com/besu-eth/besu/blob/07f0a4b2f832257842db71eacf4bca584f87fafe/ethereum/api/src/main/java/org/hyperledger/besu/ethereum/api/jsonrpc/internal/methods/AbstractTraceByBlock.java#L120-L123)), unlike its eth_call and every other client, and must ignore it instead. Erigon does not parse `nonce` at all. Enforcing funding removes Parity’s `transact_virtual` balance top-up for unsigned calls ([executive.rs](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/machine/src/executive.rs#L821-L833)), a cost H13 already records for raw transactions. Overrides are already accepted in incompatible positions: Reth takes state and block overrides as parameters 4 and 5, Nethermind state overrides as parameter 4, Erigon a Geth-style config object as parameter 4, which silently ignores a Reth-style map; Besu takes none. Reserving the Reth positions with the eth_simulateV1 schemas moves Erigon. See [simulation §1, §7, §8, §14 and §15](../../docs/source-review/simulation.md).

### Settled details (2026-09-24, Geth implementation)

The Geth draft first rejected supplied gas above the RPC gas cap with -38026, reading "never truncate" literally. That made `trace_call` fail where the same `eth_call` succeeds, contrary to this decision’s premise that tracing must not change the call. Unsigned calls therefore run over-cap gas at the server cap, as `eth_call` does; the cap is server policy, not a truncated result. A signed raw transaction is different: capping its gas would change the signed transaction, so H13 rejects it with -38026. The [pinned draft](https://github.com/banteg/execution-apis/commit/53ffb857) states both rules.

### Divergent-decisions review (2026-09-26)

The [review](../../docs/reviews/2026-09-26-divergent-decisions/H14-H15-H16.md) kept every rule. Besu, Erigon and Nethermind already apply them in their own eth_call: omitted fees run free, a zero price sees BASEFEE 0, a positive price below the base fee and underfunded priced calls are rejected, and priced calls are charged. Erigon’s and Nethermind’s debug_traceCall follow the zero-fee rule too. In these three clients the trace path is the outlier inside the client, through separate code paths that were never aligned. Reth is consistent with itself but not with the others: its shared call environment sets `disable_fee_charge`, which in revm skips the balance check, the upfront debit, the refund and the beneficiary reward. The flag was added for OP operator fees ([#18634](https://github.com/paradigmxyz/reth/pull/18634), after issue [#18470](https://github.com/paradigmxyz/reth/issues/18470)), reverted the same day ([#18645](https://github.com/paradigmxyz/reth/pull/18645)) and re-added in [#19073](https://github.com/paradigmxyz/reth/pull/19073) (2025-10-16), so it is deliberate, but its L1 consequence, no gas charge and no funding check, is not what it was added for. Whether that is intended is an open question to Reth. The Geth draft c8449896 already returns BASEFEE 0 for a zero-fee trace_call, so the earlier-proposal notes and the 12:56 snapshot above are historical.

### Which parent governs (2026-09-29)

The environment rule (BASEFEE 0 for a zero-fee call, applied per call, and priced calls below the base fee rejected) follows eth_call: it is Nethermind’s, Geth’s and Erigon’s eth_call behavior. It does not follow eth_simulateV1, which with validation off, its default, runs every call, priced ones included, at BASEFEE 0 for the whole simulated block ([ethsimulatev1-notes](https://github.com/ethereum/execution-apis/blob/5bcdc34a477b10af278c079525374e6a4046f291/docs-api/docs/ethsimulatev1-notes.mdx#L174-L180)). The draft’s “Fees follow eth_call and eth_simulateV1” should therefore say that they follow eth_call; the rejection codes were only borrowed from eth_simulateV1, and are now recommended rather than required (H14).

Blob fees are less settled. BLOBBASEFEE 0 for a zero or defaulted `maxFeePerBlobGas` follows Geth’s eth_call and the eth_simulateV1 schema default, but four of the six trace implementations disagree on both cases. An explicit zero is rejected by Nethermind, Reth, Besu and Anvil. A defaulted cap runs at the head’s blob base fee on Reth, Besu, Anvil and Erigon 3.7.0, and Nethermind’s trace path fails with an internal error (-32603) on it. Only the Geth draft and Erigon’s development build follow the rule. The [2026-09-26 review](../../docs/reviews/2026-09-26-divergent-decisions/H14-H15-H16.md#3-verdicts) marked it “keep, unverified”; revisit it before asking clients to change blob behavior.

### Gas-default clarification (2026-09-30)

Omitted gas uses the client’s eth_call default subject to the RPC cap, rather than requiring execution at that cap. The September 29 review demonstrated an allowance of 100,000 gas below a 50,000,000 cap, and separately reproduced Reth raising the cap when the selected block allowed more gas. Paired priced GAS probes now check eth_call compatibility and independently bound both methods by the zero-price explicit-cap control; agreement between two methods alone cannot establish that the cap is respected. Single-item trace_callMany probes exercise the same policy. H13 retains rejection rather than clamping for signed transactions.

### Grandfathering revision (2026-09-30)

The [client review](../../docs/reviews/2026-09-30-open-policy-grandfathering/README.md) keeps ordinary execution-fee semantics, separates unresolved blob normalization from the universal-zero requirement, and makes positional overrides preferred optional extensions while preserving recognized working wrappers. Current Besu eth_call source normalizes the blob price to 1, Erigon and Geth to 0, and live Reth preserves the selected price. The old zero/default blob probes remain retained evidence but no longer define conformance; their outcomes remain unassessed pending policy review. Defined blob fields and accepted override contents must still take effect or cause rejection. This revises the recommendation, not client agreement or measured build state.

### Erigon position and blob rule (2026-10-01)

Erigon [agreed with H15 and has shipped it](https://github.com/ethereum/execution-apis/issues/890#issuecomment-5920232075): omitted fees default to 0, a zero effective price runs with GASPRICE and BASEFEE 0 and no fee balance effects, validation is skipped only when both caps are 0, and a priced call pays upfront gas, refunds, burn and tip. It named one gap it will fix: its trace_callMany recognizes the configuration wrapper, but the wrapper’s state overrides never take effect, the silent case the recommendation rules out. For the blob clause that the [grandfathering revision](../../docs/reviews/2026-09-30-open-policy-grandfathering/README.md) left unresolved, Erigon proposed deciding each fee independently rather than with one universal zero: BASEFEE is zeroed when the execution price is 0, and BLOBBASEFEE when the call is a blob call, carrying blobVersionedHashes or maxFeePerBlobGas, and its maxFeePerBlobGas is not positive. The recommendation now adopts that rule in place of the unresolved clause. An omitted, null or zero cap on a blob call runs with BLOBBASEFEE 0 and pays no blob fee, a positive cap is validated against the selected blob base fee and charged, and non-blob calls keep the selected BLOBBASEFEE. An explicit zero cap is accepted rather than rejected, as with Geth’s eth_call CallDefaults and the eth_simulateV1 schema default of 0.

The retained `blob-fee-defaulted` and `blob-fee-zero` probes are scored again, and the rule moves most trace implementations. Nethermind rejects an explicit zero cap (-32000) and its open #14092 defaults an omitted cap to the block’s blob base fee, as its eth_call does. Reth and Anvil reject an explicit zero (-32003) and run an omitted cap at the head’s blob base fee; Besu runs an omitted cap the same way and returns an internal error (-32603) for an explicit zero. Erigon 3.7.0 runs both at the head’s blob base fee. Only the Geth draft and Erigon’s development build (#24330, #24343) already follow the rule. The positive-cap and non-blob probes already agree on every build. Erigon also asked whether an explicit `gas: 0` means omitted gas: its eth_call treats it so, while its trace_call runs the call with a zero budget and fails out of gas. It asks only that the two methods agree; the question remains open. This records one client’s position; H15 stays under review.

### Explicit zero gas (2026-10-01)

Erigon asked whether an explicit `gas: 0` means omitted gas: its eth_call treats it so, while its trace_call runs a zero budget. The [reply](https://github.com/ethereum/execution-apis/issues/890#issuecomment-5921187168) proposed a real zero limit, and the recommendation now says so. Only omitted or null gas (null is omission, H14) takes the eth_call default under the RPC cap. An explicit `"gas": "0x0"` is a supplied limit that fails the intrinsic-gas check, so the call is rejected (-38013 recommended) with no trace, and a trace_callMany request with such an item errors as a whole. That is already what eth_call does in Geth, Nethermind, Besu, Reth and Anvil, and what trace_call, debug_traceCall and eth_simulateV1 do in every client, Erigon’s included; the execution-apis conformance test `eth_simulateV1/ethSimulate-instrict-gas-38013` requires it for `"gas":"0x0"`. Only Erigon’s eth_call family (eth_call, eth_callMany, debug_traceCallMany and GraphQL) falls back to the default when `*args.Gas == 0`, so dropping that fallback is the one change. Reading Erigon main, a gas-0 trace_call fails the intrinsic check in `preCheck` and returns -38013 rather than the out-of-gas frame Erigon described; the reply asked which request produced that frame. `probes-prague` tests the rule with `field-gas-zero`, `field-gas-zero-many`, their eth_call control `field-gas-zero-eth-call` and `field-gas-null`, which must equal its omitted twin.

The [focused capture](../../evidence/2026-10-01/gas-zero/README.md) with the 2026-09-30 eval builds confirms it. No build returns a result or an out-of-gas frame for a gas-0 trace_call or trace_callMany. Erigon 3.8.0-dev returns -38013 (“intrinsic gas too low: have 0, want 53122”) for both, as reading main predicted, and so does the Geth draft; Nethermind 2.2.0-preview, Reth, Anvil and Erigon 3.7.0 reject with -32000. Besu fails with an internal error (-32603), which is not the required rejection, and its trace_callMany wraps it as a result (H25); Nethermind 2.0.0 returns its known truncated streamed response. The eth_call control matches: every build rejects the zero limit (Besu -32003, the others -32000) except both Erigon builds, whose eth_call runs the call with the default budget. A null gas returns its omitted twin’s GAS word on every build.
