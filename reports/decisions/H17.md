## Recommendation

Make account existence explicit. An account appears only if its balance, nonce, code, storage or existence changed; existence means presence in the state trie, so an existing EIP-161-empty account removed by touch-clearing is a deletion. + and - appear only when the account is born or dies: a born account marks balance, nonce (including zero) and code (including empty) with +, and lists its nonzero post-state slots as +. For an account that exists at both endpoints, unchanged fields use =, changed fields use *, and changed slots always use * with 32-byte from/to words, including zero words; slots never use =. If an address already existed with empty code, do not mark it as newly created. Compare existence at the execution endpoints; transient creation and destruction with an account absent at both endpoints does not produce an account diff.

Absent accounts and existing accounts with empty code are different states; consumers should be able to reconstruct the change without guessing. Reserving + and - for account birth and death keeps a slot marker from implying an existence change.

## Background

Parity's [account diff algorithm](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/pod/src/account.rs#L103-L134) compares optional account existence before comparing fields: absent-to-present marks balance, nonce, code and present storage as Born; present-to-absent marks them Died; present-to-present uses Same or Changed. Its [RPC serializer](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/types/trace.rs#L160-L207) encodes those variants as `+`, `-`, `=` and `*`. The [original create/delete test](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/pod/src/state.rs#L88-L114) explicitly expects a newly created account's zero nonce and empty code to be `+`.

This history explains why `+` is an existence marker, not shorthand for a nonzero or nonempty value. A pre-existing empty-code account is therefore a changed or unchanged account, not a birth. The linked modern stateDiff cases should be checked against pre-state existence as well as byte values; output shape alone cannot establish whether a client classified the account correctly.

The [2026-09-24 assessment audit](../../docs/h17-assessment-audit.md) separates marker encoding from execution and environment errors. Besu's lone failure was a missing state diff on an invalid raw transaction; it now blocks marker assessment. Erigon's only failure and one Reth failure compared deployed code against the expected block environment despite correct creation markers; H08/H15 retain those environment differences. Independently valid transfers still show Nethermind omitting the empty-code birth marker and Reth treating a newly funded account as changes from zero. Source inspection explains both. Nethermind's [PR #13668](https://github.com/NethermindEth/nethermind/pull/13668) merged at 12:08 UTC after the earlier snapshot. The fresh 12:21 UTC matrix resolves development build `9d6e8b8d`, which contains that fix and restores the missing code-birth markers; release `bec830cd` still differs. Existing prefunded-account controls pass on all nine builds.

### Independent account-existence oracle

`coverage/model-transfer` sends 7 wei from a funded sender at nonce 10 to `0x0000000000000000000000000000000000004444`. The recipient is absent from genesis and the selected chain has only two empty blocks. Its positive final balance therefore proves absent-to-present independently of any client response. `model-many-transfers` checks that the next call treats that same recipient as existing. `model-empty-runtime` derives the CREATE address from the sender and nonce and requires empty code to be added. The `a/prefunded-empty` control is a transfer to an already existing account, so unchanged nonce/code must remain `=`.

### Code paths and assessment boundaries

Nethermind `StateProvider.ReportChanges` suppresses the code callback when both byte lengths are zero, collapsing absent code and existing empty code. Its release Parity converter then writes `=` for an unreported code change. PR #13668 reconstructs the empty-code marker from balance existence. Reth’s locked `revm-inspectors` replaces `None` from the prestate database with a default account, then selects added fields only for `is_created()` with zero original balance. That excludes ordinary transfers and loses the prior-existence distinction. Besu and Erigon compare explicit pre/post existence; the Geth draft passes those flags to every field encoder. The [source audit](../../docs/h17-assessment-audit.md#why-the-code-produces-these-results) links each pinned implementation.

A missing `stateDiff` blocks H17 assessment; it cannot prove a wrong marker. Creation checks require the `+` marker and code bytes consistent with returned runtime. H08/H15 independently check the expected execution output and block environment. This removes Besu’s invalid-raw-transaction false attribution and Erigon/Reth environment double-counting while still rejecting mutated markers and inconsistent runtime bytes. “Partially assessed” for Besu/Erigon records unavailable evidence, not a confirmed account-marker defect. H26 owns deletion; these endpoint tests do not prove complete storage enumeration or all reverted/internal creation paths.

### Reth fix and regression results

[revm-inspectors PR #526](https://github.com/paradigmxyz/revm-inspectors/pull/526), commit `af80e453`, preserves the original database existence flag before defaulting field values. It adds all fields for a previously absent nonempty account, including transfer and fee recipients, while keeping existing accounts in the changed/unchanged path. Empty non-created accounts remain omitted and the existing selfdestruct branch is preserved. On Fedora, the unchanged implementation fails two real-EVM regression tests; the fix passes all 34 Parity integration tests. The tests cover first and second transfers, fresh fee recipients, zero-value calls, and empty/nonempty-runtime CREATE into absent, existing empty and prefunded accounts. Existing EIP-7702 and pre/post-Cancun deletion tests also pass. [Retained before/after logs and dependency lock](../../evidence/2026-09-24/h17-client-fix/README.md) identify the exact code and commands. This validates the inspector patch; published Reth RPC results remain separate and retain their observed status until build uptake.

### Revised recommendation (2026-09-24 source review)

The previous recommendation defined account markers but not account inclusion or slot markers. The Geth draft reports zero-to-value and value-to-zero slots on a surviving account as `+` and `-` ([trace_capture.go](https://github.com/banteg/go-ethereum/blob/fa8ecb9242dda61858c44cf43c70d00548fbd7cd/eth/tracers/trace_capture.go#L245-L251)), while Parity, Besu, Erigon, Nethermind and Reth all report `*` from or to the zero word; the harness accepted both until [fb511d3c](https://github.com/banteg/trace-interop/commit/fb511d3c) and now rejects the Geth form. Parity never used `=` for a slot ([account_diff.rs](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/types/src/account_diff.rs#L64)), and the schema no longer allows it. A born account lists only nonzero slots in Besu, Erigon, Reth and Geth; Parity could leak a zero `+` for a slot written and then cleared. An existing EIP-161-empty account removed by touch-clearing splits clients three ways (Besu and Erigon report `-`, Nethermind a schema-invalid `*` to null, Reth and the Geth draft omit it), but such accounts cannot be created after Spurious Dragon and no fixture has one. On the captured cases only the Geth draft moves. See [statediff §2 and §5](../../docs/source-review/statediff.md).
