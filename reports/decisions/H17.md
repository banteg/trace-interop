# New-account stateDiff encoding

H17 · Spec decision / likely serializer fix · [All decisions](../../decisions/README.md)

**Status: ⚪ Under review** · [Status definitions](../../decisions/README.md#status-key)

No policy conclusion has been recorded. Implementation observations below do not establish client-team agreement.

## Recommendation

Make account existence explicit: + for fields of a newly created account (including empty code and nonce zero), - for deletion, * for a changed existing value, = for unchanged existing fields. If an address already existed with empty code, do not mark it as newly created. Compare existence at the execution endpoints; transient creation and destruction with an account absent at both endpoints does not produce an account diff.

Absent and existing-but-empty are different states; consumers should be able to reconstruct the change without guessing.

## Background

Parity's [account diff algorithm](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/pod/src/account.rs#L103-L134) compares optional account existence before comparing fields: absent-to-present marks balance, nonce, code and present storage as Born; present-to-absent marks them Died; present-to-present uses Same or Changed. Its [RPC serializer](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/types/trace.rs#L160-L207) encodes those variants as `+`, `-`, `=` and `*`. The [original create/delete test](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/pod/src/state.rs#L88-L114) explicitly expects a newly created account's zero nonce and empty code to be `+`.

This history explains why `+` is an existence marker, not shorthand for a nonzero or nonempty value. A pre-existing empty-code account is therefore a changed or unchanged account, not a birth. The linked modern stateDiff cases should be checked against pre-state existence as well as byte values; output shape alone cannot establish whether a client classified the account correctly.

The [2026-09-24 assessment audit](../../docs/h17-assessment-audit.md) separates marker encoding from execution and environment errors. Besu's lone failure was a missing state diff on an invalid raw transaction; it now blocks marker assessment. Erigon's only failure and one Reth failure compared deployed code against the expected block environment despite correct creation markers; H08/H15 retain those environment differences. Independently valid transfers still show Nethermind omitting the empty-code birth marker and Reth treating a newly funded account as changes from zero. Source inspection explains both. Nethermind's [PR #13668](https://github.com/NethermindEth/nethermind/pull/13668) merged at 12:08 UTC after the matrix snapshot and repairs empty-code birth markers as well as deletion; it needs build uptake and retesting. Existing prefunded-account controls pass on all nine builds.
