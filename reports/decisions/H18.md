# EIP-7702 code changes in stateDiff

H18 · Likely client bug · [All decisions](../../decisions/README.md)

**Status: ⚪ Under review** · [Status definitions](../../decisions/README.md#status-key)

No policy conclusion has been recorded. Implementation observations below do not establish client-team agreement.

## Recommendation

Report net pre/post delegation-code changes, including set, replace and clear, independently of account-creation flags. Preserve authorization effects when later execution reverts. Multiple accepted authorizations that restore the original code produce no net code change, although nonce changes may remain.

stateDiff must include code that changed, even if the account already existed.

## Background

Parity's [state-diff algorithm](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/pod/src/account.rs#L103-L136) compares account code in the pre- and post-state independently of trace actions. That predates EIP-7702 but supplies the right historical meaning of `stateDiff.code`: changed existing code uses `*`, new-account code uses `+`, and deletion uses `-`. The pinned [Reth state-diff path](https://github.com/paradigmxyz/reth/blob/03cb186c1d36eebbacc7bda08f36e25711d0804e/crates/rpc/rpc/src/trace.rs) and linked authorization cases show an implementation can miss code written during transaction preprocessing even when later EVM execution is traced.

[EIP-7702](https://eips.ethereum.org/EIPS/eip-7702#behavior) writes a delegation indicator or clears code while processing authorizations before the execution portion. It explicitly preserves processed authorizations even if the later execution reverts. The EIP's rationale explains why delegation was made persistent. A complete transaction state diff therefore has to include the authorization-side code change despite a failed call frame.

EIP-7702 permits multiple valid tuples from one authority, with the last valid code write winning. stateDiff reports their net effect, not each intermediate write. Authorization processing also skips certain invalid tuples without rejecting an otherwise valid outer transaction; H13’s execution-validity rule must follow those fork-defined distinctions. Event-level authorization history would require a separate output contract.
