## Recommendation

Define ex.used as post-operation gas remaining, and mem/store/push as effects of that same operation. Use null for no memory write, with actual offset and bytes for a write. Specify call/return gas boundaries using dedicated nested-call fixtures before choosing detailed gas formulas.

Same-step effects let consumers follow execution without shifting writes between opcodes. Memory-write deltas alone do not encode allocated memory size; reconstructing expansion also needs opcode context.

## Background

Parity's [interpreter](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/evm/src/interpreter/mod.rs#L348-L405) calls the VM tracer before an opcode with its cost and reported memory region, then after the opcode with the current remaining gas, pushed stack words and memory. The [VM tracer](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/trace/src/executive_tracer.rs#L241-L274) stores that after-step gas in the value serialized as `ex.used` and extracts that post-step memory slice. Its internal field is named `gas_used`, but the passed value is remaining gas; the recommendation follows the execution path rather than the misleading name.

[EIP-5656](https://eips.ethereum.org/EIPS/eip-5656#semantics) introduced MCOPY after Parity's codebase and defines it as an actual destination-memory write, including overlapping copies. The pinned [Besu VM generator](https://github.com/besu-eth/besu/blob/d997aad7b3be6333464c0687d3761c568ee63524/ethereum/api/src/main/java/org/hyperledger/besu/ethereum/api/jsonrpc/internal/results/tracing/vm/VmTraceGenerator.java) and [Erigon VM tracer](https://github.com/erigontech/erigon/blob/c25b8e47dc1a77ecdbd15d38ba3beae1d29530ec/rpc/jsonrpc/trace_adhoc.go#L545) should classify MCOPY's destination and capture its post-operation bytes. The original hook design does not determine the exact gas boundary for trapped nested calls, which remains a separate fixture question.

Parity's [memory-region calculation](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/evm/src/interpreter/mod.rs#L472-L493) included MLOAD and the entire requested CALL output window. Those were post-step snapshots, not exclusively writes. The draft deliberately narrows mem to bytes actually written: memory expansion is distinct from a byte write, and a short return must not claim the untouched tail of the requested output window. This refinement needs explicit fixtures rather than an appeal to Parity compatibility.

## Decision needed

Retain the fixed regressions. Add MLOAD with and without expansion, short CALL output over a nonzero tail, empty return data, zero-length/OOG copies, and nested warm-access/stipend/refund probes. Separate actual writes from memory expansion and snapshots.
