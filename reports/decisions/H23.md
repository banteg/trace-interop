# Special-action address matching

**Question:** Which addresses of a CREATE, SELFDESTRUCT or reward record do trace_filter address lists match?

H23 · Spec decision / client discrepancy · [All decisions](../../decisions/README.md)

**Status: 🤝 Converged** · [Status definitions](../../decisions/README.md#status-key)

Converged on matching a record only by the addresses it reports: a failed CREATE has no created-address match because its result carries no address (H09). Erigon agrees and its development build implements it (#24355); the reverted-CREATE fix PRs for Reth and Nethermind implement it too. This records direction from implementations and client teams, not unanimous formal approval.

## Recommendation

Define from/to equivalents per action: creator and created address for CREATE; the executing (self-destructing) account and beneficiary for SELFDESTRUCT, which after EIP-6780 usually survives; and recipient only (author) for rewards. A record matches only on addresses it reports: a failed CREATE reports no created address (H09), so it can match its creator but never a populated recipient list, even though a client may know the would-be address. A reward has no from side: in intersection mode it is excluded whenever fromAddress is populated, even if other records in the same block match fromAddress, while in union mode a toAddress match suffices. Apply H03 composition, so union can retain a creator match. Matching a reverted action does not imply a committed transfer.

Address-based history should not silently omit a transfer or creation because its action uses different field names. Matching only reported addresses keeps every match explainable from the returned record; a failed CREATE reports no address because no contract exists there (H09), so the two decisions stand together.

## Background

Parity's [original address matcher](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/trace/src/types/filter.rs#L82-L110) assigns sender/recipient equivalents per action: CREATE uses the creator and successful result address, SELFDESTRUCT uses the destroyed account and refund address, and PoW reward uses its author as the recipient. This mapping is part of the indexed filter implementation, not a reinterpretation of a generic `to` field. The pinned Besu CREATE and SELFDESTRUCT cases test that the same records visible in `trace_block` can be found by their relevant addresses.

[Parity issue #9822](https://github.com/openethereum/parity-ethereum/issues/9822) reported that `trace_filter` dropped a failed contract creation visible by transaction/block tracing; [the fix](https://github.com/openethereum/parity-ethereum/commit/1ac1224cd3f983d66d650e78428d274350c84a30) addressed that historical edge. a failed CREATE has no successful `result.address`. Parity's matcher still allows a creator-only query to find it but cannot satisfy a nonempty recipient filter. The proposed mapping preserves that distinction instead of assigning a successful destination to a failed creation.

Reward and failed-CREATE matching diverged in source before `probes-forks` and `mined-probes` covered them. Besu filters rewards through the generic `action.getFrom()` and `action.getTo()` ([TraceFlatTransactionStep.java](https://github.com/besu-eth/besu/blob/07f0a4b2f832257842db71eacf4bca584f87fafe/ethereum/api/src/main/java/org/hyperledger/besu/ethereum/api/jsonrpc/internal/methods/TraceFlatTransactionStep.java#L61-L80)) and Nethermind through `action.From` and `action.To` ([TxTraceFilter.cs](https://github.com/NethermindEth/nethermind/blob/ac02224f25fd4901116ebf2643d522ec4a0e60a1/src/Nethermind/Nethermind.JsonRpc/Modules/Trace/TxTraceFilter.cs#L41-L57)); a reward action carries only `author`, so `toAddress: [miner]` never returned rewards in either client (Nethermind #13800, in 2.1.0-preview · fca93966, now matches all eight rewards by author on `probes-forks/rewards-to`). Erigon emits a reward whenever the coinbase is in `toAddress` ([trace_filtering.go](https://github.com/erigontech/erigon/blob/3b4861d10387ca3e19f7b16d1b8c0ec1fcd616cd/rpc/jsonrpc/trace_filtering.go#L597-L617)), ignoring `mode` and `fromAddress`, so an intersection with a populated sender list still returns it. Nethermind sets a failed CREATE’s `action.To` to the would-be address ([ParityLikeTxTracer.cs](https://github.com/NethermindEth/nethermind/blob/ac02224f25fd4901116ebf2643d522ec4a0e60a1/src/Nethermind/Nethermind.Blockchain/Tracing/ParityStyle/ParityLikeTxTracer.cs#L413-L421)) and matches on it; Reth’s Alloy matcher uses a failed CREATE’s `result.address`, which Reth and Erigon still report (H09). Reth and the Geth draft otherwise match the draft.

### Revised recommendation (2026-09-24 source review)

The previous wording called the SELFDESTRUCT side the "destroyed account", which is inaccurate after EIP-6780, when the account usually survives, and did not spell out reward matching under each mode. The matching itself is unchanged and follows Parity ([filter.rs](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/trace/src/types/filter.rs#L96-L121)). Writing the reward rule down exposes Besu and Nethermind (rewards unreachable through `toAddress`) and Erigon (rewards ignore `mode`). See [filter-selection §2, §5 and §11](../../docs/source-review/filter-selection.md).

### Divergent-decisions review (2026-09-26)

The [review](../../docs/reviews/2026-09-26-divergent-decisions/H04-H23-H30-H32.md) kept every rule. Erigon, Nethermind 2.1.0-preview and Reth already agree with the draft and Parity on creation, SELFDESTRUCT and reward matching; only Besu, which matches generic `from` and `to` fields, differs. The failed-CREATE rule is the one place three natives share an alternative: Erigon, Nethermind and Reth (with Anvil) return a reverted CREATE for `toAddress: [would-be address]`. Each does so incidentally: Alloy’s matcher states Parity’s intent but sees the would-be address in the H09 result shape, Erigon matches `result.address` whenever a result exists, and Nethermind matches an internal `action.To` its record never shows. The recommendation now states the principle behind the rule, that a record matches only addresses it reports, and ties it to H09’s address-free reverted-CREATE result. The counter-argument is recorded: a reverted CALL matches its `to`, and a CREATE2 retry search would want every attempt at one address; that search is served by the creator side while failed CREATEs carry no address. Erigon and Reth drop the match once they adopt H09’s result shape, and Nethermind needs a matcher guard.

Supporting controls (not standalone assertions): [a/transaction-tree](../cases/a/transaction-tree.md).

## Decision needed

`probes-forks` checks reward matching by author, intersection and union with a sender list on the PoW blocks. The mined-probes filters query mined top-level and nested reverted CREATEs by their would-be addresses and creators, and SELFDESTRUCT to self by both sides; the filter oracles ignore a failed CREATE’s result address. Add a reward-leak case for Erigon: a sender listed in fromAddress also sends a transaction to the coinbase in the same block, so an intersection query would return the reward.
