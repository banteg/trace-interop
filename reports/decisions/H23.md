# Special-action address matching

H23 · Spec decision / client discrepancy · [All decisions](../../decisions/README.md)

**Status: ⚪ Under review** · [Status definitions](../../decisions/README.md#status-key)

No policy conclusion has been recorded. Implementation observations below do not establish client-team agreement.

## Recommendation

Define from/to equivalents per action: creator and successfully created address for CREATE; the executing (self-destructing) account and beneficiary for SELFDESTRUCT, which after EIP-6780 usually survives; and recipient only for rewards. A failed CREATE has no created-address match: it can match its creator, but not a populated recipient list. A reward matches toAddress by author and has no from side: in intersection mode it is excluded whenever fromAddress is populated, while in union mode a toAddress match suffices. Apply H03 composition, so union can retain a creator match. Matching a reverted action does not imply a committed transfer.

Address-based history should not silently omit a transfer or creation because its action uses different field names.

## Background

Parity's [original address matcher](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/trace/src/types/filter.rs#L82-L110) assigns sender/recipient equivalents per action: CREATE uses the creator and successful result address, SELFDESTRUCT uses the destroyed account and refund address, and PoW reward uses its author as the recipient. This mapping is part of the indexed filter implementation, not a reinterpretation of a generic `to` field. The pinned Besu CREATE and SELFDESTRUCT cases test that the same records visible in `trace_block` can be found by their relevant addresses.

[Parity issue #9822](https://github.com/openethereum/parity-ethereum/issues/9822) reported that `trace_filter` dropped a failed contract creation visible by transaction/block tracing; [the fix](https://github.com/openethereum/parity-ethereum/commit/1ac1224cd3f983d66d650e78428d274350c84a30) addressed that historical edge. a failed CREATE has no successful `result.address`. Parity's matcher still allows a creator-only query to find it but cannot satisfy a nonempty recipient filter. The proposed mapping preserves that distinction instead of assigning a successful destination to a failed creation.

Reward and failed-CREATE matching diverge in source, and no fixture covers them yet. Besu filters rewards through the generic `action.getFrom()` and `action.getTo()` ([TraceFlatTransactionStep.java](https://github.com/besu-eth/besu/blob/07f0a4b2f832257842db71eacf4bca584f87fafe/ethereum/api/src/main/java/org/hyperledger/besu/ethereum/api/jsonrpc/internal/methods/TraceFlatTransactionStep.java#L61-L80)) and Nethermind through `action.From` and `action.To` ([TxTraceFilter.cs](https://github.com/NethermindEth/nethermind/blob/ac02224f25fd4901116ebf2643d522ec4a0e60a1/src/Nethermind/Nethermind.JsonRpc/Modules/Trace/TxTraceFilter.cs#L41-L57)); a reward action carries only `author`, so `toAddress: [miner]` never returns rewards in either client. Erigon emits a reward whenever the coinbase is in `toAddress` ([trace_filtering.go](https://github.com/erigontech/erigon/blob/3b4861d10387ca3e19f7b16d1b8c0ec1fcd616cd/rpc/jsonrpc/trace_filtering.go#L597-L617)), ignoring `mode` and `fromAddress`, so an intersection with a populated sender list still returns it. Nethermind sets a failed CREATE’s `action.To` to the would-be address ([ParityLikeTxTracer.cs](https://github.com/NethermindEth/nethermind/blob/ac02224f25fd4901116ebf2643d522ec4a0e60a1/src/Nethermind/Nethermind.Blockchain/Tracing/ParityStyle/ParityLikeTxTracer.cs#L413-L421)) and matches on it; Reth’s Alloy matcher uses a failed CREATE’s `result.address`, which Reth and Erigon still report (H09). Reth and the Geth draft otherwise match the draft.

### Revised recommendation (2026-09-24 source review)

The previous wording called the SELFDESTRUCT side the "destroyed account", which is inaccurate after EIP-6780, when the account usually survives, and did not spell out reward matching under each mode. The matching itself is unchanged and follows Parity ([filter.rs](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/trace/src/types/filter.rs#L96-L121)). Writing the reward rule down exposes Besu and Nethermind (rewards unreachable through `toAddress`) and Erigon (rewards ignore `mode`). See [filter-selection §2, §5 and §11](../../docs/source-review/filter-selection.md).

Supporting controls (not standalone assertions): [a/transaction-tree](../cases/a/transaction-tree.md).

## Decision needed

Add reward fixtures on the PoW `forks` chain (toAddress set to the coinbase, and an intersection with a sender list) and a mined reverted CREATE queried by its would-be address and by its creator. The filter oracles already ignore a failed CREATE’s result address.
