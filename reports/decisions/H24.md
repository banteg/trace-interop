# Sibling failure isolation

H24 · Reproduced reporting defect · [All decisions](../README.md#decisions-to-review)

**Status: ⚪ Under review** · [Status definitions](../../decisions/README.md#status-key)

No policy conclusion has been recorded. Implementation observations below do not establish client-team agreement.

## Recommendation

Attach error and result data to the actual call frame. A sibling failure must not change another frame's status. A child’s local success remains success even if a later ancestor revert rolls back its state changes; frame outcome and committed stateDiff answer different questions.

A successful caller can handle a failed subcall and continue; frame results must preserve that distinction.

## Background

Parity's [original flat tracer](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/trace/src/executive_tracer.rs#L41-L151) pushes a frame index on entry, then writes either its result or its failure to that exact frame when the EVM exits it. Its child count and traceAddress advance independently of the outcome. This is the historical reason to attach an error to a call frame rather than infer it from another frame's opcode stream: an EVM caller can inspect a failed CALL's success bit and then return successfully.

In the pinned [Besu flat trace generator](https://github.com/besu-eth/besu/blob/d997aad7b3be6333464c0687d3761c568ee63524/ethereum/api/src/main/java/org/hyperledger/besu/ethereum/api/jsonrpc/internal/results/tracing/flat/FlatTraceGenerator.java#L549-L565), `hasRevertInSubCall` scans the transaction-wide trace frames for a matching depth, without first delimiting the current call's subtree. It is used when assigning the root and nested frame errors. That explains why the sibling fixtures can report a handled revert on the wrong frame; the observed trace result remains the regression oracle for this diagnosis.
