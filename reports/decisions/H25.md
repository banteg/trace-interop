# Well-formed errors for rejected raw transactions

**Question:** How does a trace method report a validation or execution failure found while producing its response?

H25 · Reproduced response serialization defect · [All decisions](../../decisions/README.md)

**Status: 🤝 Converged** · [Status definitions](../../decisions/README.md#status-key)

Erigon and Reth report a failure found before output as one complete JSON-RPC error. Nethermind can leave truncated JSON on the wire for a rejected signed transaction; #13666, merged, fixes it in the development build. Besu’s development build agrees since #11401 (merged 2026-10-02) and returns a rejected trace_callMany bundle as one error; Besu 26.9.0 still nests a complete error envelope inside the result. Nethermind 2.1.0 was cut without #13666 and still truncates. This records direction from implementations, not unanimous formal approval.

## Recommendation

Before committing result bytes, report validation or execution setup failures as one complete JSON-RPC error. Buffer when necessary to guarantee a replaceable response. After output has been committed, a later failure must explicitly abort the transport rather than append a second envelope or finish a partial result as success. Request parsing alone is not full validation; later callMany admission can depend on earlier calls.

Clients must be able to parse failures and associate them with a request, regardless of the chosen signed-transaction admission policy.

## Background

Parity's [original `trace_rawTransaction` implementation](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/impls/traces.rs#L148-L168) parses RLP, validates the signed transaction and resolves the state/header before returning a `Result<TraceResults>`; each failure maps to an RPC error instead of a partial trace object. The later [Ethereum RPC error specification](https://eips.ethereum.org/EIPS/eip-1474) likewise describes an `error` member on the response object, so this decision concerns response integrity independently of which signed transactions a client accepts.

The pinned [Nethermind trace module](https://github.com/NethermindEth/nethermind/blob/a404c4f06a67aee52cc448216b8d37a77062f106/src/Nethermind/Nethermind.JsonRpc/Modules/Trace/TraceRpcModule.cs#L141-L177) validates RLP before tracing but, when streaming is enabled, `BuildStreamingSingleResult` returns a lazy streaming result whose execution runs while the JSON writer is active. This makes a late admission or execution failure a different problem from malformed RLP. prevalidating the request alone cannot ensure a complete JSON-RPC error if a deferred trace fails after result bytes have been sent; buffering or an error-safe streaming boundary is needed for that guarantee. An explicit transport abort is an incomplete request, not a successful trace or a complete JSON-RPC error; it cannot count as passing the semantic assessment.
