# Account deletion across Cancun

H26 · Reproduced stateDiff discrepancy · [All decisions](../README.md#decisions-to-review)

**Status: ⚪ Under review** · [Status definitions](../../decisions/README.md#status-key)

No policy conclusion has been recorded. Implementation observations below do not establish client-team agreement.

## Recommendation

Compare account existence before and after the execution. For present-to-absent accounts, use deletion markers for balance, nonce and code; account deletion implies clearing all storage. The policy for enumerating untouched prior storage slots still needs agreement. After EIP-6780 a pre-existing contract normally survives SELFDESTRUCT, so do not report code deletion. An account absent at both endpoints has no net account diff, even if created and destroyed during execution.

Deletion and a zero balance with retained code are observably different states. Apply the rules of the selected block.

## Background

Parity's [original account diff](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/pod/src/account.rs#L103-L140) distinguishes a present account becoming absent (`Died` for balance, nonce, code and each prior storage slot supplied to that helper) from an account that remains present with changed values. Its [transaction finalizer](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/machine/src/executive.rs#L1132-L1181) actually removed SELFDESTRUCT accounts at the end of execution under those pre-Cancun rules. The deletion markers therefore describe account existence, not merely a zeroed balance.

[EIP-6780](https://eips.ethereum.org/EIPS/eip-6780) deliberately changed that premise: SELFDESTRUCT normally transfers the balance without deleting a pre-existing account's code or storage, preserving deletion only for a contract created in the same transaction. This explains why the selected block's fork rules determine the stateDiff, and why the Nethermind/Reth pre-Cancun missing code and nonce markers are meaningful. `stateDiff` compares the before and after account snapshots. A contract created and destroyed within the same transaction can leave no account at either endpoint, so even genuine transient deletion need not produce a `Died` entry; an execution trace is needed to see that event. A prefunded address, however, existed before creation; deletion at that address can require a net deletion entry.

The helper is not evidence that historical traces enumerated every old slot: [Account::to_pod](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/account-state/src/account.rs#L142-L157) exposes storage_changes, while [state diff construction](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/account-state/src/state.rs#L868-L926) builds partial account snapshots. Exhaustive storage enumeration has a different cost from reporting account deletion and must be specified explicitly.
