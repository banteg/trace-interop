# Filter execution across fork boundaries

**Question:** When trace_filter spans a fork boundary, does each block run under its own fork rules and state?

H27 · Reproduced cross-method discrepancy · [All decisions](../../decisions/README.md)

**Status: ⚪ Under review** · [Status definitions](../../decisions/README.md#status-key)

No policy conclusion has been recorded. Implementation observations below do not establish client-team agreement.

[Client positions](../../decisions/README.md#client-positions): none recorded.

## Recommendation

Return records produced with each block’s own fork rules and state, whether retrieved from an index or replayed: each block is traced from its parent’s post-block state with its own pre-transaction system operations applied, under its own fork rules. Filtering and pagination over the ordered range must agree with the corresponding per-block records. Do not reuse one block’s execution rules, or its post-transaction state, across a block boundary.

The same block must not trace differently depending on the other blocks included in a query.

## Background

Parity's [original trace database filter](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/trace/src/db.rs#L349-L365) searched indexed trace blooms over the requested range, loaded each stored block's traces, and filtered those records. The trace namespace thus established per-block result consistency without requiring a range request to execute blocks again. This matters across forks because each stored trace was produced with the rules in force when its block was imported.

The pinned [Besu range pipeline](https://github.com/besu-eth/besu/blob/d997aad7b3be6333464c0687d3761c568ee63524/ethereum/api/src/main/java/org/hyperledger/besu/ethereum/api/jsonrpc/internal/methods/TraceFilter.java#L142-L202) obtains one `protocolSpec` and transaction processor from its first block header, then feeds a list of blocks to the pipeline. That is a plausible cause of the reproduced difference between a cross-fork filter and the same individual block traces; the fixture comparison, rather than code inspection alone, establishes the defect. The requirement is output equivalence and fork-correct provenance, not a mandate to re-execute indexed traces.

Besu’s range execution skips more than fork rules. `TraceFilterSource` streams every block’s transactions into one `ChainUpdater` ([TraceFilterSource.java](https://github.com/besu-eth/besu/blob/07f0a4b2f832257842db71eacf4bca584f87fafe/ethereum/api/src/main/java/org/hyperledger/besu/ethereum/api/jsonrpc/internal/methods/TraceFilterSource.java#L40-L55), [TraceBlock.java](https://github.com/besu-eth/besu/blob/07f0a4b2f832257842db71eacf4bca584f87fafe/ethereum/api/src/main/java/org/hyperledger/besu/ethereum/api/jsonrpc/internal/methods/TraceBlock.java#L192-L216)), and `ExecuteTransactionStep` processes transactions only ([ExecuteTransactionStep.java](https://github.com/besu-eth/besu/blob/07f0a4b2f832257842db71eacf4bca584f87fafe/ethereum/api/src/main/java/org/hyperledger/besu/ethereum/api/jsonrpc/internal/methods/ExecuteTransactionStep.java#L84-L111)). Between blocks no block reward, withdrawal, beacon-root, history or request processing is applied, so block N+1 executes on block N’s post-transaction state rather than its post-block state. Besu’s `trace_block` and `trace_filter` also never run the pre-execution system calls, although its `debug_traceBlock` does, so a transaction that reads the EIP-4788 or EIP-2935 contracts is traced against stale system storage even in a single-block query (H28).

### Revised recommendation (2026-09-24 source review)

The previous client-facing change said only "use each block’s own execution rules", which invites a fix that swaps the protocol spec per block and leaves the state skew in place. The recommendation now names the starting state and the pre-transaction system operations. It still moves only Besu. See [filter-selection §7](../../docs/source-review/filter-selection.md).
