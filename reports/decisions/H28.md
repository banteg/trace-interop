# Historical state at system-operation boundaries

H28 · Reproduced historical-state discrepancy; cause unresolved · [All decisions](../README.md#decisions-to-review)

**Status: ⚪ Under review** · [Status definitions](../../decisions/README.md#status-key)

No policy conclusion has been recorded. Implementation observations below do not establish client-team agreement.

## Recommendation

Historical state at block N should include that block's changes, including system operations, but none from N+1. Replay should start from the appropriate parent state and apply each system transition once.

A future system write must not appear in an earlier block's state. This is an execution-context issue, not a cosmetic trace encoding choice.

## Background

Parity's [original replay path](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/src/client/client.rs#L1639-L1667) obtained `state_at_beginning(block)` from the parent block's post-state, then applied the selected block's transactions in order with its own environment. That is the lineage for distinguishing replay's pre-block starting state from the post-state used by a historical simulated call. Parity predates the current beacon-root and block-hash system writes, so its transaction-only loop is not a complete modern replay recipe.

[EIP-4788](https://eips.ethereum.org/EIPS/eip-4788) and [EIP-2935](https://eips.ethereum.org/EIPS/eip-2935) explicitly perform their system updates at the start of the selected block, before transactions. Consequently, block N's post-state includes those writes and block N+1's does not belong in a query at N. The pinned [Erigon `trace_call` state selection](https://github.com/erigontech/erigon/blob/c25b8e47dc1a77ecdbd15d38ba3beae1d29530ec/rpc/jsonrpc/trace_adhoc.go#L1056-L1105) is the relevant modern entrypoint; the beacon-root fixtures demonstrate the one-block-ahead result, while the exact offset inside its state reader still needs investigation.
