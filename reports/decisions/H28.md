# Historical state at system-operation boundaries

**Question:** Which state does a historical trace at block N run against, relative to the system operations of blocks N and N+1?

H28 · Historical-state discrepancy fixed on Erigon main · [All decisions](../../decisions/README.md)

**Status: 🤝 Converged** · [Status definitions](../../decisions/README.md#status-key)

Historical trace_call agrees on every captured native build, including Erigon 3.7.0, which ships the end-of-block history boundary from #24056 (merged 2026-09-18). Two differences remain outside trace_call, both captured and both with an open fix. Besu block replay skips the block’s pre-block system calls, so the mined beacon-root and history reads see the parent’s values (Besu #10953). Erigon’s historical trace_callMany read the next block’s system writes at block 55; #24293 fixed it on main and the development build now agrees. The stricter Harmonized milestone is also blocked by schema-invalid beacon-call-55 responses from Besu and Nethermind: the beacon-roots contract REVERTs and both omit the REVERT frame result that H09 requires. This records agreement on the checked block boundary, not complete system-operation coverage or unanimous formal approval.

## Recommendation

Historical state at block N should include that block’s changes, including system operations, but none from N+1. Replay starts from the parent’s post-block state, applies the block’s pre-transaction system operations once, then its preceding transactions. trace_call and the first trace_callMany item at block N run against the same state and environment.

A future system write must not appear in an earlier block's state. This is an execution-context issue, not a cosmetic trace encoding choice.

## Background

Parity's [original replay path](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/src/client/client.rs#L1639-L1667) obtained `state_at_beginning(block)` from the parent block's post-state, then applied the selected block's transactions in order with its own environment. That is the lineage for distinguishing replay's pre-block starting state from the post-state used by a historical simulated call. Parity predates the current beacon-root and block-hash system writes, so its transaction-only loop is not a complete modern replay recipe.

[EIP-4788](https://eips.ethereum.org/EIPS/eip-4788) and [EIP-2935](https://eips.ethereum.org/EIPS/eip-2935) perform their system updates at the start of the selected block, before transactions. Consequently, block N's post-state includes those writes and block N+1's does not belong in a query at N. Erigon [PR #24056](https://github.com/erigontech/erigon/pull/24056), merged on 2026-09-18 as [66571d04390](https://github.com/erigontech/erigon/commit/66571d043907723f190fbe1f882008c27008fa29), identified a history reader opened one transaction index too late: Min(N+1)+1 included the next block's system call. It changes the historical trace_call, debug_traceCall and default-index debug_traceCallMany readers from txnIndex 0 to -1 and adds TestTraceCallExcludesNextBlockSystemCall. The maintainer explicitly retained 0 for trace_callMany because that method selects the parent block. The captured v3.6.1 release predates the fix; development c25b8e47 contains it and passes the H28 checks.

The H28 probes use `trace_call` and `eth_getStorageAt` only, so they do not exercise replay. Besu opens the parent world state ([Tracer.java](https://github.com/besu-eth/besu/blob/07f0a4b2f832257842db71eacf4bca584f87fafe/ethereum/api/src/main/java/org/hyperledger/besu/ethereum/api/jsonrpc/internal/processor/Tracer.java#L42-L53)) and then processes the block’s transactions without its pre-execution system calls ([ExecuteTransactionStep.java](https://github.com/besu-eth/besu/blob/07f0a4b2f832257842db71eacf4bca584f87fafe/ethereum/api/src/main/java/org/hyperledger/besu/ethereum/api/jsonrpc/internal/methods/ExecuteTransactionStep.java#L84-L111)); only its plugin `TraceServiceImpl` runs them. A mined transaction that reads the EIP-4788 contract at its own timestamp, or the EIP-2935 slot for its parent, therefore sees stale storage in Besu replay. The open [Besu #10953](https://github.com/besu-eth/besu/pull/10953) replays block pre-execution before tracing transactions.

The maintainer’s reason for keeping txIndex 0 in `trace_callMany` does not hold. That method executes with block N’s header and base fee but reads state after N+1’s pre-block system transaction ([trace_adhoc.go](https://github.com/erigontech/erigon/blob/3b4861d10387ca3e19f7b16d1b8c0ec1fcd616cd/rpc/jsonrpc/trace_adhoc.go#L1347), [helper.go](https://github.com/erigontech/erigon/blob/3b4861d10387ca3e19f7b16d1b8c0ec1fcd616cd/rpc/rpchelper/helper.go#L175-L190)), so its first item sees N+1’s beacon-root and history writes while `trace_call` at N does not. Parity’s `call_many` used the same state and header as `call`, and Erigon’s own `debug_traceCallMany` default moved to −1. Not yet verified at runtime.

### Revised recommendation (2026-09-24 source review)

The previous recommendation did not say that `trace_call` and the first `trace_callMany` item share one state, nor that replay applies the block’s own pre-transaction system operations. Both are now explicit (H16, H27). They move Besu replay and Erigon’s historical `trace_callMany`, neither of which the current probes capture. See [statediff §3 and §4](../../docs/source-review/statediff.md).
