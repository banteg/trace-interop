# Omitted trace_filter range bounds

H30 · Spec decision / compatibility · [All decisions](../README.md#decisions-to-review)

**Status: ⚪ Under review** · [Status definitions](../../decisions/README.md#status-key)

No policy conclusion has been recorded. Implementation observations below do not establish client-team agreement.

## Recommendation

Default omitted fromBlock to genesis (earliest), not the node’s retention boundary, and omitted toBlock to latest. Resolve tags once per request, respect explicit endpoints, then filter and paginate the ordered range. Return 4444 when required history is unavailable; report resource limits explicitly rather than silently narrowing the range or returning incomplete success.

An omitted lower bound should search history, including when only toBlock is supplied. A fixed genesis boundary gives the same query meaning on archive and pruned nodes. The captured chain has its first matches in block 1 and head 48; count: 3 exposes the historical-search default but does not test pruning.

## Background

The pinned draft already describes an earliest-to-latest default. Both pinned Besu and Nethermind builds start at head 48; Erigon and Reth start at block 1. An explicit head-only query succeeds on all four. See the [live capture](../../evidence/2026-09-23/h30-code-review/README.md).

Parity's [original filter conversion](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/types/trace_filter.rs#L44-L68) explicitly used `Latest` for *both* omitted bounds; its pending fallback and address defaults are separate choices. Pinned [Nethermind](https://github.com/NethermindEth/nethermind/blob/a404c4f06a67aee52cc448216b8d37a77062f106/src/Nethermind/Nethermind.JsonRpc/Modules/Trace/TraceRpcModule.cs#L278-L296) preserves that latest/latest default, while Erigon and Reth follow the draft's earliest start. The live case with only `toBlock: 2` exposes the compatibility difference more clearly than an empty object: a latest implicit start cannot reach the requested early endpoint.

Parity could serve the query from an [indexed trace database](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/trace/src/db.rs#L349-L365), whereas modern clients may replay range blocks. A [Reth operator report](https://github.com/paradigmxyz/reth/issues/24473) documents heavy replay load from much smaller explicit ranges. Earliest-to-latest is a deliberate compatibility change from the originating implementation and an unbounded default can be expensive without range limits or an index. The proposal chooses useful historical-search semantics over preserving the old default. Servers may impose explicit limits, but must not silently redefine earliest according to retention or return a truncated success. count is not a bound on scan or replay work.

The historical direction is especially clear in Parity's log filter: its [April 2016 change](https://github.com/openethereum/parity-ethereum/commit/fd2d55934b5285d213661014e064d7aa64ca497b) explicitly replaced an `earliest` default with `latest`, before the [May 2016 trace namespace introduction](https://github.com/openethereum/parity-ethereum/commit/7c2adc41375d021e40c9c1e6456aeb6a8e7623a9) gave `trace_filter` latest/latest defaults from the start. Today [Ethereum.org documents](https://ethereum.org/developers/docs/apis/json-rpc/#eth-getlogs) `eth_getLogs` fromBlock and toBlock as latest by default, and pinned [Geth](https://github.com/ethereum/go-ethereum/blob/572bd3696587d4f9599d577c3211c23985f7e4d1/eth/filters/api.go#L466-L482) and [Reth](https://github.com/paradigmxyz/reth/blob/4cd8f5f747ebb7fa6200bd880a2197b37cebdc1e/crates/rpc/rpc-eth-types/src/logs_utils.rs#L156-L177) implement that choice. The current [execution-apis filter schema](https://github.com/ethereum/execution-apis/blob/5bcdc34a477b10af278c079525374e6a4046f291/src/schemas/filter.yaml#L13-L24) permits both fields to be omitted but does not itself declare their defaults, so the trace profile should make its choice explicit.

**Recommendation risk:** the genesis default conflicts with both the originating trace contract and the documented `eth_getLogs` convention. On pinned [Reth](https://github.com/paradigmxyz/reth/blob/4cd8f5f747ebb7fa6200bd880a2197b37cebdc1e/crates/rpc/rpc/src/trace.rs#L352-L393), an omitted fromBlock starts at block 0, a pruned node rejects that history, and even an archive node rejects a range above its [default 100-block limit](https://github.com/paradigmxyz/reth/blob/4cd8f5f747ebb7fa6200bd880a2197b37cebdc1e/crates/rpc/rpc-server-types/src/constants.rs#L17-L20). The fixed genesis boundary and explicit 4444 error avoid silently shifting results with pruning, but they leave an ordinary unbounded request failing on many nodes. `count` does not bypass Reth's upfront range check. Historical callers can state an explicit fromBlock and receive a clear pruned-history or resource-limit error.
