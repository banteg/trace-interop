# Omitted trace_filter range bounds

H30 · Spec decision / compatibility · [All decisions](../README.md#decisions-to-review)

**Status: ⚪ Under review** · [Status definitions](../../decisions/README.md#status-key)

No policy conclusion has been recorded. Implementation observations below do not establish client-team agreement.

## Recommendation

Default omitted fromBlock and toBlock to latest, resolving both against the same canonical head at request start. An explicit toBlock older than an omitted fromBlock is a reversed range and must return a range error. Respect explicit endpoints, then filter and paginate the ordered range. Return 4444 when explicitly requested history is unavailable; report resource limits explicitly rather than silently narrowing the range or returning incomplete success.

This preserves Parity/OpenEthereum’s original trace_filter default and matches the documented eth_getLogs convention. A plain filter targets only the current head, so a small count does not leave a chain-wide range implicit or request history that may be pruned or exceed a range cap. Historical callers must name fromBlock; explicit bounds retain their meaning. On the frozen fixture, head is 48, so the omitted-bounds query matches an explicit 48-to-48 query, while toBlock 2 alone is reversed.

## Background

The pinned draft initially described an earliest-to-latest default. In the [live capture](../../evidence/2026-09-23/h30-code-review/README.md), both pinned Besu and Nethermind builds start at head 48; Erigon and Reth start at block 1, as does the experimental Geth draft fork. An explicit head-only query succeeds on all builds. These observations establish the split, not client-team agreement on a standard.

Parity’s [original filter conversion](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/types/trace_filter.rs#L44-L68) explicitly used `Latest` for both omitted bounds; its pending fallback and address defaults are separate choices. Pinned [Nethermind](https://github.com/NethermindEth/nethermind/blob/a404c4f06a67aee52cc448216b8d37a77062f106/src/Nethermind/Nethermind.JsonRpc/Modules/Trace/TraceRpcModule.cs#L278-L296) preserves that default. The live case with only `toBlock: 2` exposes the difference more clearly than an empty object: a latest implicit start at head 48 cannot reach block 2. Besu reports `-32602`, Nethermind `-32000`; the proposal requires a range error but leaves its code for review.

Parity could serve historical queries from an [indexed trace database](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/ethcore/trace/src/db.rs#L349-L365), whereas modern clients may replay range blocks. A [Reth operator report](https://github.com/paradigmxyz/reth/issues/24473) documents heavy replay load from much smaller explicit ranges. The earlier earliest-to-latest recommendation made an omitted lower bound convenient for historical search, but could turn an ordinary query into an unbounded replay. `count` limits returned records, not scan or replay work.

The historical direction is especially clear in Parity’s log filter: its [April 2016 change](https://github.com/openethereum/parity-ethereum/commit/fd2d55934b5285d213661014e064d7aa64ca497b) explicitly replaced an `earliest` default with `latest`, before the [May 2016 trace namespace introduction](https://github.com/openethereum/parity-ethereum/commit/7c2adc41375d021e40c9c1e6456aeb6a8e7623a9) gave `trace_filter` latest/latest defaults from the start. Today [Ethereum.org documents](https://ethereum.org/developers/docs/apis/json-rpc/#eth-getlogs) `eth_getLogs` fromBlock and toBlock as latest by default, and pinned [Geth](https://github.com/ethereum/go-ethereum/blob/572bd3696587d4f9599d577c3211c23985f7e4d1/eth/filters/api.go#L466-L482) and [Reth](https://github.com/paradigmxyz/reth/blob/4cd8f5f747ebb7fa6200bd880a2197b37cebdc1e/crates/rpc/rpc-eth-types/src/logs_utils.rs#L156-L177) implement that choice. The current [execution-apis filter schema](https://github.com/ethereum/execution-apis/blob/5bcdc34a477b10af278c079525374e6a4046f291/src/schemas/filter.yaml#L13-L24) permits both fields to be omitted but does not itself declare their defaults, so the trace profile makes its choice explicit.

**Compatibility cost:** callers relying on implicit historical search in Erigon, Reth or the Geth draft fork must supply `fromBlock`. On pinned [Reth](https://github.com/paradigmxyz/reth/blob/4cd8f5f747ebb7fa6200bd880a2197b37cebdc1e/crates/rpc/rpc/src/trace.rs#L352-L393), an omitted start currently resolves to block 0; a pruned node rejects that history and even an archive node rejects a range above its [default 100-block limit](https://github.com/paradigmxyz/reth/blob/4cd8f5f747ebb7fa6200bd880a2197b37cebdc1e/crates/rpc/rpc-server-types/src/constants.rs#L17-L20). Latest/latest avoids that ordinary-request failure. Explicit history must still preserve the requested start and return a pruned-history or resource-limit error if it cannot be served; it must not silently shift to the retention boundary or truncate success.

## Decision needed

Confirm latest/latest and reversed-range error semantics with client teams; align Erigon, Reth and the experimental Geth draft fork. Agree explicit range limits and a common error code for reversed ranges; add a pruned-node explicit-history case. count limits returned records, not execution work.
