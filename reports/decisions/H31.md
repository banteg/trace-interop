# Omitted trace_callMany block

**Question:** Is trace_callMany's block argument optional, and what is its default?

H31 · Spec decision / compatibility · [All decisions](../../decisions/README.md)

**Status: ⚪ Under review** · [Status definitions](../../decisions/README.md#status-key)

No policy conclusion has been recorded. Implementation observations below do not establish client-team agreement.

[Client positions](../../decisions/README.md#client-positions): none recorded.

## Recommendation

Make the trace_callMany block argument optional and default it to latest, matching trace_call. An explicit block selector must override that default; explicit pending is handled under H32.

The same unsigned simulation should not silently change its block environment when batched. The frozen NUMBER constructor returns 48 at latest and 49 in Reth's pending environment, making the difference observable without mempool transactions.

## Background

All tested builds return NUMBER 48 for trace_callMany at explicit latest and for trace_call with omitted or explicit latest. With trace_callMany's block omitted, Besu rejects the argument count, Erigon and Nethermind return 48, and Reth returns 49. The pinned schema marks the block argument optional; see the [live capture](../../evidence/2026-09-23/h30-code-review/README.md).

Parity's [original `trace_callMany` implementation](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/impls/traces.rs#L119-L145) accepts an optional block parameter and uses the same `unwrap_or_default()` as `trace_call`; [BlockNumber's default](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/types/block_number.rs#L43-L47) is `Latest`. Both methods resolve a state and header for that selected block. Thus the proposed default follows the original namespace's API contract and the explicit-latest cross-client control, while Besu's argument-count failure is a request-shape incompatibility.

Pinned [Reth code](https://github.com/paradigmxyz/reth/blob/03cb186c1d36eebbacc7bda08f36e25711d0804e/crates/rpc/rpc/src/trace.rs#L146-L190) deliberately defaults omitted `trace_callMany` to `BlockId::pending()` and describes sequential calls atop a pending block; its observed NUMBER 49 is consistent with a next-block environment. Choosing latest intentionally changes that established Reth default when pending differs from latest. The sequential application of calls can still work under either selector, so the issue is the omitted selector's compatibility and environment, not whether callMany is sequential.

Reth main has since converged: [d8d704cf](https://github.com/paradigmxyz/reth/commit/d8d704cf7d83e3b159910bd8bd0d35b41b2813cc) "fix(rpc): default trace_callMany to latest" ([#27410](https://github.com/paradigmxyz/reth/pull/27410), 2026-09-24) uses `block_id.unwrap_or_default()` ([trace.rs](https://github.com/paradigmxyz/reth/blob/861a56167cd4eee8ed66e2bfb5d54a6b0620b40d/crates/rpc/rpc/src/trace.rs#L157)) with the test `trace_call_many_defaults_to_latest`. The pending default described above now applies only to released builds (2.6.0 and earlier).
