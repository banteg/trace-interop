# Trace block tags and pending state

**Question:** Which block tags do the trace methods accept, and how is `pending` handled?

H32 · Spec decision / client discrepancy · [All decisions](../../decisions/README.md)

**Status: ⚪ Under review** · [Status definitions](../../decisions/README.md#status-key)

No policy conclusion has been recorded. Implementation observations below do not establish client-team agreement.

[Client positions](../../decisions/README.md#client-positions): none recorded.

## Recommendation

trace_filter bounds use BlockNumberOrTagForRange: earliest, latest, safe and finalized are accepted, pending returns -32602, and earliest means the lowest block the client has available. Filter bounds do not accept a block hash or an EIP-1898 object, unlike Parity, Erigon and Nethermind; eth_getLogs selects a single block with a separate member, and a trace_filter range names blocks by number or tag. trace_call and trace_callMany accept a block number, tag or block hash (BlockNumberOrTagOrHash). trace_block, trace_replayBlockTransactions, trace_call and trace_callMany accept pending only when the client evaluates it in a real pending environment: the next block (number head+1) and that block’s header fields, and for the block methods its pending transactions. A client without one rejects pending with -32602 rather than evaluating it as latest, and a valid tag must not produce an internal error. Records traced from a pending block carry its number and the hash of the block the client built, which is not canonical; all other localized records carry canonical hashes. Resolve selectors against one consistent chain view for the request.

A caller must be able to tell whether a tag was rejected, resolved to a mined block, or evaluated in a pending environment. In the frozen fixture, safe resolves to head 48, while Reth's pending call environment exposes NUMBER 49. These observations do not establish mempool transaction inclusion.

## Background

The pinned filter schema lists earliest, finalized, safe, latest and pending, while the draft profile leaves pending-state behavior and pending localization open. In the live capture, Erigon and Nethermind resolve safe filter bounds; Besu returns -32603 and Reth -32602. Erigon development rejects pending with -32000 while its release resolves it to mined block 48; in the 2026-09-26 matrix both Erigon builds, 3.7.0 included, reject it. See the [live capture](../../evidence/2026-09-23/h30-code-review/README.md).

The explicit earliest-to-block-2 filter is compared with an explicit block-0-to-block-2 control. Nethermind release 2.0.0 · bec830cd returns [] for both. That is not a tag or history issue: before [Nethermind #13677](https://github.com/NethermindEth/nethermind/pull/13677), `trace_filter` returned the records gathered so far when a block or its parent lacked state, and genesis has no parent (H06). The development build in the current matrix, 2.1.0-preview · 82516987, contains #13677 and returns the records for both. Finalized and unavailable safe/finalized were not exercised.

Parity's original pending behavior was method-specific: the [filter type](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/types/trace_filter.rs#L44-L68) warned and silently substituted `latest`; [`trace_block`](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/impls/traces.rs#L67-L78) returned `null`; simulations and replay with a pending block argument rejected it as invalid parameters. These choices predate safe/finalized selectors and did not define a shared pending state or a way to localize mined and pending trace records consistently. That history supports specifying pending per method rather than inheriting one global tag behavior.

**Recommendation risk:** explicitly rejecting pending collection requests until a contract is agreed changes Parity's historical filter fallback and `trace_block` null response. That is probably clearer to callers, but it should be recorded as a compatibility decision. The live safe-tag checks establish parsing only on available endpoints; they do not yet prove semantics for an unavailable safe/finalized head, so the recommendation's word `resolvable` matters.

### Revised recommendation (2026-09-24 source review)

The previous recommendation left pending open for every method and did not fix the selector types. The revision decides pending for historical selectors: filter bounds use the eth_getLogs `BlockNumberOrTagForRange` type, and single-block selectors reject pending as well. Current code differs widely for `trace_block("pending")`: Reth traces its locally built pending block and localizes records with that block’s hash, which is not canonical ([trace.rs](https://github.com/paradigmxyz/reth/blob/861a56167cd4eee8ed66e2bfb5d54a6b0620b40d/crates/rpc/rpc/src/trace.rs#L523-L560)); Besu silently uses latest; Nethermind uses its pending block; Erigon and the Geth draft return an error; Parity returned null. For filter bounds, Besu returns -32603 for safe and pending, Reth rejects earliest and safe, and Erigon’s release then resolved pending to latest (3.7.0 rejects it). `earliest` now follows the shared tag definition, which the Geth draft (mapping it to block 0 even where eth_getLogs uses the history cutoff) must change. Simulations gain block-hash selectors, which Parity, Erigon, Nethermind and Reth accept and Besu rejects. The compatibility cost against Parity’s filter fallback and `trace_block` null remains as recorded above. See [filter-selection §6 and §10](../../docs/source-review/filter-selection.md) and [simulation §5](../../docs/source-review/simulation.md).

### Divergent-decisions review (2026-09-26)

The [review](../../docs/reviews/2026-09-26-divergent-decisions/H04-H23-H30-H32.md) kept the filter-bound rules: earliest, safe and finalized follow the eth_getLogs type that Erigon and Nethermind implement, and Besu’s internal error and Reth’s rejections are incidental (an incomplete resolver, and Alloy typing bounds as quantities, which also rejects "latest"). Erigon (deliberately, #22533), Besu and Reth reject a pending filter bound; only Nethermind keeps Parity’s silent latest fallback. For pending elsewhere the draft had left simulations unspecified. Besu and Nethermind accept `pending` in trace_call and trace_callMany but run at the head block (NUMBER 48), indistinguishable from latest, while Reth and Anvil provide a pending environment (NUMBER 49) and Erigon, the Geth draft and Parity reject it. Reth also traces a real pending block in trace_block; Nethermind traces the head instead, since it builds no pending block for RPC. The maintainer decision is one rule for block methods and simulations: accept pending only with a real pending environment, otherwise -32602. Parity, Erigon and Nethermind accept block-hash filter bounds, each through a generic block-selector type; the draft rejected them silently and now states the rejection as a deliberate departure.

## Decision needed

Erigon (#24345) and Nethermind (#13936) development builds now reject pending in every trace method with -32602; Besu, Nethermind 2.0.0 and Anvil trace the head block at pending, and Reth and the Geth draft return `[]` for the frozen chain’s empty pending block, which cannot show its environment. Erigon and Nethermind accept a block hash as a filter bound, as a string or an EIP-1898 object. Add block-hash simulation selectors, finalized and unavailable-finality fixtures, and a pruned filter from earliest that expects success from the retention boundary.
