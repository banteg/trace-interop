# Trace block tags and pending state

H32 · Spec decision / client discrepancy · [All decisions](../../decisions/README.md)

**Status: ⚪ Under review** · [Status definitions](../../decisions/README.md#status-key)

No policy conclusion has been recorded. Implementation observations below do not establish client-team agreement.

## Recommendation

trace_filter bounds use BlockNumberOrTagForRange: earliest, latest, safe and finalized are accepted, pending returns -32602, and earliest means the lowest block the client has available. trace_block and trace_replayBlockTransactions also reject pending with -32602 until a pending contract exists; localized records never carry a block hash that is not canonical. trace_call and trace_callMany accept a block number, tag or block hash (BlockNumberOrTagOrHash). Pending for simulations remains unspecified: a client that does not implement it must reject it explicitly, and a valid tag must not produce an internal error. Resolve selectors against one consistent chain view for the request.

A caller must be able to tell whether a tag was rejected, resolved to a mined block, or evaluated in a pending environment. In the frozen fixture, safe resolves to head 48, while Reth's pending call environment exposes NUMBER 49. These observations do not establish mempool transaction inclusion.

## Background

The pinned filter schema lists earliest, finalized, safe, latest and pending, while the draft profile leaves pending-state behavior and pending localization open. In the live capture, Erigon and Nethermind resolve safe filter bounds; Besu returns -32603 and Reth -32602. Erigon development rejects pending with -32000 while its release resolves it to mined block 48. See the [live capture](../../evidence/2026-09-23/h30-code-review/README.md).

The explicit earliest-to-block-2 filter is compared with an explicit block-0-to-block-2 control. Nethermind release 2.0.0 · bec830cd returns [] for both. That is not a tag or history issue: before [Nethermind #13677](https://github.com/NethermindEth/nethermind/pull/13677), `trace_filter` returned the records gathered so far when a block or its parent lacked state, and genesis has no parent (H06). The development build 641592d2 contains #13677 and returns the records for both. Finalized and unavailable safe/finalized were not exercised.

Parity's original pending behavior was method-specific: the [filter type](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/types/trace_filter.rs#L44-L68) warned and silently substituted `latest`; [`trace_block`](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/impls/traces.rs#L67-L78) returned `null`; simulations and replay with a pending block argument rejected it as invalid parameters. These choices predate safe/finalized selectors and did not define a shared pending state or a way to localize mined and pending trace records consistently. That history supports specifying pending per method rather than inheriting one global tag behavior.

**Recommendation risk:** explicitly rejecting pending collection requests until a contract is agreed changes Parity's historical filter fallback and `trace_block` null response. That is probably clearer to callers, but it should be recorded as a compatibility decision. The live safe-tag checks establish parsing only on available endpoints; they do not yet prove semantics for an unavailable safe/finalized head, so the recommendation's word `resolvable` matters.

### Revised recommendation (2026-09-24 source review)

The previous recommendation left pending open for every method and did not fix the selector types. The revision decides pending for historical selectors: filter bounds use the eth_getLogs `BlockNumberOrTagForRange` type, and single-block selectors reject pending as well. Current code differs widely for `trace_block("pending")`: Reth traces its locally built pending block and localizes records with that block’s hash, which is not canonical ([trace.rs](https://github.com/paradigmxyz/reth/blob/861a56167cd4eee8ed66e2bfb5d54a6b0620b40d/crates/rpc/rpc/src/trace.rs#L523-L560)); Besu silently uses latest; Nethermind uses its pending block; Erigon and the Geth draft return an error; Parity returned null. For filter bounds, Besu returns -32603 for safe and pending, Reth rejects earliest and safe, and Erigon’s release resolves pending to latest. `earliest` now follows the shared tag definition, which the Geth draft (mapping it to block 0 even where eth_getLogs uses the history cutoff) must change. Simulations gain block-hash selectors, which Parity, Erigon, Nethermind and Reth accept and Besu rejects. The compatibility cost against Parity’s filter fallback and `trace_block` null remains as recorded above. See [filter-selection §6 and §10](../../docs/source-review/filter-selection.md) and [simulation §5](../../docs/source-review/simulation.md).
