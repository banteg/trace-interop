# Trace block tags and pending state

**Question:** Which block tags do the trace methods accept, and how is `pending` handled?

H32 · Spec decision / client discrepancy · [All decisions](../../decisions/README.md)

## Recommendation

trace_filter bounds use BlockNumberOrTagForRange: earliest, latest, safe and finalized are accepted, pending is rejected (-32602 recommended), and earliest means the lowest block the client has available. An unresolvable safe or finalized tag returns an error, never head substitution or a successful empty collection. Filter bounds do not accept a block hash: a block-hash string or an EIP-1898 block-hash object as fromBlock or toBlock is rejected (-32602 recommended), as eth_getLogs range bounds reject them. Erigon and Nethermind accept both today; Parity accepted only the EIP-1898 object form, never a bare hash string, and resolved it to a number, so its hash bounds never pinned a block. A trace_filter range names blocks by number or tag; as in eth_getLogs, a single block is pinned by hash through the separate `blockHash` member specified in H33. trace_call and trace_callMany accept a block number, tag or block hash (BlockNumberOrTagOrHash). trace_block, trace_replayBlockTransactions, trace_call and trace_callMany accept pending only when the client evaluates it in a real pending environment: the next block (number head+1) and that block’s header fields, and for the block methods its pending transactions. A client without one rejects pending (-32602 recommended) rather than evaluating it as latest, and a valid tag must not produce an internal error. Records traced from a pending block carry its number and the hash of the block the client built, which is not canonical; all other localized records carry canonical hashes. Resolve selectors against one consistent chain view for the request.

A caller must be able to tell whether a tag was rejected, resolved to a mined block, or evaluated in a pending environment. In the frozen fixture, safe resolves to head 48, while Reth's pending call environment exposes NUMBER 49. These observations do not establish mempool transaction inclusion.

## Background

The pinned filter schema lists earliest, finalized, safe, latest and pending, while the draft profile leaves pending-state behavior and pending localization open. In the live capture, Erigon and Nethermind resolve safe filter bounds; Besu returns -32603 and Reth -32602. Erigon development rejects pending with -32000 while its release resolves it to mined block 48; in the 2026-09-26 matrix both Erigon builds, 3.7.0 included, reject it. See the [live capture](../../evidence/2026-09-23/h30-code-review/README.md).

The explicit earliest-to-block-2 filter is compared with an explicit block-0-to-block-2 control. Nethermind release 2.0.0 · bec830cd returns [] for both. That is not a tag or history issue: before [Nethermind #13677](https://github.com/NethermindEth/nethermind/pull/13677), `trace_filter` returned the records gathered so far when a block or its parent lacked state, and genesis has no parent (H06). The development build in the current matrix, 2.2.0-preview · 287f54f0, contains #13677 and returns the records for both. Finalized and unavailable safe/finalized were not exercised.

Parity's original pending behavior was method-specific: the [filter type](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/types/trace_filter.rs#L44-L68) warned and silently substituted `latest`; [`trace_block`](https://github.com/openethereum/parity-ethereum/blob/55c90d4016505317034e3e98f699af07f5404b63/rpc/src/v1/impls/traces.rs#L67-L78) returned `null`; simulations and replay with a pending block argument rejected it as invalid parameters. These choices predate safe/finalized selectors and did not define a shared pending state or a way to localize mined and pending trace records consistently. That history supports specifying pending per method rather than inheriting one global tag behavior.

**Recommendation risk:** explicitly rejecting pending collection requests until a contract is agreed changes Parity's historical filter fallback and `trace_block` null response. That is probably clearer to callers, but it should be recorded as a compatibility decision. The live safe-tag checks establish parsing only on available endpoints; they do not yet prove semantics for an unavailable safe/finalized head, so the recommendation's word `resolvable` matters.

### Revised recommendation (2026-09-24 source review)

The previous recommendation left pending open for every method and did not fix the selector types. The revision decides pending for historical selectors: filter bounds use the eth_getLogs `BlockNumberOrTagForRange` type, and single-block selectors reject pending as well. Current code differs widely for `trace_block("pending")`: Reth traces its locally built pending block and localizes records with that block’s hash, which is not canonical ([trace.rs](https://github.com/paradigmxyz/reth/blob/861a56167cd4eee8ed66e2bfb5d54a6b0620b40d/crates/rpc/rpc/src/trace.rs#L523-L560)); Besu silently uses latest; Nethermind uses its pending block; Erigon and the Geth draft return an error; Parity returned null. For filter bounds, Besu returns -32603 for safe and pending, Reth rejects earliest and safe, and Erigon’s release then resolved pending to latest (3.7.0 rejects it). `earliest` now follows the shared tag definition, which the Geth draft (mapping it to block 0 even where eth_getLogs uses the history cutoff) must change. Simulations gain block-hash selectors, which Parity, Erigon, Nethermind and Reth accept and Besu rejects. The compatibility cost against Parity’s filter fallback and `trace_block` null remains as recorded above. See [filter-selection §6 and §10](../../docs/source-review/filter-selection.md) and [simulation §5](../../docs/source-review/simulation.md).

### Divergent-decisions review (2026-09-26)

The [review](../../docs/reviews/2026-09-26-divergent-decisions/H04-H23-H30-H32.md) kept the filter-bound rules: earliest, safe and finalized follow the eth_getLogs type that Erigon and Nethermind implement, and Besu’s internal error and Reth’s rejections are incidental (an incomplete resolver, and Alloy typing bounds as quantities, which also rejects "latest"). Erigon (deliberately, #22533), Besu and Reth reject a pending filter bound; only Nethermind keeps Parity’s silent latest fallback. For pending elsewhere the draft had left simulations unspecified. Besu and Nethermind accept `pending` in trace_call and trace_callMany but run at the head block (NUMBER 48), indistinguishable from latest, while Reth and Anvil provide a pending environment (NUMBER 49) and Erigon and Parity reject it. The Geth draft rejected it then; in the 2026-09-29 refresh it runs trace_call and trace_callMany at pending in a real pending environment (NUMBER 0x31), as Reth and Anvil do. Reth also traces a real pending block in trace_block; Nethermind traces the head instead, since it builds no pending block for RPC. The maintainer decision is one rule for block methods and simulations: accept pending only with a real pending environment, otherwise -32602. Erigon and Nethermind accept block-hash filter bounds, and Parity accepted the EIP-1898 object form, each through a generic block-selector type; the draft rejected them silently and now states the rejection as a deliberate departure.

### Grandfathering revision (2026-09-30)

Preserve correct canonical hash-to-height range endpoints as documented optional extensions, while retaining numbers and mined tags as the portable baseline. This does not make hash range bounds exact-block identity guarantees; H33 supplies that separate capability. Accepted endpoints require a coherent canonical view and errors for unknown, noncanonical, unexecuted or unavailable endpoints. Unresolvable finality tags also error. Pending remains real execution or rejection. Erigon’s recorded agreement applies to the earlier stricter no-hash recommendation; approval of this relaxation is not inferred. See the [client review](../../docs/reviews/2026-09-30-open-policy-grandfathering/README.md).

### Client positions and reversal (2026-09-30)

[Erigon](https://github.com/ethereum/execution-apis/issues/890#issuecomment-5889999591) and [Nethermind](https://github.com/ethereum/execution-apis/issues/890#issuecomment-5910488976) both asked on execution-apis#890 for trace_filter to take the bound types of eth_getLogs: no block-hash string or EIP-1898 object as a range bound, rejected with -32602, and a separate `blockHash` member (H33) to pin one block. The grandfathering revision above, which kept canonical hash endpoints as an optional range extension, is reversed on their stated positions: hash bounds are rejected again, the pinned draft’s TraceFilter drops the hash forms, and an accepted hash bound differs even when its page equals the numeric range. The rest of that revision stands: an unresolvable safe or finalized tag is an error, and pending remains real execution or rejection. Localized records outside a pending block carry canonical hashes again, since H33 no longer serves side-chain blocks. Erigon’s earlier agreement applies again and Nethermind agrees; Reth and Besu have not answered. The captured responses are unchanged and are reassessed against the restored contract.

### Pending block with a pooled transaction (2026-10-18)

On the frozen chain an empty pending block traces as `[]`, which names no block, so the h30 `block-pending` and `replay-pending` cases left Reth and the Geth draft blocked. The ordered [`pending` corpus](../../docs/scenarios.md#pending-block) first sends one signed transfer, checks that it is pooled and not mined, and then traces pending; the h30 cases are retired. The [capture](../../evidence/2026-10-18/eval-pending/README.md) with the 2026-10-17 eval builds shows Reth 2.7.0 (both builds) and the Geth draft tracing block 49 holding the transfer under a non-canonical hash, Erigon and both Nethermind builds rejecting pending (-32602; Erigon 3.7.1 -32000), and both Besu builds tracing head block 48 and its canonical transactions, as latest. Every assessed pending block case now has a verdict.

## Decision needed

Erigon (#24345) and Nethermind (#13936) development builds reject pending in every trace method with -32602, and Erigon 3.7.0’s -32000 rejection agrees too now that the code is recommended; Besu’s internal error (-32603) for a pending filter bound is a server failure, not a rejection. At pending, Besu, Nethermind 2.0.0 and Anvil trace the head block in trace_block and trace_replayBlockTransactions; with a transaction pooled first (the `pending` corpus), Reth and the Geth draft trace block 49 holding it, while Besu still traces head block 48; in trace_call and trace_callMany, Reth, Anvil and the Geth draft run in a real pending environment (NUMBER 0x31 in the 2026-09-29 refresh), while Besu and Nethermind 2.0.0 run at the head. Erigon accepts a block hash as a filter bound, as a string or an EIP-1898 object, and needs to reject both (`h30/filter-hash-bounds` and `-object-bounds`), as Nethermind’s development build does with -32602 since #14111; pinning a single block by hash is H33. Add block-hash simulation selectors, finalized and unavailable-finality fixtures, and a pruned filter from earliest that expects success from the retention boundary.
