# Single-block hash selection in trace_filter

**Question:** Can trace_filter select exactly one block by hash, and what does a hash that is unknown or not canonical return?

H33 · Spec decision / eth_getLogs alignment · [All decisions](../../decisions/README.md)

**Status: ⚪ Under review** · [Status definitions](../../decisions/README.md#status-key)

## Recommendation

trace_filter may implement an optional `blockHash` member (a 32-byte hash), using the selector shape of eth_getLogs under EIP-234. An unsupported non-null member must be explicitly rejected (-32602 recommended), never silently ignored; universal implementation is a separate portability decision. A null member is omitted under H14, including on clients without hash-selection support. A non-null `blockHash` is mutually exclusive with non-null `fromBlock` and `toBlock` (-32602 recommended); null bounds are omitted. An accepted collection selects exactly the block with that hash: the result, including `[]`, is for that block, and every record carries that hash. Address matching, mode (including reward matching), ordering and `after`/`count` apply as for a single-block range, with the original `traceAddress` values. A known noncanonical block may return its own accurate records when the client retains the required body, branch state and execution environment; clients without that capability may explicitly reject it. Orphan support and retention are not required. Unknown, unexecuted, pruned or otherwise unavailable blocks return an error (-32001 recommended for unknown/unavailable selection; 4444 recommended for pruned history), never null, `[]`, partial results or another block’s records. Resolve and trace against one coherent view, preserving the requested identity rather than resolving a hash to a height and scanning a replacement block. Validate the selector before any `count: 0` shortcut. Range bounds use the numeric/tag baseline; correct canonical hash-to-height bounds may remain optional extensions under H32, distinct from this exact-block selector. Existing correct hash-string or EIP-1898 selectors on other trace methods remain optional capabilities; accepting `requireCanonical: true` must enforce canonicality or reject the request, never ignore the flag. This specifies exact-block-or-error semantics without requiring the full EIP-234 orphan-serving contract.

An empty trace_filter result names no block. If an indexer sees block A at height N and asks for its traces while B replaces A, `[]` from B cannot be told apart from “A has no matches”: nonempty results carry `blockHash`, but `[]` does not, and neither reading the head before and after nor a JSON-RPC batch pins the view. EIP-234 added `blockHash` to eth_getLogs for this ambiguity, and every client’s eth_getLogs implements it. H32 treats optional canonical hash range bounds as height endpoints, which do not pin a block’s identity; this decision supplies the exact-block member. Explicit rejection makes optional support detectable without attributing an empty answer to the wrong block. As in H12, support may vary while accepted requests have a precise contract. Grandfathering preserves accurate optional capabilities, not ignored fields or replacement-block results; the eth_getLogs precedent requires an error for an unknown hash-filter query, even though H06 permits null for a missing block lookup.

## Background

### Origin (2026-09-29)

Erigon [raised the question](https://github.com/ethereum/execution-apis/issues/890#issuecomment-5889999591) during H32 review: should trace_filter take the `blockHash` member that EIP-234 gave eth_getLogs? The [study](../../docs/reviews/2026-09-29-trace-filter-blockhash.md) compares current clients, eth_getLogs and the alternatives, and proposed the original mandatory, canonical-only recommendation, superseded below. It is a proposal for client review, and the draft is unchanged.

### Measured (2026-09-29)

The h30 and reorg-safe cases were [captured](../../evidence/2026-09-29/h33-blockhash/README.md) with the refresh matrix’s builds, each hash case beside the numeric filter of the same block. No build implements the member. Besu, Erigon and Nethermind accept `{blockHash: H}` and answer for another block: Besu, Erigon 3.8.0-dev and both Nethermind builds trace the head (block 0x30), and Erigon 3.7.0 scans from genesis to the head, with or without address lists, a page, null bounds or the genesis hash ([`h30/filter-blockhash`](../cases/h30/filter-blockhash.md)). Where the head has no matching records they return `[]` while block 2 has some. The three also answer an unknown hash as they answer no selector at all, return `[]` for it with `count: 0`, and answer `{blockHash, fromBlock: 0x2}` with block 2’s records; Erigon and Nethermind accept a short hash and an EIP-1898 object as well, which Besu rejects with -32602. Reth, Anvil and the Geth draft reject every non-null `blockHash` with -32602, which differed on successful-selection cases under the original mandatory proposal; these rejections satisfy the revised optional contract. A null `blockHash` beside numeric bounds is omitted by Besu, Erigon, Nethermind and the Geth draft, which drops null members, and rejected by Reth and Anvil. In reorg-safe, Besu and Nethermind answer branch A’s and branch B’s block 0x2d hashes with the current head in every phase; after the switch to B, Nethermind 2.2.0-preview returns B’s empty head, `[]`, for A’s hash, the ambiguity the member exists to remove. Reth and the Geth draft reject, and Erigon stops at the branch switch (“Invalid forkchoice state”), so its phases are blocked. `-page-past-end`, `-empty` and B’s empty block after the switch expect `[]`, so they match on the builds that ignore the member without showing that it selected anything.

### Current behavior (2026-09-29)

No client implements the member. Nethermind and Erigon have no such member, accept unknown members ([`a/filter-unknown-field`](../cases/a/filter-unknown-field.md) succeeds on both) and default omitted bounds to latest, so `{blockHash: H}` silently traces latest..latest: exactly the misattribution the member is meant to prevent, without any reorg. Besu declares `blockHash` in the `FilterParameter` it shares with eth_getLogs, but its `TraceFilter` never reads it, so it too answers for latest, and drops the hash when bounds are present. Reth (measured on 2.6.0), Anvil (both through Alloy’s `deny_unknown_fields` TraceFilter) and the Geth draft reject it with -32602. Parity had no member and rejected unknown ones. Its range bounds accepted an EIP-1898 object, but not a bare hash string, and resolved it to a number before scanning the canonical, number-indexed trace database, so a side-chain hash returned the canonical block’s traces at that height: its hash bounds never pinned a block. H14’s unknown-member rule already stops the silent latest answer in Nethermind, Erigon and Besu even without this member; [NethermindEth/nethermind#14050](https://github.com/NethermindEth/nethermind/pull/14050) does so for Nethermind.

### eth_getLogs does not settle canonicality (2026-09-29)

Every client’s eth_getLogs implements EIP-234: all reject `blockHash` combined with bounds (-32602), and an unknown hash is an error (-32000; Reth -32001). A known noncanonical hash splits them: Geth and Besu serve it (Besu marks the logs removed), Erigon, Reth and Anvil do not, and Nethermind appears from source to answer with the canonical block at that height. The execution-apis Filter schema encodes the exclusivity but specifies neither case. So “as eth_getLogs does” fixes the selector and its exclusivity, not the orphan policy. The original recommendation narrowed EIP-234 to canonical blocks: serving an orphan needs its body, its parent’s state and its branch environment, which historical canonical state retention does not provide, and it keeps H32’s rule that non-pending localized records carry canonical hashes. Canonical-only still prevents a replacement block’s `[]` from being attributed to the requested one. It also separates the two errors discussed in the [Erigon #24357 review](https://github.com/erigontech/erigon/pull/24357#discussion_r4118373485): a range bound past the head is the range rule’s -32602, and a hash outside the view is the not-found rule’s -32001.

### trace_block by hash is the weaker alternative (2026-09-29)

A hash selector on trace_block would also preserve identity, and Reth (measured on 2.6.0, canonical in practice) and Nethermind (from source, not canonical-only) already accept one. But Erigon, Besu, the Geth draft and Anvil take numbers and tags only, and the draft types trace_block and trace_replayBlockTransactions as BlockNumberOrTag, so it needs a draft change and four client changes as well. It also moves address matching, mode, pagination and the full-block response cost onto callers, and block replay is no substitute: on Reth, replaying mainnet block 1 by hash returned `[]` where trace_block returned its reward record. The trace_filter member reuses the existing matcher, ordering and pagination rules, and each client can map it onto a single-block range within one chain view in roughly 10 to 20 lines, by the study’s estimate. See [the alternatives](../../docs/reviews/2026-09-29-trace-filter-blockhash.md#the-alternatives-are-more-nuanced-than-the-message-suggests).

### Softened recommendation (2026-09-30)

The [all-method selector review](../../docs/reviews/2026-09-30-hash-selectors-all-methods.md) found method-specific hash syntax and canonicality behavior rather than a uniform trace contract. The revised recommendation follows H12’s optional-capability baseline and the sibling eth_getLogs shape: explicit rejection is allowed, but an accepted collection must belong entirely to the requested block. Accurate orphan replies are allowed where supported; unavailable orphan state is an error and no orphan retention is required. This supersedes the original mandatory-implementation, canonical-only proposal above. H14 still treats a null member as omitted, and H32’s agreed rejection of hash range bounds remains. Correct optional selector forms on other methods are preserved; ignored requireCanonical flags are not grandfathered. Erigon raised the single-block question and said either answer works, so its comment is context rather than approval of the revised recommendation. The proposal remains under review; neither a client-team consensus nor a changed pinned draft is claimed. Captured responses are unchanged; the existing cases are reassessed against the softened contract.

### Draft update (2026-09-30)

The optional exact-block-or-error proposal is now included in the [execution-apis draft](https://github.com/banteg/execution-apis/commit/6a9a69b3), and the harness pins that revision. The schema recognizes blockHash, rejects malformed hashes and hash-plus-range conflicts, and retains null omission. This advances the draft after the ledger-only softening above; it does not record client-team consensus or upstream adoption. The selected client captures are unchanged. The [Geth draft fork follow-up](https://github.com/banteg/go-ethereum/commit/ec1cec0be8) implements canonical, executed hash selection, rejects unknown/noncanonical/unexecuted hashes before count: 0, and preserves the selected block across a reorg during lookup. Its regressions, full tests, command builds, lint, generated-code and dependency checks passed. This follow-up is not part of the selected cross-client captures and does not establish upstream Geth adoption.

### Scoped canonicality feedback (2026-09-30)

The user privately relayed Erigon’s support for canonical-only hash resolution and its report that existing eth_getLogs and trace_filter hash resolution is canonical-only. There is no independently verifiable public source link; the report records a paraphrase and provenance, not the private screenshot or a public endorsement of every H33 clause. Canonical-only resolution is compatible with the revised optional exact-block-or-error proposal, which also permits accurate orphan replies where supported. This feedback does not establish implementation of the blockHash member or settle universal support. [Nethermind’s public comment](https://github.com/ethereum/execution-apis/issues/890#issuecomment-5906720536) explicitly defers H32/H33. The later H32 grandfathering revision also supersedes the earlier background’s rejection of all hash range bounds: correct optional canonical hash-to-height bounds may remain, while exact identity belongs to H33. Both decisions remain under review.

## Decision needed

Discuss the optional exact-block-or-error contract with client teams and decide universal implementation separately; the pinned draft now includes this proposal, which remains under review. The existing h30 and reorg-safe probes permit explicit rejection of non-null hash selection, while accepted canonical results must equal their numeric twins. after/filter-hash-a may return A’s retained records, compared with before/filter-tail from the same build, or reject; restored/filter-hash-b may return B’s frozen empty result or reject. Before B’s payloads arrive its hash is unknown and must error. Rejection and successful empty results do not establish hash support. Null remains omission under H14. Add state/availability and advertised-capability controls before claiming full orphan support, plus the reverse empty/nonempty reorg arrangement, a reorg between resolution and tracing, a known unexecuted header, and pruned history. Erigon’s captured reorg setup remains blocked; no new execution is claimed. Recapture the updated Geth fork against h30 and reorg-safe before claiming measured hash support in the published matrix.
