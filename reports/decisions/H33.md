# Single-block hash selection in trace_filter

**Question:** Can trace_filter select exactly one block by hash, and what does a hash that is unknown or not canonical return?

H33 · Spec decision / eth_getLogs alignment · [All decisions](../../decisions/README.md)

**Status: ⚪ Under review** · [Status definitions](../../decisions/README.md#status-key)

No policy conclusion has been recorded. Implementation observations below do not establish client-team agreement.

[Client positions](../../decisions/README.md#client-positions): none recorded.

## Recommendation

trace_filter takes a `blockHash` member (a 32-byte hash), as eth_getLogs does under EIP-234. Every client must implement it; callers may omit it. A non-null `blockHash` is mutually exclusive with non-null `fromBlock` and `toBlock` (-32602 recommended), and an explicit null for any of the three is the same as omitting it (H14). It selects exactly the block with that hash: the result, including `[]`, is for that block, and its records carry that hash. Address matching, mode (including reward matching), ordering and `after`/`count` then apply as for a single-block range, with the original `traceAddress` values. The block must be canonical in the request’s chain view and executed: an unknown, noncanonical or not-yet-executed hash, or an otherwise unavailable block, returns an error (-32001 recommended, as for an unknown single block under H06; 4444 recommended for pruned history), never `[]`, a partial result or another block’s records. Resolve the hash and trace the block in one chain view, never resolving it to a number and querying that number against a newer view. Validate the selector before any `count: 0` shortcut. Range bounds keep rejecting hashes (H32). Noncanonical (orphan) blocks, which EIP-234 serves, are out of scope and left to a later decision.

An empty trace_filter result names no block. If an indexer sees block A at height N and asks for its traces while B replaces A, `[]` from B cannot be told apart from “A has no matches”: nonempty results carry `blockHash`, but `[]` does not, and neither reading the head before and after nor a JSON-RPC batch pins the view. EIP-234 added `blockHash` to eth_getLogs for this ambiguity, and every client’s eth_getLogs implements it. H32 keeps hashes out of range bounds because eth_getLogs selects a single block with a separate member; this decision supplies that member.

## Background

### Origin (2026-09-29)

Client maintainers raised the question during H32 review: should trace_filter take the `blockHash` member that EIP-234 gave eth_getLogs? The [study](../../docs/reviews/2026-09-29-trace-filter-blockhash.md) compares current clients, eth_getLogs and the alternatives, and proposes the recommendation above. It is a proposal for client review: the draft is unchanged, and no case has been captured.

### Current behavior (2026-09-29)

No client implements the member. Nethermind and Erigon have no such member, accept unknown members ([`a/filter-unknown-field`](../cases/a/filter-unknown-field.md) succeeds on both) and default omitted bounds to latest, so `{blockHash: H}` silently traces latest..latest: exactly the misattribution the member is meant to prevent, without any reorg. Besu declares `blockHash` in the `FilterParameter` it shares with eth_getLogs, but its `TraceFilter` never reads it, so it too answers for latest, and drops the hash when bounds are present. Reth (measured on 2.6.0), Anvil (both through Alloy’s `deny_unknown_fields` TraceFilter) and the Geth draft reject it with -32602. Parity had no member and rejected unknown ones. Its range bounds accepted an EIP-1898 object, but not a bare hash string, and resolved it to a number before scanning the canonical, number-indexed trace database, so a side-chain hash returned the canonical block’s traces at that height: its hash bounds never pinned a block. H14’s unknown-member rule already stops the silent latest answer in Nethermind, Erigon and Besu even without this member; [NethermindEth/nethermind#14050](https://github.com/NethermindEth/nethermind/pull/14050) does so for Nethermind.

### eth_getLogs does not settle canonicality (2026-09-29)

Every client’s eth_getLogs implements EIP-234: all reject `blockHash` combined with bounds (-32602), and an unknown hash is an error (-32000; Reth -32001). A known noncanonical hash splits them: Geth and Besu serve it (Besu marks the logs removed), Erigon, Reth and Anvil do not, and Nethermind appears from source to answer with the canonical block at that height. The execution-apis Filter schema encodes the exclusivity but specifies neither case. So “as eth_getLogs does” fixes the selector and its exclusivity, not the orphan policy. The recommendation narrows EIP-234 to canonical blocks: serving an orphan needs its body, its parent’s state and its branch environment, which historical canonical state retention does not provide, and it keeps H32’s rule that non-pending localized records carry canonical hashes. Canonical-only still prevents a replacement block’s `[]` from being attributed to the requested one. It also separates the two errors discussed in the [Erigon #24357 review](https://github.com/erigontech/erigon/pull/24357#discussion_r4118373485): a range bound past the head is the range rule’s -32602, and a hash outside the view is the not-found rule’s -32001.

### trace_block by hash is the weaker alternative (2026-09-29)

A hash selector on trace_block would also preserve identity, and Reth (measured on 2.6.0, canonical in practice) and Nethermind (from source, not canonical-only) already accept one. But Erigon, Besu, the Geth draft and Anvil take numbers and tags only, and the draft types trace_block and trace_replayBlockTransactions as BlockNumberOrTag, so it needs a draft change and four client changes as well. It also moves address matching, mode, pagination and the full-block response cost onto callers, and block replay is no substitute: on Reth, replaying mainnet block 1 by hash returned `[]` where trace_block returned its reward record. The trace_filter member reuses the existing matcher, ordering and pagination rules, and each client can map it onto a single-block range within one chain view in roughly 10 to 20 lines, by the study’s estimate. See [the alternatives](../../docs/reviews/2026-09-29-trace-filter-blockhash.md#the-alternatives-are-more-nuanced-than-the-message-suggests).
