# Single-block hash selection in trace_filter

**Question:** Can trace_filter select exactly one block by hash, and what does a hash that is unknown or not canonical return?

H33 · Spec decision / eth_getLogs alignment · [All decisions](../../decisions/README.md)

**Status: 🤝 Converged** · [Status definitions](../../decisions/README.md#status-key)

Converged on a canonical-only blockHash member for trace_filter, in the EIP-234 shape: mutually exclusive with non-null bounds (-32602 recommended), exactly the hashed block including [], and an error rather than [] or another block’s records for an unknown or noncanonical hash. Nethermind asked for this contract publicly and its development build implements it (#14111); Erigon raised the member publicly and privately supports canonical-only resolution. Reth and Besu have not answered. Serving side-chain blocks is out of scope. Direction aligned, not unanimous formal approval.

Policy evidence: [Erigon on execution-apis#890](https://github.com/ethereum/execution-apis/issues/890#issuecomment-5889999591) · [Nethermind on execution-apis#890 (H32/H33)](https://github.com/ethereum/execution-apis/issues/890#issuecomment-5910488976).

## Recommendation

trace_filter takes a `blockHash` member (a 32-byte hash), in the shape EIP-234 gave eth_getLogs. It is part of the trace_filter contract, as H01 admits no optional subsets: clients implement it, and callers may omit it. A non-null `blockHash` is mutually exclusive with non-null `fromBlock` and `toBlock` (-32602 recommended), and an explicit null for any of the three is the same as omitting it (H14). It selects exactly the block with that hash: the result, including `[]`, is for that block, and its records carry that hash. Address matching, mode (including reward matching), ordering and `after`/`count` then apply as for a single-block range, with the original `traceAddress` values. The block must be canonical in the request’s chain view and executed: an unknown, noncanonical or not-yet-executed hash, or an otherwise unavailable block, returns an error (-32001 recommended, as for an unknown single block under H06; 4444 recommended for pruned history), never `[]`, a partial result or another block’s records. Resolve the hash and trace the block in one chain view, never resolving it to a number and querying that number against a newer view. Validate the selector before any `count: 0` shortcut. Range bounds keep rejecting hashes (H32). Existing correct hash-string or EIP-1898 selectors on other trace methods remain optional capabilities; accepting `requireCanonical: true` must enforce canonicality or reject the request, never ignore the flag. Serving noncanonical (side-chain) blocks, which EIP-234 allows for eth_getLogs, is out of scope: it is not permitted now and is left as a possible later extension.

An empty trace_filter result names no block. If an indexer sees block A at height N and asks for its traces while B replaces A, `[]` from B cannot be told apart from “A has no matches”: nonempty results carry `blockHash`, but `[]` does not, and neither reading the head before and after nor a JSON-RPC batch pins the view. EIP-234 added `blockHash` to eth_getLogs for this ambiguity, and every client’s eth_getLogs implements it. H32 keeps hashes out of range bounds because eth_getLogs selects a single block with a separate member; this decision supplies that member. Canonical-only selection needs no side-chain body, parent state or branch environment, keeps H32’s canonical localization, and still prevents a replacement block’s `[]` from being attributed to the requested one. As in eth_getLogs, an unknown hash-filter query is an error, even though H06 permits null for a missing block lookup.

## Background

### Origin (2026-09-29)

Erigon [raised the question](https://github.com/ethereum/execution-apis/issues/890#issuecomment-5889999591) during H32 review: should trace_filter take the `blockHash` member that EIP-234 gave eth_getLogs? The [study](../../docs/reviews/2026-09-29-trace-filter-blockhash.md) compares current clients, eth_getLogs and the alternatives, and proposed the mandatory, canonical-only recommendation above. It was softened and then restored on 2026-09-30, as recorded below.

### Measured (2026-09-29)

The h30 and reorg-safe cases were [captured](../../evidence/2026-09-29/h33-blockhash/README.md) with the refresh matrix’s builds, each hash case beside the numeric filter of the same block. No build implements the member. Besu, Erigon and Nethermind accept `{blockHash: H}` and answer for another block: Besu, Erigon 3.8.0-dev and both Nethermind builds trace the head (block 0x30), and Erigon 3.7.0 scans from genesis to the head, with or without address lists, a page, null bounds or the genesis hash ([`h30/filter-blockhash`](../cases/h30/filter-blockhash.md)). Where the head has no matching records they return `[]` while block 2 has some. The three also answer an unknown hash as they answer no selector at all, return `[]` for it with `count: 0`, and answer `{blockHash, fromBlock: 0x2}` with block 2’s records; Erigon and Nethermind accept a short hash and an EIP-1898 object as well, which Besu rejects with -32602. Reth, Anvil and the Geth draft reject every non-null `blockHash` with -32602, so they pass the error cases and differ wherever a result is expected. A null `blockHash` beside numeric bounds is omitted by Besu, Erigon, Nethermind and the Geth draft, which drops null members, and rejected by Reth and Anvil. In reorg-safe, Besu and Nethermind answer branch A’s and branch B’s block 0x2d hashes with the current head in every phase; after the switch to B, Nethermind 2.2.0-preview returns B’s empty head, `[]`, for A’s hash, the ambiguity the member exists to remove. Reth and the Geth draft reject, and Erigon stops at the branch switch (“Invalid forkchoice state”), so its phases are blocked. `-page-past-end`, `-empty` and B’s empty block after the switch expect `[]`, so they match on the builds that ignore the member without showing that it selected anything.

### Current behavior (2026-09-29)

No client implements the member. Nethermind and Erigon have no such member, accept unknown members ([`a/filter-unknown-field`](../cases/a/filter-unknown-field.md) succeeds on both) and default omitted bounds to latest, so `{blockHash: H}` silently traces latest..latest: exactly the misattribution the member is meant to prevent, without any reorg. Besu declares `blockHash` in the `FilterParameter` it shares with eth_getLogs, but its `TraceFilter` never reads it, so it too answers for latest, and drops the hash when bounds are present. Reth (measured on 2.6.0), Anvil (both through Alloy’s `deny_unknown_fields` TraceFilter) and the Geth draft reject it with -32602. Parity had no member and rejected unknown ones. Its range bounds accepted an EIP-1898 object, but not a bare hash string, and resolved it to a number before scanning the canonical, number-indexed trace database, so a side-chain hash returned the canonical block’s traces at that height: its hash bounds never pinned a block. H14’s unknown-member rule already stops the silent latest answer in Nethermind, Erigon and Besu even without this member; [NethermindEth/nethermind#14050](https://github.com/NethermindEth/nethermind/pull/14050) does so for Nethermind.

### eth_getLogs does not settle canonicality (2026-09-29)

Every client’s eth_getLogs implements EIP-234: all reject `blockHash` combined with bounds (-32602), and an unknown hash is an error (-32000; Reth -32001). A known noncanonical hash splits them: Geth and Besu serve it (Besu marks the logs removed), Erigon, Reth and Anvil do not, and Nethermind appears from source to answer with the canonical block at that height. The execution-apis Filter schema encodes the exclusivity but specifies neither case. So “as eth_getLogs does” fixes the selector and its exclusivity, not the orphan policy. The recommendation narrows EIP-234 to canonical blocks: serving an orphan needs its body, its parent’s state and its branch environment, which historical canonical state retention does not provide, and it keeps H32’s rule that non-pending localized records carry canonical hashes. Canonical-only still prevents a replacement block’s `[]` from being attributed to the requested one. It also separates the two errors discussed in the [Erigon #24357 review](https://github.com/erigontech/erigon/pull/24357#discussion_r4118373485): a range bound past the head is the range rule’s -32602, and a hash outside the view is the not-found rule’s -32001.

### trace_block by hash is the weaker alternative (2026-09-29)

A hash selector on trace_block would also preserve identity, and Reth (measured on 2.6.0, canonical in practice) and Nethermind (from source, not canonical-only) already accept one. But Erigon, Besu, the Geth draft and Anvil take numbers and tags only, and the draft types trace_block and trace_replayBlockTransactions as BlockNumberOrTag, so it needs a draft change and four client changes as well. It also moves address matching, mode, pagination and the full-block response cost onto callers, and block replay is no substitute: on Reth, replaying mainnet block 1 by hash returned `[]` where trace_block returned its reward record. The trace_filter member reuses the existing matcher, ordering and pagination rules, and each client can map it onto a single-block range within one chain view in roughly 10 to 20 lines, by the study’s estimate. See [the alternatives](../../docs/reviews/2026-09-29-trace-filter-blockhash.md#the-alternatives-are-more-nuanced-than-the-message-suggests).

### Softened recommendation (2026-09-30)

The [all-method selector review](../../docs/reviews/2026-09-30-hash-selectors-all-methods.md) found method-specific hash syntax and canonicality behavior rather than a uniform trace contract. The revised recommendation follows H12’s optional-capability baseline and the sibling eth_getLogs shape: explicit rejection is allowed, but an accepted collection must belong entirely to the requested block. Accurate orphan replies are allowed where supported; unavailable orphan state is an error and no orphan retention is required. This supersedes the original mandatory-implementation, canonical-only proposal above. H14 still treats a null member as omitted, and H32’s agreed rejection of hash range bounds remains. Correct optional selector forms on other methods are preserved; ignored requireCanonical flags are not grandfathered. Erigon raised the single-block question and said either answer works, so its comment is context rather than approval of the revised recommendation. The proposal remains under review; neither a client-team consensus nor a changed pinned draft is claimed. Captured responses are unchanged; the existing cases are reassessed against the softened contract.

### Draft update (2026-09-30)

The optional exact-block-or-error proposal is now included in the [execution-apis draft](https://github.com/banteg/execution-apis/commit/6a9a69b3), and the harness pins that revision. The schema recognizes blockHash, rejects malformed hashes and hash-plus-range conflicts, and retains null omission. This advances the draft after the ledger-only softening above; it does not record client-team consensus or upstream adoption. The selected client captures are unchanged. The [Geth draft fork follow-up](https://github.com/banteg/go-ethereum/commit/ec1cec0be8) implements canonical, executed hash selection, rejects unknown/noncanonical/unexecuted hashes before count: 0, and preserves the selected block across a reorg during lookup. Its regressions, full tests, command builds, lint, generated-code and dependency checks passed. This follow-up is not part of the selected cross-client captures and does not establish upstream Geth adoption.

### Scoped canonicality feedback (2026-09-30)

The user privately relayed Erigon’s support for canonical-only hash resolution and its report that existing eth_getLogs and trace_filter hash resolution is canonical-only. There is no independently verifiable public source link; the report records a paraphrase and provenance, not the private screenshot or a public endorsement of every H33 clause. Canonical-only resolution is compatible with the revised optional exact-block-or-error proposal, which also permits accurate orphan replies where supported. This feedback does not establish implementation of the blockHash member or settle universal support. [Nethermind’s public comment](https://github.com/ethereum/execution-apis/issues/890#issuecomment-5906720536) explicitly defers H32/H33. The later H32 grandfathering revision also supersedes the earlier background’s rejection of all hash range bounds: correct optional canonical hash-to-height bounds may remain, while exact identity belongs to H33. Both decisions remain under review.

### Client positions and reversal (2026-09-30)

[Nethermind](https://github.com/ethereum/execution-apis/issues/890#issuecomment-5910488976) asked on execution-apis#890 for the stricter contract: add a `blockHash` member to trace_filter, reject hash bounds (-32602), reject a non-null `blockHash` together with `fromBlock` or `toBlock`, and return an error, not `[]`, for an unknown or non-canonical hash. [Erigon](https://github.com/ethereum/execution-apis/issues/890#issuecomment-5889999591) raised the member and said either answer works for it, and its feedback recorded above supports canonical-only resolution. The softened recommendation and the orphan allowance in the draft update above are therefore reversed. The member is part of the contract, since H01 admits no optional subsets, so rejecting a well-formed non-null hash differs wherever a selection is expected. A noncanonical hash must be an error, and an ignored member or an orphan-served result differs. Serving side-chain blocks is not permitted now; it is left as a possible later extension. The `requireCanonical` rule for optional hash selectors on other methods stands. The pinned draft now states the canonical-only member, and the captured h30 and reorg-safe responses are reassessed against it without new captures. Nethermind and Erigon agree; Reth and Besu have not answered.

### Geth draft capture (2026-09-30)

The [2026-09-30 eval](../../evidence/2026-09-30/eval/README.md) captured the Geth draft follow-up (ec1cec0be8). It answers each hash case with block 2’s records alone, and the genesis hash and a page past the end with `[]`; it rejects a hash with non-null bounds and a malformed hash with -32602, and an unknown hash with -32001, also with `count: 0`. In reorg-safe, A’s hash after the switch and B’s after the restore return -32001 (“is not canonical”). All its H33 cases agree. This measures the draft fork, not upstream Geth adoption.

### Nethermind capture (2026-10-01)

The [2026-10-01 eval](../../evidence/2026-10-01/eval/README.md) captured Nethermind 2.2.0-preview · 759efed7, which includes #14111. It answers each hash case with block 2’s records, and the genesis hash and a page past the end with `[]`; it rejects a hash with non-null bounds and a malformed hash with -32602, and an unknown hash with -32000 (“header not found”), also with `count: 0`. In reorg-safe, A’s hash after the switch and B’s after the restore return -32000 (“block is not canonical”). All its H33 cases agree; the code differs from the recommended -32001, which is not required. Nethermind 2.0.0 still ignores the member.

## Decision needed

Implement the member: Besu (read the parsed `blockHash`), Erigon, and Reth and Anvil through Alloy’s `TraceFilter`. The pinned draft (banteg/execution-apis d45f4366) states the contract. The [h30 and reorg-safe cases](../../evidence/2026-09-29/h33-blockhash/README.md) measure it: an implementation passes `h30/filter-blockhash`, `-address-from`, `-address-to`, `-union`, `-page`, `-null-bounds` and `-genesis` only by answering block 2’s records (or genesis’s `[]`), and the reorg-safe `after/filter-hash-a` and `restored/filter-hash-b` only by an error once the block is noncanonical; a rejection of a well-formed hash differs wherever a selection is expected. The [2026-09-30 eval](../../evidence/2026-09-30/eval/README.md) measures the Geth draft at ec1cec0be8, which implements the canonical-only member and passes every captured case, including the reorg phases. The [2026-10-01 eval](../../evidence/2026-10-01/eval/README.md) measures Nethermind’s #14111 in 759efed7, which passes every captured case, including the reorg phases, with -32000 where -32001 is recommended, and the Geth draft at 67f41deaa0, whose responses are unchanged. That build includes 26f398b982, which returns -32001 when the selected block is reorganized out while it is traced, reads the executed head before the canonical lookup, and pins hash and EIP-1898 bound rejection and 4444 for a pruned selection; the frozen cases do not exercise those paths. `reorg` carries the same cases uncaptured. Erigon’s phases stay blocked until its forkchoice fix ([#24032](https://github.com/erigontech/erigon/pull/24032)) lands. Not yet covered: the reverse arrangement, where the replacing block has records and the replaced one none (the frozen B branch has only empty blocks, so it needs a new branch fixture); a reorg between resolving the hash and tracing the block, which needs a client test hook; a known header ahead of execution; and pruned history.
